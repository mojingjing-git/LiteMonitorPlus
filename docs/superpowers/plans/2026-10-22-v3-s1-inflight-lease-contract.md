## 1. 现状（已核实，行号对应 `9ffb4219`）

### 1.1 键的构成

```csharp
// src/Plugins/PluginExecutor.cs:284-285
string contentHash = (url + "|" + body).GetHashCode().ToString("X");
string cacheKey = $"{inst.Id}{keySuffix}_{step.Id}_{contentHash}";
```

| 维度 | 是否已入键 | 说明 |
|---|---|---|
| 实例 ID | ✅ 已有 | `inst.Id` |
| 目标索引 | ✅ 已有 | `keySuffix`（`.0` `.1` …） |
| 步骤 ID | ✅ 已有 | `step.Id` |
| URL | ✅ 已有 | 但经 `ResolveTemplate` 后 |
| 请求体 | ✅ 已有 | |
| **HTTP 方法** | ❌ 缺失 | `step.Method` 未入键 |
| **影响响应的 Header** | ❌ 缺失 | `resolvedHeaders`（含 `Authorization`、`Cookie`）传入请求但**不入键** |
| **代理配置** | ❌ 缺失 | `step.Proxy` 未入键 |
| **响应编码** | ❌ 缺失 | `step.ResponseEncoding` 未入键 |
| 摘要算法 | ⚠️ `GetHashCode()` | 32 位、**进程内加盐**、每次运行可能不同、非抗碰撞 |

### 1.2 由此产生的三个具体缺陷

1. **凭据串用（安全）**：两个步骤 URL 与 body 相同但 `Authorization` 不同 → 共享同一条在途请求与同一条缓存条目。缓存条目里可能存着**另一个凭据**取回的响应。
2. **代理串用**：同 URL/body 但代理不同 → 共用一条走错代理的请求。
3. **合并失效（性能）**：`GetHashCode()` 在不同进程/不同次运行下不同 → 键不可跨进程复现；且它是弱摘要，碰撞概率不可忽略。

### 1.3 在途合并的三个竞态

```csharp
// src/Plugins/PluginExecutor.cs:324
var task = _inflightRequests.GetOrAdd(cacheKey, _ => FetchRawAsync(...));

// src/Plugins/PluginExecutor.cs:346（catch 内）
_inflightRequests.TryRemove(cacheKey, out _);
// src/Plugins/PluginExecutor.cs:351（finally 内，无条件）
_inflightRequests.TryRemove(cacheKey, out _);
```

| 竞态 | 说明 |
|---|---|
| **工厂并发** | `ConcurrentDictionary.GetOrAdd` 的 valueFactory **可能并发执行多次**。即两个线程同时到达同一键时，**可能发出两个 HTTP 请求**，合并保证不成立。 |
| **双份移除** | `catch` 与 `finally` 各做一次无条件 `TryRemove`，共两次。 |
| **过早移除** | `finally` 在**成功路径也执行**，且是**每个等待者各自**执行。第一个等待者拿到结果就把条目删掉 → 后续到达者无法加入正在进行的请求，合并窗口坍缩。 |
| **误删新条目** | 旧任务的 `finally` 与新到达者刚插入的条目竞争时，旧任务会删掉**新条目**（无条件移除，不校验身份）。 |

### 1.4 共享任务与取消

`FetchRawAsync` 在 `:324` 以 `CancellationToken.None` 启动 —— 共享请求本身**不被任何等待者取消**；每个等待者用独立的 `TaskCompletionSource` + `token.Register` 自行超时/取消（`:329-334`）。这个形状是**对的**，应保留：它天然满足"取消一个等待者不影响其他等待者"。缺陷在于条目管理，不在取消语义。

### 1.5 客户端重置联动

```csharp
// src/Plugins/PluginManager.cs:391-396（连续失败第 3 次时）
_executor.ResetNetworkClients();
_executor.ClearCache(inst.Id);
```

`ResetNetworkClients()`（`PluginExecutor.cs` 构造函数之后、`InitializeDefaultClient` / 旧客户端释放处）会**替换并释放** `HttpClient` 实例。被释放客户端上的在途请求会中止。

### 1.6 缓存清理依赖键结构

`ClearCache(inst.Id)` 依赖缓存键**以实例 ID 开头**做前缀匹配。若把缓存键改成纯摘要，该清理会失效。

## 2. 冻结的契约

### C1 · 请求身份（RequestIdentity）

定义一个结构化身份对象，其字段为：

| 字段 | 规则 |
|---|---|
| `InstanceId` | `inst.Id`（已有） |
| `TargetIndex` | `keySuffix`（已有） |
| `StepId` | `step.Id`（已有） |
| `Method` | `step.Method`，**大写规范化**；未指定按 `GET` |
| `CanonicalUrl` | 由 `Uri` 解析：`scheme` 与 `host` 转小写；移除 `fragment`；**保留** `path` 与 `query` 原样（不重排 query——顺序可能影响语义）；非默认端口保留 |
| `Body` | `ResolveTemplate` 之后的请求体原文 |
| `Headers` | **步骤级 Header 的全部**（解析占位符之后），按名排序后拼接。**不做白名单过滤**——漏掉一个携带凭据的 header 造成的串用，比合并机会减少更严重 |
| `Proxy` | `step.Proxy`（解析占位符之后）；无则为空串 |
| `ResponseEncoding` | `step.ResponseEncoding`；无则为空串 |

> **注意**：`InstanceId` / `TargetIndex` / `StepId` **已经**在现行键中。实施时**不得**把它们当作"新加项"重复编码，也**不得**在改造中把它们从键里去掉（见 C4 的缓存清理约束）。

### C2 · 摘要算法

- 用 **SHA-256** 对上述字段按固定顺序、以长度前缀或分隔符无歧义地拼接后取摘要，输出十六进制，**取前 32 个十六进制字符（128 位）**。
- **禁止**继续使用 `GetHashCode()` 作为等价依据。
- **禁止**用 `GetHashCode()` 参与任何"两请求是否等价"的判断。

### C3 · 在途租约模型

目标：保证**同一身份下任意时刻只有一个 HTTP 请求在途**，且条目生命周期与任务生命周期解耦。

必须满足：

1. **原子获取**：`GetOrAdd` 的 valueFactory **不得**直接启动 HTTP 请求。推荐形态（二选一，实现时说明选了哪个）：
   - `ConcurrentDictionary<string, Lazy<Task<string>>>`，`Lazy` 使用 `LazyThreadSafetyMode.ExecutionAndPublication`；或
   - 条目为自研租约对象，内部用锁保证"任务只创建一次"，外部再包一层"等待者计数"。
2. **比较后移除**：条目移除必须使用**带值比较**的原子移除（`ConcurrentDictionary<TKey,TValue>.TryRemove(KeyValuePair<TKey,TValue>)` 语义），即**仅当字典中该键当前映射的值仍是本条目时才移除**。禁止无条件 `TryRemove(key, out _)`。
3. **移除时机**：仅在共享任务**终结**（成功或异常）时移除一次，由任务自身的延续（continuation）驱动。**每个等待者的 `finally` 不得移除条目。**
4. **等待者取消**：等待者取消只释放自己的等待（`TaskCompletionSource` + `token.Register`），**不得**触碰字典条目、不得取消共享任务、不得影响其他等待者。共享请求以 `CancellationToken.None` 启动这一现状**保持不变**。
5. **共享任务的失败**：共享任务失败时，所有等待者都应收到该失败；失败后条目按第 3 条移除，下一批到达者可重新发起。

### C4 · 缓存身份与 `ClearCache` 兼容性

- **缓存条目必须包含全部影响响应的字段**（否则缓存会返回另一凭据/另一代理下的响应）。
- **缓存键必须继续包含实例 ID 前缀**，或改用可按实例过滤的条目结构，使 `ClearCache(inst.Id)` 仍然有效。**若放弃实例前缀而改用条目字段过滤，必须同时给出等效实现并说明。**
- 缓存键与在途键**允许不同**：
  - 推荐：缓存键 = `实例ID | 目标索引 | 步骤ID | 摘要`（保持现状的"每实例各存各的"语义，`ClearCache` 前缀匹配继续可用）；
  - 在途键 = `摘要`（**允许跨实例合并**相同请求——同身份同响应，语义安全）。
  - 若实现方选择不跨实例合并，须说明理由，且在途键仍须包含 C1 全部字段。
- 缓存命中判定与在途合并判定**不得**共用同一套不完整的字段集。

### C5 · `ResetNetworkClients()` 联动

必须满足：

1. **在途条目不绑定 `HttpClient` 实例**。条目管理与客户端生命周期解耦：客户端被替换时，**不得**清空在途字典。
2. **不得**因为客户端重置而主动取消正在进行的共享请求。允许它们因旧客户端被释放而自然失败。
3. 客户端重置导致的中止，**必须**走**普通异常路径**返回给等待者（可诊断的异常类型或明确的错误分类），**不得**触发递归重置、不得放大为重置风暴。
4. `ResetNetworkClients()` 是**全局**动作，而 `fails` 计数是**按实例**的。因此必须明确并实现一条规则：**单个实例的连续失败不得独立地反复触发全局客户端重置**。至少要做到重置是幂等且有上限的（例如同一时间窗内至多一次）。实施方须说明所选规则。
5. **`ResetNetworkClients()` 的公开签名不得改变**。节流逻辑必须实现**在方法内部**，不得要求调用方传入新参数或调整调用顺序——调用点位于 `src/Plugins/PluginManager.cs`（S1.1 的 ownership），而本方法位于 `src/Plugins/PluginExecutor.cs`（S1.2 的 ownership）。两者由不同 worker 并行实施，签名变化会造成跨文件冲突。

### C6 · 与 LM-001（计时器）的一致性

S1.1 引入的"实例代次"机制必须与本契约协同：

- 实例代次变化（重启）后，**旧代次**的在途等待者不得写回结果。
- 代次**不得**用于区分在途键——两个代次的同一身份请求可以共享（响应相同）；代次只用于**结果写回**的裁决。

### C7 · 禁止事项

- 禁止为了"合并率更高"而**削弱身份字段**（例如把 Header 收敛成白名单）。
- 禁止改变插件的刷新间隔、退避节奏、缓存时长等**用户可见语义**。
- 禁止放宽既有断言、删除测试或扩大异常吞噬范围。
- 禁止在 `PluginExecutor.cs` 之外新增对在途字典的直接访问。

## 3. 验收矩阵（三个 worker 合并执行）

以下每一条都必须在 `tests/LiteMonitor.Tests/` 下有**对应的新测试**（S1.1 与 S1.2 可各自建文件，S1.3 建 `HttpLifecycleTests.cs`），且**必须真正执行**（不得早退冒充通过）。

### 3.1 身份隔离（LM-002）

| # | 断言 |
|---|---|
| I1 | URL 与 body 相同、`Authorization` 不同 → **两条**独立请求，不共享在途、不共享缓存 |
| I2 | URL 与 body 相同、`Cookie` 不同 → 同上 |
| I3 | URL 与 body 相同、方法不同（GET vs POST）→ 同上 |
| I4 | URL 与 body 相同、代理不同 → 同上 |
| I5 | URL 与 body 相同、响应编码不同 → 同上 |
| I6 | 完全相同的身份（含全部 header）→ **共享一条**在途请求（合并仍然有效） |
| I7 | 同一请求在**不同进程/不同次运行**下产生**相同**的摘要（证明不再依赖 `GetHashCode()` 的进程内加盐） |

### 3.2 合并与竞态（LM-002）

| # | 断言 |
|---|---|
| R1 | N 个并发等待者发起**同一**身份请求 → 实际发出的 HTTP 请求数 **== 1** |
| R2 | 旧任务完成时，字典中已存在**同键的新条目** → 旧任务的收尾**不得**删除新条目 |
| R3 | 一个等待者取消 → 共享请求**继续**执行；其他等待者**仍拿到结果** |
| R4 | 全部等待者取消 → 条目最终被清理（不泄漏） |
| R5 | 共享任务失败 → 所有等待者收到失败；条目被清理；后续请求可重新发起 |

### 3.3 缓存（LM-002 / LM-008 联动）

| # | 断言 |
|---|---|
| C1c | 不同凭据的同名请求**不共享**缓存条目 |
| C2c | `ClearCache(inst.Id)` 之后该实例的缓存被清空，其他实例的**不受影响** |
| C3c | 缓存条目的身份字段与在途身份字段**一致**（不得出现"在途隔离了但缓存没隔离"） |

### 3.4 客户端重置联动（C5）

| # | 断言 |
|---|---|
| X1 | `ResetNetworkClients()` 调用后，在途字典**不被清空** |
| X2 | 重置导致的中止以**普通异常**返回给等待者，不触发递归重置 |
| X3 | 单个实例连续失败**不会**在时间窗内反复触发全局重置（给出所选上限规则） |

### 3.5 计时器（LM-001，S1.1）

| # | 断言 |
|---|---|
| T1 | 启动即可见 → 能执行 |
| T2 | 启动即不可见 → 变可见后**恢复执行** |
| T3 | 可见→不可见→可见 → 轮询持续 |
| T4 | 执行期间被禁用 → 不重复启动 |
| T5 | 失败进入退避 → 成功恢复周期 |
| T6 | 快速停止/启动/重启 → 无并发重复执行 |
| T7 | 取消 → 无未观察的异步异常 |
| T8 | **Stop 返回后**旧任务不重新调度、**不写回结果**；Restart 后**最多一个**有效调度 |

### 3.6 HTTP 资源与期限（LM-003，S1.2 / S1.3）

| # | 断言 |
|---|---|
| H1 | 插件响应被正确释放（无响应泄漏） |
| H2 | 响应体超过字节上限 → **明确失败**且连接归还 |
| H3 | 更新元数据请求的 `HttpRequestMessage`、`HttpResponseMessage`、`JsonDocument` 均被释放 |
| H4 | `ResponseHeadersRead` 之后正文读取有**独立**期限，超时能中断 |
| H5 | 镜像测速正文读取有独立取消期限 |
| H6 | **不得**改动 `UpdateChecker` 现有验签实现（`UpdateSignatureTests.cs` 必须仍全通过） |
