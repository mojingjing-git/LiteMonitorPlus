## 3. M1：更新失败时可靠恢复并如实报告（F1）

主要文件：

- `LiteMonitor.Updater/Program.cs`，必要时提取更新器内部的文件应用组件。
- `src/UI/Helpers/MainFormBizHelper.cs`，只整合更新完成、恢复及中断状态的提示。
- 更新器专用测试；优先为文件应用组件建独立测试工程，仅在确有需要时调整解决方案。

修改步骤：

1. 将“文件原先是否存在、备份位置、是否进入提交阶段、恢复结果”作为明确的文件恢复记录。记录必须在可能修改目标文件前可用，不得等摘要验证成功后才登记。
2. 在目标文件同目录写入暂存文件并完成长度、摘要验证，然后使用同卷的替换操作提交已有文件；新增文件用移动提交。提交失败不能静默退回直接覆盖目标文件的旧路径。
3. 任何提交或后续验证失败，都把当前文件和已完成文件纳入恢复。已有文件恢复原内容；本次新增的文件恢复为原先不存在的状态。恢复失败应保留备份和足够的诊断信息。
4. 汇总输出区分成功、失败但已恢复、失败且恢复不完整。`Rollback` 返回实际结果，不能在恢复失败后仍宣称已恢复原版本。
5. 整合现有状态标记读取逻辑。仅凭 `update_in_progress` 不能宣称“程序未被替换”；中断后应说明状态未确认，并指明保留的恢复材料。进程突然结束后的多文件事务恢复若未实现，不得宣称整个安装具备崩溃原子性。

验收：

- 暂存写入或校验失败：原目标内容不变。
- 当前文件提交失败、提交后的验证失败：当前文件和此前文件均有明确恢复结果。
- 新增文件后发生失败：能恢复其原先不存在的状态。
- 恢复本身失败：结果可见，备份保留，不报告全部恢复成功。
- 成功路径仍可更新并启动目标应用；测试替身不执行真实进程结束或启动命令。

## 4. M2：停止后不再授予旧请求采样需求（F3）

主要文件：`src/System/WebServer/WebSessionManager.cs`、`tests/LiteMonitor.Tests/WebDemandTests.cs`、`tests/LiteMonitor.Tests/WebSamplingDemandTests.cs`。只有现有接口无法表达回归时，才调整同步器或服务器生命周期代码。

修改步骤：

1. 在与 Stop 相同的 `_clientsGate` 临界区内完成运行状态检查、连接代次检查及 HTTP 租约授予。审查现有锁顺序，避免引入反向加锁。
2. 需求通知留在锁外；不在锁内执行网络写入或等待异步操作。
3. 保留既有在途 HTTP 响应约定：允许响应完成与允许授予采样需求分别判断。快速停止再启动后，旧连接也不能借用新一代的运行状态授予需求。
4. 不简单地让所有未运行状态的 `SyncNow` 都返回；初始化与停止时向硬件传播 false 的既有调用必须继续有效。

验收：

- 用可控同步点覆盖请求检查与 Stop 交错的边界，Stop 完成后旧请求不能产生需求。
- 快速重启后，旧请求不能修改新代次的需求；新请求仍能正常授予。
- 停止后推进可控时钟，需求状态和最后应用的硬件需求均为 false。
- 既有 HTTP 响应、WebSocket 需求、租约正常到期和停止测试全部通过。

## 5. M3：保持有效玻璃帧，并随位置刷新请求（F4、F5）

主要文件：`src/UI/LiveGlassController.cs`、`src/UI/MainForm_Transparent.cs`，必要时整合 `src/UI/UIController.cs` 的通知入口；相关测试放入现有外观测试工程。后端仅在请求或测试接缝确有需要时修改。

帧租约修改：

1. 绘制开始时先尝试获取替代帧。没有新帧时保留仍有效、属于当前请求代次的旧租约。
2. 得到新租约后再交换并释放旧租约；确认旧租约释放不会清除服务中的新租约。
3. 暂停、停止或请求失效时释放旧租约并使用既有回退，不能把过期内容当成当前有效帧。同步更新相关注释，明确租约跨多次绘制持有。

位置请求修改：

1. 将窗口 `LocationChanged` 或 `Move` 接入同一个几何变化入口，覆盖用户拖动与程序设置位置。
2. 位置改变也推进请求代次，并刷新物理客户区屏幕矩形。复用现有内部代次机制；如名称不再准确，可在内部改为几何代次，不为此扩展公开接口。
3. 在 UI 线程读取窗口几何，把不可变请求交给后端。移动通知不得重新启动整个捕获服务，也不得绕过既有帧率限制。
4. 移动前已在途的帧不得在移动后重新成为有效内容；新位置有效帧到来前使用既有回退。尺寸不变不能成为跳过几何刷新的理由。

验收：

- 一帧、多次绘制：所有绘制都能使用同一有效帧。
- 新帧替换：旧帧只释放一次，新帧继续可用；停止后没有遗留租约。
- 请求失效与暂停：旧帧不继续暴露，回退行为正确。
- 在 STA 窗口测试或现有可控窗口接缝中，仅改变位置：后端请求矩形和代次均更新；不调用真实桌面抓取。
- 移动前在途帧被拒绝，移动后新代次帧可用；连续移动仍保持现有捕获节流。
- 实施后再做桌面验收：同屏拖动、程序吸附/定位和跨屏 DPI；该验收不能用合成帧测试替代，也不能提前记录为通过。

## 6. M4：卸载路径边界和自启归属（F2、F6）

### 6.1 插件卸载（F2）

主要文件：`src/Plugins/PluginMarket.cs`、`tests/LiteMonitor.Tests/PluginMarketTests.cs`；仅在共享校验确有需要时提取内部校验器。

1. 提取无文件副作用的 ID 校验逻辑，安装和卸载复用；内置插件保护仍单独执行，不能因此放宽安装条件。
2. 卸载时分别校验条目 ID、持久化记录 ID 及其一致性，随后校验文件名与记录的一致性。
3. 规范化候选目标路径，并以 Windows 的大小写规则和目录分隔符边界确认它是 `PluginsDir` 的直接子文件；仅做字符串前缀比较不算归属校验。
4. 记录不合法时返回现有错误模型能表达的失败，不删除文件、不先删记录。正常安装、更新、卸载的用户流程保持一致。

验收：正常插件可卸载；内置插件仍受保护；不合法 ID、记录与条目不一致、目录外目标均被拒绝且无文件副作用。目录边界检查覆盖同前缀的相邻目录。所有文件测试限定在测试临时目录。

### 6.2 自启迁移（F6）

主要文件：`src/System/AutoStart.cs` 及对应测试；为计划任务进程调用使用可替换适配器，测试仅返回固定 XML 和退出码。

1. 先创建新品牌任务，检查进程退出码，再查询确认任务启用且启动路径属于当前安装；只有这一步成功，才考虑清理旧任务。
2. 查询旧任务 XML，读取实际启动操作。只有能确认属于当前安装迁移的目标才允许清理，例如同一安装目录中的已知旧主程序名。
3. 不同目录、无法解析、多个或无法确认的启动操作均保留。路径规范化规则明确处理引号、大小写及环境变量；不执行 XML 中的命令来判断归属。
4. 删除失败只报告迁移清理未完成，不能影响已确认的新任务；创建或核验失败时保留旧任务并向用户返回失败。

验收：独立目录原版任务完整保留；已确认的同安装旧任务在新任务成功后才清理；创建失败、查询失败、归属不明和清理失败都按上述规则返回。单元测试不调用真实 `schtasks`。
