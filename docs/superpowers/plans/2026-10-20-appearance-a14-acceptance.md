## 1. 验收范围与口径

### 1.1 v4 §7.4 的预算（本轮唯一判据）

| 场景 | 预算 |
|---|---|
| 新效果关闭 | 新模块不创建位图/计时器/捕获；热路径不增加托管分配；每帧额外 CPU ≤ `max(基线×5%, 0.1ms)` |
| 静态机能效果 | 普通档额外 CPU ≤ 1ms/帧；**4卡 + 两倍物理尺寸档 ≤ 2ms/帧**；不新增动画计时器；以实际最低 80ms（12.5Hz）报告投影 |

### 1.2 为什么必须做"配对测量"而不是直接比绝对值

A04 基线给出的**绝对值**（例如 4 卡两倍档旧入口 ≈ 69.53 ms/帧）在不同时间跑出来差异极大：

| 运行 | 夹具 | 旧入口中位数 |
|---|---|---|
| A04 基线（`appearance-baseline`） | `DarkFlat_Classic__vertical__gpu4__dpi96__scale2.0` | 67.19 ms |
| L-02 后重采（`appearance-baseline-l02`） | 同上 | 69.53 ms |
| A14 配对测量（帧级交替） | 同上 | **87.58 ms** |

同一台机器、同一份代码，绝对值却差了 **30%**。原因（据实说明，不掩饰）：

1. **帧级交替本身有代价**：配对测量里每一帧都要把两条路径各画一遍，画布内容交替变化，
   GDI+ 的部分路径比"连续画同一张图"更慢；
2. **机器当时的系统负载 / CPU 频率**与采基线时不同；
3. **20 帧的测量窗口**会系统性低报 4%–38%（A04 已记录）。

⇒ **绝对值不可跨批次比较**。因此本轮所有判定都基于**同一进程、同一时刻、同一画布**下
old 与 new 的**配对差值**，绝对值只作为"基线大小"的上下文出现。

### 1.3 配对测量的方法（`tests/LiteMonitor.PerformanceProbe` 新增 `--appearance-paired`）

| 设计点 | 做法 | 为什么 |
|---|---|---|
| 同一张图 | 固定帧号（`ApplyFrame(ctx, data, 1)`），两条路径画**完全相同**的画面 | 否则差值混入了"内容不同导致的绘制量差异" |
| 帧级交替 | 每一帧先测一条路径、紧接着测另一条 | 系统负载 / CPU 频率漂移在**每一对**里被抵消，而不是只靠轮次平均 |
| 顺序翻转 | 第 1 轮 `legacy→wired`，第 2 轮 `wired→legacy`，逐轮交替 | 消除"谁先画谁受益于画布/GDI+ 缓存"的系统性偏差 |
| 主判据 | **逐帧配对差值的中位数** | 抗单帧抖动（实测逐帧差值的 P10–P90 可达 ±10ms，中位数被压到 ±0.7ms 内） |
| 辅判据 | 逐帧差值的 P10 / P90 / 均值 | 暴露噪声幅度，避免只报一个好看的数字 |
| 托管分配 | 单独一轮测量（不夹在计时里），`GC.GetAllocatedBytesForCurrentThread` | v4 §7.4 的**硬判据**，且不受计时噪声影响 |
| 轮数 / 帧数 | 4 轮 × 60 帧 × 2 路径 = 每夹具 480 次绘制 | v4 §7.4 要求"同机至少三轮配对" |

⚠️ **不使用进程 CPU 时间做主判据**：Windows 的进程 CPU 时间粒度约 15.6ms，
用它去判"0.1ms 级"的差异没有意义。离屏渲染是 CPU-bound 的（无 IO、无等待），
因此用每帧墙钟是可靠的近似；进程 CPU 时间在 JSON 里另有记录作佐证。

⚠️ **遗留偏差（据实声明）**：先画的那条路径略占便宜（画布内容对它是"新"的）。
顺序按轮翻转只能抵消**平均**偏差，不能完全消除，故配对差值应理解为**略微偏保守**（新路径略被高估）。

## 2. 本轮发现并修复的问题

### 2.1 热路径的托管分配回归（v4 §7.4 硬判据）

**现象**：A13 接线后，`UIRenderer.Render` 里每一帧都要执行
`BuildGroupRegions(groups, t)` —— 它 `new List<DecorGroupRegion>(count)`，
连带它的内部数组，**每帧 2 次托管分配**。

即使旧主题一个装饰都不开，这两次分配也照样发生 ⇒ 违反
v4 §7.4「新效果关闭 → **热路径不增加托管分配**」。

**修复**（两处）：

1. `UIRenderer.Render` 新重载：窗口底纹**只在底纹真的开启时**才构建组区域列表
   （`options.ScanlineEnabled || options.GridEnabled`）—— 旧主题下连列表都不建；
2. `AppearanceRuntime.RentGroupRegions`：改用**一个复用的 List** 承载组区域
   （`Clear()` 不释放容量），布局稳定后每帧 0 次分配。

**验证**：见 §3.2 的"额外托管分配"列 —— 旧主题全部为 **0 字节/帧**。

### 2.2 探针自身的顺序 bug（不是产品缺陷，但差点污染结论）

新增的配对测量最初放在 `AppearanceProbeRunner.RenderFixture` 的
`ctx.Theme.DisposeFonts()` **之后**，导致主题字体已被释放，
后续绘制访问 `Font.Height` 抛 `ArgumentException: Parameter is not valid.`
（堆栈：`System.Drawing.Font.GetHeight` → `UIRenderer.DrawMainTitle`）。

⇒ **27 个竖屏夹具全部失败**，而横屏因为不读 `Font.Height` 而"看起来正常"。
这是**探针代码**的缺陷，**生产代码无此问题**（生产里 `Theme.Scale` 内的
`DisposeFonts()` 与字体重建是配对的）。已把配对测量移到 `DisposeFonts()` 之前。

⚠️ 记录这一点是因为它演示了一个真实陷阱：**"横屏通过、竖屏失败"这种不对称现象，
往往不是业务逻辑差异，而是探针自身的时序问题**。

### 2.3 客户区最外一圈"漏色"：抗锯齿 + 精确客户区填充（独立验收 R5 的真正根因）

**起因**：本轮要验证一项优化 —— 渐变两端色都完全不透明时，渐变必然盖满整块客户区，
那张**不透明底板**就是一次纯浪费的全屏填充（4 卡两倍档实测约 2.2 ms/帧），
于是加了一个 `NeedsBasePlate(mode, options)` 判定：渐变两端 alpha 都 = 255 时跳过底板。

**验证结果**：它**不是**像素零变化。`AppearanceWiringProbe` 的
「机能主题竖屏装饰生效」4 个用例（dpi96/120/144/192）的 `wiredPixelSha256` 全部改变。

**定位过程**（新增的 PNG 导出 + alpha 覆盖度诊断字段）：

1. 差异像素 = **1061**，逐行/逐列分布显示：`row 0` 整行 240 个 + `col 0` 整列 822 个，
   减去重复的 `(0,0)` ⇒ 恰好 1061；其余只是零星散点。
2. 画布上 **alpha < 255 的像素数也恰好是 1061** ⇒ **差异的全部来源就是这些半透明像素**，
   其余 196219 个像素完全一致。
3. 客户区矩形实测为 `0,0,240,822`（与画布同尺寸），渐变两端 alpha 均为 255
   ⇒ 渐变**本应**盖满整个客户区。
4. 复现实验定位根因：绘制层为文字与圆角开了 `SmoothingMode.AntiAlias`，
   而 `PixelOffsetMode` 保持默认 —— 对位图而言默认等价 `Half`（坐标偏移半像素）。
   于是抗锯齿的填充**只覆盖目标矩形边界像素的约一半**：

   | 条件 | `row 0` 的 alpha（min/max/不满 255 个数） |
   |---|---|
   | `AntiAlias` + `PixelOffsetMode.Default`（真实路径） | **64 / 128 / 240** |
   | `AntiAlias` + `PixelOffsetMode.HighQuality` | 255 / 255 / 0 |
   | `None` + `None` | 255 / 255 / 0 |
   | 真实探针实测 | **72 / 139 / 240** |

   ⇒ 严格按 `options.ClientBounds` 填充，**客户区最外一圈必然留下半透明像素**。

5. **为什么旧路径没这个问题**：旧的实心底板一直用 `(-5,-5, w+10, h+10)` 的**溢出**矩形，
   代码注释写得很直白 ——「从 (-5,-5) 开始画，确保绝对覆盖掉 (0,0) 处的物理像素死角」。
   **A13 引入的新背景层改用精确的 `options.ClientBounds`，把这个保护丢了。**
   这正是独立验收 R5「底板锚定完整客户区」要解决的那一类问题，
   而 R5 给出的实测反例（局部失效区内点 `(40,45)` 仍是预填的洋红色）是它的**另一个表现**。

**修复**（4 处）：

1. `ThemeAppearanceOptions.GetEdgeCoveredBounds(clientBounds, padding = 2)` ——
   客户区四边各外扩 2px，**让抗锯齿的过渡带落在客户区之外**；
   外扩出来的像素会被 Graphics 的裁剪自动丢弃，不会画到窗口外。
2. 背景层的**底板 / 渐变 / 染色 / 噪点**改用该外扩矩形；
   **边缘辉光保持精确客户区**（它本就该画在边缘，语义不同）。
3. 渐变的**轴仍按精确客户区计算**（两端色的落点不变），只把**填充范围**外扩
   ⇒ 客户区内的渐变分布完全不变，只有边缘从"半透明带"变成"完整不透明"。
4. **新入口**的 solid 底板锚定 `options.ClientBounds`（R5 的正题）：
   旧实现用 `g.VisibleClipBounds` —— 局部失效时它就是那块裁剪区，
   底板会从窗口原点偏移着画，**失效区里补不上底色**；改锚定后由 Graphics 裁剪限制写入范围，
   失效区能被正确补色。
   **旧入口保持原样**：它拿不到完整客户区（没有外观快照），
   改动会破坏「旧主题新旧入口逐像素一致」这条基线，也会破坏 A04 的 368 夹具旧入口基线。

⚠️ **横屏为什么例外**：横屏旧入口的底板是 `(0,0,panelWidth,panelHeight)`，**没有溢出**，
它的边缘本来就带着同一条抗锯齿半透明带。所以横屏新入口锚定 `options.ClientBounds` 后
**不能再外扩** —— 否则两者的边缘带不同，「旧主题横屏像素一致」会失败。
竖屏旧入口本来就是溢出填充，新入口外扩 2px 才能与之等价。

### 2.4 `NeedsBasePlate` 优化的结论

**原前提**：渐变两端 alpha 都 = 255 ⇒ 渐变必然盖满 ⇒ 底板是纯浪费。

**这个前提在抗锯齿下不成立**：渐变（斜向 `LinearGradientBrush`）的边缘只被覆盖约一半，
所以"盖满"并不成立 ⇒ 跳过底板会让客户区最外一圈的底层从
「底板的部分覆盖」变成「渐变的部分覆盖」⇒ **像素变化**（§2.3 的 1061 个像素）。

**修复 §2.3 之后**：底板与渐变使用**同一个外扩矩形** ⇒ 渐变完全覆盖客户区 ⇒
跳过底板后画面**完全不变** ⇒ 该优化成立，且在渐变两端不透明时省下一次全屏不透明填充。

**验证工具的补强**（本轮新增，属于探针能力而非产品改动）：

- `AppearanceWiringProbe` 增加 **PNG 导出**（`wiredPng` 字段）——
  哈希只能回答"变没变"，PNG 才能回答"**变在哪**"；
- 增加 `clientBounds` / 渐变两端色与 alpha / **半透明像素数** / `row 0` 与 `col 0` 的 alpha 统计
  —— 直接把"背景层有没有真的铺满客户区"变成可测量证据；
- ⚠️ 注意：导出的 PNG 由 32bppPArgb 克隆而来，**alpha 仍是预乘值**，
  读 PNG 的 alpha 只能用于**位置**判断，颜色数值要回看原始字节。

### 3.2 静态机能效果（CyberPunk_Mech）—— ❌ **超预算**

v4 §7.4 判据：普通档 ≤ 1ms/帧；**4 卡 + 两倍物理尺寸档 ≤ 2ms/帧**。

## 6. 超预算的处置

### 6.1 结构性结论（不是某个实现 bug）

把 §4.2 的分解按面积归一化后，额外**经过时间**的构成非常清楚：

| 层 | 普通档 (192,480 px) | 4 卡两倍档 (1,276,800 px) | 面积比 6.6× | 随面积线性？ |
|---|---|---|---|---|
| 渐变背景 | +0.98 | +4.42 | 4.5× | ✅ 线性 |
| 扫描线 | +0.99 | （见 §4.2 表） | — | ✅ 线性 |
| 网格 | ≈ 0 | ≈ 0 | — | 与扫描线共用一次填充 |
| 外框 + 辉光 | +0.62 | +0.6 | ≈ 1× | ❌ 与面积无关（只有边框一圈） |
| 渐变进度条 | ≈ 0 | ≈ 0 | — | 条面积很小 |

⇒ 额外成本 ≈ **「大面积 alpha 混合填充」× 2 层**（渐变 + 扫描线）**+ 一圈路径抗锯齿描边**。

这是 GDI+ 在 32bpp ARGB 上的固有成本量级：
单层全屏 alpha 混合 ≈ **5 ns/px**（192,480 px → 0.98ms）。

### 6.2 v4 的 2ms 预算在当前视觉方案下**不可达**

4 卡两倍档要落在 2ms 内，等价于"在全屏 1,276,800 px 上最多做 **0.4 层**全屏 alpha 混合"。
而当前方案最少需要 **2 层**（渐变 + 扫描线）才能呈现用户要的效果。

⇒ **不是实现 bug，是预算与视觉方案之间的结构性矛盾。**

### 6.3 可做的"视觉零变化"优化（**已执行**）

| 优化 | 预期收益 | 实测收益 | 状态 |
|---|---|---|---|
| **渐变模式跳过不透明底板** —— `DrawBasePlate` 先铺一层不透明底板，紧接着 `DrawGradient` 用**完全不透明**的渐变把它盖住 ⇒ 底板是纯浪费的一次全屏填充。渐变带 alpha 时才需要底板（玻璃帧要叠在底板上）。 | 4 卡两倍档 ≈ −2.2ms（普通档 ≈ −0.5ms） | **4 卡两倍档 −1.32ms**（+11.77 → +10.45）；960×3208 档 **−7.25ms**（+25.30 → +18.05） | ✅ **已执行**，且经开关对照验证为**像素零变化**（§2.4、§3.4） |
| 扫描线与网格共用一次填充 | 已实现（A05 的现状），无进一步收益 | — | ✅ 现状 |
| 外框 / 辉光路径抗锯齿 | 4 卡两倍档 ≈ −0.6ms | 未做 | ❌ **不做**：关掉抗锯齿会改变边缘观感，不属于"零变化" |

⚠️ 注意第一项**曾经被判定为"零变化"却并不成立**：抗锯齿下渐变的边缘只被覆盖约一半，
跳过底板会让客户区最外一圈改变像素。必须先修 §2.3 的边缘漏色，才谈得上"零变化"。

即便全部做完，4 卡两倍档仍在 **≈ 10ms**，是 2ms 预算的 5 倍。

### 6.4 整机影响（给决策用的真实数字）

以**最终复测**的 4 卡两倍档（480×2660）为准：旧入口 72.95 ms/帧 → 新入口 83.86 ms/帧。

> ⚠️ **口径更正（2026-10-20 独立复核 N1）**：下表的 72.95 / 83.86 ms/帧 来自 `Stopwatch`，
> 是**绘制经过时间**，**不是 CPU 时间**。把经过时间直接当成处理器时间来推算整机占用，
> 属于**口径混用**——等待、抢占、GC 停顿都会被算进经过时间，却不会全部计入 CPU 时间。
> 因此下表的"整机 %"是**基于经过时间的假设估算**，**不能当作实测的整机 CPU 占用**。
> 真正的 CPU 口径数据见 §6.7。
>
> 📌 **这条更正已被 §6.7.5 部分收窄（2026-10-21）**：它在**绝对值**上完全成立。
> 在**增量**上，5 轮实测显示 CPU 口径（+8.73 ms/帧）与同批次经过时间（+8.97 ms/帧）
> 只差 **2.7%** —— 因为本项目的额外成本是**纯 CPU 密集的 alpha 混合填充**，没有 IO 等待可占。
> ⇒ 收窄后的准确表述是：**本批次**的 CPU 增量与耗时增量接近，
> 因此 §6.4 基于经过时间给出的**量级估算**得到实测支持；
> 但这**不能推广**为「两种口径始终等价」—— 等待 / 抢占 / GC 停顿的占比一旦变化即不再成立。
> ⇒ **CPU 预算与整机投影一律以 CPU 时间口径的结果为准**（§6.7.5 / §6.7.6）；
> 真正需要用 CPU 口径核对的是**绝对值**（旧入口基线本身也随机器负载漂移）。

| 项 | 4 卡两倍档 @12.5Hz（v4 §7.4 规定的最低刷新率） |
|---|---|
| 旧入口基线 | 72.95 ms/帧（经过时间）→ 假设估算整机 **5.70%** |
| 新入口 | 83.86 ms/帧（经过时间）→ 假设估算整机 **6.55%** |
| **增量** | **+0.85 个百分点**（16 逻辑核；修复前为 +0.92）<br>⚠️ 此为**经过时间假设估算**，非实测 CPU 占用 |

⇒ 对整机负载的**估算**影响是 **约 +0.85 个百分点**（口径见上）。
主程序默认刷新间隔 1000ms（1Hz）时，额外**经过时间**是 **10.45 ms/秒 ≈ 单核 1.06%**（修复前 11.77 ms/秒 ≈ 1.2%）。

**这个结论对用户拍板是否成立**：用户关心的是"会不会让机器变卡"，而不是"CPU 时间的确切数值"。
绘制路径是 CPU 密集型（alpha 混合填充），经过时间与 CPU 时间的差距主要来自等待/抢占，
在 12.5Hz 的低频刷新下等待占比有限 ⇒ **量级结论（额外约 10ms/帧、约 +0.85 个百分点）成立**，
但**精确数值须以 §6.7 的 CPU 口径实测为准**。

> ✅ **实测已补（§6.7.5 / §6.7.6）**：CPU 口径下 4 卡两倍档的增量是 **+8.73 ms/帧**、整机 **+0.68 个百分点 @12.5Hz**，
> 与这里基于经过时间的假设估算 **+0.85 个百分点同量级**。
> ⇒ **本批次**两种口径的增量接近（实测差 2.7~3.9%），说明上面的**量级估算**是站得住的；
> 但这只是**本批次**的实测结果，**不构成**「经过时间可以替代 CPU 时间」这一普遍等价关系。
> **量级结论成立；CPU 预算与整机投影的精确数值一律以 §6.7.5 的 5 轮 CPU 口径实测为准。**

| 做法 | 为什么不做 |
|---|---|
| 底纹低频重铺（跳过某些帧的绘制） | 违反 v4 §3.3「每次 Paint 都绘制有效缓存，不能用跳过绘制来节流」；A07 提过，**已被否决** |
| 上一帧图像回填 / 强 tint 掩盖 | **已被用户否决**，且不能证明得到被遮挡的真实背景 |
| 自绘假亚克力 | **已被用户否决**（唯一路线是屏幕捕获 + `WDA_EXCLUDEFROMCAPTURE`） |
| 把"离屏下界"当实机数字上报 | 离屏渲染**不含** DWM / 窗口呈现 / 桌面合成，实机只会更高、不会更低 |

### 6.7 CPU 口径实测（N1，2026-10-21）

> §6.4 的 72.95 / 83.86 ms/帧 是**经过时间**口径；本节是**CPU 时间（处理器时间）**口径的实测，
> 用来替换 §6.4 里"基于经过时间的假设估算"。两者**不可混用**。

#### 6.7.1 测量方法

| 项 | 值 |
|---|---|
| 工具 | `tests/LiteMonitor.PerformanceProbe` 的 `--appearance-paired-cpu`（CPU 口径配对测量） |
| 口径 | `Process.TotalProcessorTime`（用户态 + 内核态处理器时间），批次前后取差值 ÷ 绘制次数 |
| 配对方式 | 同进程同刻**背靠背**测旧入口与新入口；段内**交替**先后顺序 + 逐轮**翻转**起始顺序（双重抵消顺序偏差） |
| 噪声门槛 | 取**轮间极差**；差值绝对值小于门槛即判"落在测量噪声内 → 不可判定"（**不是 0**） |
| 整机推算 | 12.5 帧/秒 × 每帧 CPU 毫秒 ÷ 1000 ÷ 逻辑核数 × 100 |
| 硬件 | AMD 5800X（16 逻辑核）；Windows 11 26H2 build 26300.9457；非 RDP；非提权会话 |

#### 6.7.2 第一轮：主题 `AuroraDream_Purple`（2 档位，3 轮）

#### 6.7.4 两个口径的关系（同批次内对比）

**关键对比：同一批次内，CPU 口径与经过时间口径的增量高度一致。**

| 档位（5 轮复核批次） | CPU 口径增量 | 同批次**经过时间**增量 | 两者之差 | 噪声门槛 | 判定余量 |
|---|---|---|---|---|---|
| 普通档(1卡@96/1.0) | **+2.0352** ms/帧 | +2.1205 ms/帧 | **3.9%** | 0.6484 | 3.1 倍 |
| 4卡两倍档(4卡@96/2.0) | **+8.7328** ms/帧 | +8.9677 ms/帧 | **2.7%** | 0.3867 | **22.6 倍** |

⇒ **本批次**两个口径的增量高度一致（差 3~4%）：CPU 密集型的 alpha 混合填充几乎没有等待/阻塞成分，
所以经过时间增量 ≈ CPU 时间增量。
⚠️ **此处必须收窄，不得推广**：§6.4 里那条「经过时间不能直接当 CPU 时间」的警告**对绝对值成立**；
在增量上，**本批次**实测接近，因而**支持** §6.4 的**量级估算**成立；
但这只是一批数据的观测结果，**不是**「两种口径始终等价」的一般性结论。
⇒ **CPU 预算与整机投影一律以 CPU 时间口径的结果为准。**

⚠️ **一处必须记下的自我更正**：3 轮那批数据曾给出"增量 +6.9753 ms/帧、整机 +0.54 个百分点"，
一度被解读成"§6.4 的估算偏保守 33%"。5 轮复核推翻了这条推论：
同一档位的**旧入口绝对值**在两批之间从 75.14 漂到 **67.14** ms/帧（机器负载不同），
差异来自**批次间漂移**，不是口径差异。**不能拿不同批次的绝对值去比口径。**
⇒ 以 §6.7.5 的 5 轮数据为准。

#### 6.7.6 结论与对 §6.4 / §6.5 的影响

| 项 | §6.4（经过时间，旧批次） | §6.7.5（CPU 口径，5 轮复核） |
|---|---|---|
| 4 卡两倍档 增量 | +10.45 ms/帧 | **+8.73 ms/帧** |

⇒ **§6.5 的结论完全成立，且现在有 CPU 口径实测支撑**：
- 「记为 M1 已知超预算项、**不写通过**」—— 不变（v4 §7.4 的 2ms/2ms 硬预算仍达不到）；

- **用户最常用的普通档（1 卡 96 DPI）只有 +2.04 ms/帧 CPU、整机 +0.16 个百分点**，
  确实"不会让机器变卡"——这一条现在有 CPU 口径实测数，不再只是"量级推断"。
