## 1. 目标、承诺和范围

### 1.1 最终交付

1. 独立的 GPU 渲染后端：支持多层合成、轮廓遮罩、模糊、折射、光晕、纹理和局部动画。
2. `LiquidGlass_GPU`：接近用户认可的 iOS 26 Liquid Glass 视觉方向，具备真实背景输入、边缘透镜变形、厚度、高光与稳定可读的文字。
3. `CyberPunk_GPU`：具有机械框体层次、局部霓虹、材质细节与数据反馈的完整主题。
4. 旧主题和旧 GDI+ 路径继续可用；新后端关闭或发生可恢复故障后，可以恢复可操作的普通面板。
5. 编辑器、预览、配置、打包、诊断和验收证据同步交付。

**完成标准是两个主题的视觉、功能、性能、资源释放均达标。测试全绿不能替代用户对画面的确认。**

### 1.2 必须沿用的用户决定

- 现有 `CyberPunk_Mech` 的 M1 超预算是已接受事项：保留其原画面，不借本计划修改它，不为它增加自动画质降级。
- 新主题采用新 ID、新配置段；不覆盖 `CyberPunk_Mech.json` 或 `LiquidGlass.json`。
- 保留监控能力、原有操作习惯和旧主题；不作“零回归”的未经验证保证。
- 两个主题共用基础设施，分别设计材质和美术参数；不再依赖一套扫描线、网格、辉光强度拼出所有风格。

### 1.3 V1 边界

| 范围 | V1 要求 |
|---|---|
| 主面板 | 竖屏、横屏、横屏单行；支持已有分组与指标组合 |
| 数据 | 使用原有采样结果；不为动画提高硬件采样频率 |
| 文字 | 中文、英文、长标题、缺失字体、数值宽度变化；前景独立清晰 |
| 交互 | 置顶、穿透、拖动、双击、右键、托盘、隐藏恢复、透明度 |
| 系统 | 旧路径维持现有 Windows 10/11 支持；新路径按能力检测启用，支持表在技术原型阶段冻结 |
| 预览 | 与正式后端共用材质和场景代码；背景使用固定样本，不启动桌面捕获 |
| 失败恢复 | GPU/捕获不可用时保留数据和操作能力，显示准确状态，允许切回旧路径 |
| 任务栏、网页、其他窗口 | 保持现有实现；验证未受影响，不在 V1 扩展 GPU 材质 |

V1 不包含：全应用迁移至 WinUI/WPF、旧主题批量 GPU 化、三维场景、全局物理模拟、强制鼠标跟随、持续全屏故障闪烁、用户可编程着色器、通用节点编辑器。

## 4. 视觉规格

### 4.1 液态玻璃：首版必做

- 参考 iOS 26 的控制层材质：通透、有厚度的圆角轮廓、边缘透镜感，避免把整个面板做成重度磨砂墙。
- 根据形状距离与法线生成折射位移；直边、圆角和不同尺寸应连续，不能只沿边框贴一条发光线。
- 保留未模糊或低模糊的背景采样分支，再按位置控制散射；不能先把唯一背景输入全部糊掉。
- 高光与阴影表达同一套厚度和光照方向；亮边不能成为均匀白描边。
- 文字、数值、告警不参与背景折射，不随高光闪动。
- 在浅色、深色、图片和细文字背景上验证；必要的局部可读性调节应平滑，不能整体忽明忽暗。
- 圆角、厚度、折射幅度、模糊、高光、阴影与背景色响应均可受控调整。
- 避免大幅色散、彩虹边或水波；这些不作为“像苹果”的必要条件。

G2 玻璃样板至少含：一个圆角片、一个完整监控分组、一块有真实数值的面板；支持切换固定背景与通过验证的实时背景。

### 4.2 赛博朋克：首版必做

- 建立完整的机械仪表设计：主框体、分组结构、连接件、灯带、数据区有清晰层级。
- 发光分为亮核心、近光晕和弱环境反射；限制发光面积，避免所有线条和文字同时发亮。
- 机械切角、分段边框、纹理、进度条共同使用一套几何与材质规则。
- 基础方案采用深色工业底板、冷色主灯与少量暖色强调；具体色值和字体在 R01 中输出并由样板确认。
- 保留原指标语义和告警色辨识，不能为风格把正常、警告、危险变得难以区分。
- 动效只集中在局部扫光、能量条和状态变化反馈；不持续抖动文字，不用大面积闪烁制造“炫酷”。
- 允许使用原创或许可清楚的纹理/图标；记录来源、许可证、尺寸和用途，素材不可代替动态材质本身。
- 关闭动效后仍是一套完成度足够的静态主题。

G2 赛博朋克样板至少含：CPU/GPU 数值、双列网络/磁盘、进度条、普通/告警状态、1 卡与 4 卡布局；展示窄面板下的删减规则，不能靠缩小所有文字塞入。

### 4.3 共用视觉验收表

| 项目 | 验收方式 | 不通过的典型表现 |
|---|---|---|
| 风格 | 与 R01 确认的参考和样板同屏比较 | 更换背景色后仍只是旧主题加描边 |
| 信息优先级 | 不依赖暂停动画，能读取 CPU/GPU/NET/DISK 核心数值 | 特效抢过数值、单位不清楚、告警辨识下降 |
| 几何 | 100%/150%/175%/200% DPI、不同尺寸放大检查 | 切角漏底、圆角亮缝、边缘粗细突变 |
| 动态 | 展示真实帧率下的拖动、背景移动和数值变化 | 自反馈、明显拖影、边缘跳动、灯光闪烁 |
| 前景 | 中文、长标题、缺失值、极大数值、字体替代 | 裁字、重叠、模糊、基线不齐 |
| 稳定性 | 重复相同场景与固定随机种子 | 每次截图无法比较，无法定位视觉回归 |

R01 输出：4–6 个基础色 token、字体及许可证/替代字体、字号阶梯、留白、框体与光照规则、动画时长、禁止出现的视觉表现。先做少量有明确方向的方案，不批量生成几十套配色让用户筛选。

用户反馈必须转化为可复现事项，例如“圆角折射过强，背景文字被拉成双影”；不能只记“继续优化”。

## 5. 目标架构与接线边界

```text
原有硬件采样 / 插件 / 历史 / 告警
                 ↓ 不改变采样周期
原有指标与布局 → 只读场景快照
                 ↓
            渲染路由与生命周期
             ├─ Legacy → 现有 GDI+ 原路径
             └─ GPU
                 ├─ 背景输入：固定样本 / 实时桌面（按需）
                 ├─ 轮廓、遮罩、纹理、效果合成
                 ├─ LiquidGlass 材质 / CyberPunk 材质
                 ├─ 清晰前景：文字、数值、图表与状态
                 └─ 经原型验证的窗口呈现后端
```

### 5.1 技术选型

首选原型方向：D3D11/DXGI 纹理与着色器，D2D/DirectWrite 前景，DirectComposition 或 Windows Composition 呈现。最终选择由 R03 的实测决定，不提前将任一组合写成已验证事实。

- 不为此更换应用框架或硬件库。
- .NET 绑定库只选一套，经 R03 记录维护状态、许可证、支持框架、原生依赖、包版本和可复现构建后冻结。
- 着色器随发布包提供预编译产物和来源哈希；用户运行时不依赖本机 shader 编译器或 SDK。
- 首版避免引入仅为材质所需的庞大 UI 框架；若选型要求提升全应用最低系统版本，必须作为范围变化重新评估。
- GPU 不支持、依赖缺失或处于不支持的会话时，旧功能仍能启动，不能在静态初始化阶段崩溃。

### 5.2 推荐新增目录

以下是规划路径；R05 冻结后才能依赖具体公开类型名。

```text
src/Rendering/Contracts/       场景、能力、参数、代次、诊断与生命周期合同
src/Rendering/Scene/           原布局到只读场景的适配
src/Rendering/Gpu/             设备、缓存、效果合成、调度、前景
src/Rendering/Presentation/    呈现、窗口能力与后端切换
src/Rendering/Capture/         新 GPU 背景源、裁切和帧所有权
src/Rendering/Materials/Glass/  玻璃材质
src/Rendering/Materials/Cyber/  赛博朋克材质
resources/shaders/             着色器来源、构建配置与产物清单
resources/materials/           纹理与许可说明
resources/themes/              新增 LiquidGlass_GPU.json / CyberPunk_GPU.json
tools/AppearanceMaterialLab/   独立样板与固定场景运行器
tests/AppearanceGpu*/          后续实现阶段新增的合同、呈现、资源与性能探针
```

不得用自定义插件执行脚本或加载任意 shader 文件绕过发布与配置边界。主题只描述受支持的材质参数和受控素材引用。

当前主工程的默认 C# glob 仅显式排除了 `tests/` 等目录，没有排除 `tools/`。第一个原型源码进入 `tools/` **之前**，由构建 owner 增加对应 `Compile Remove`，或先把独立原型放在已隔离的目录；不能等 R23 才处理，否则原型入口和依赖可能被主工程误编译。样板公共项目/入口也由构建 owner 统一维护，各样板 owner 只写自己的子目录。

### 5.3 场景与线程合同

| 合同 | 要求 |
|---|---|
| 场景输入 | 包含分组、标签、数值、单位、阈值状态、条形比例和布局；不携带 `Control`、可变 `Theme`、GDI 画刷或硬件对象。正常状态及“配置禁写/空态/故障”等现有提示也必须适配，不能只画指标 |
| 坐标 | 以 96 DPI 逻辑单位描述布局，提交时单次映射为物理像素；如从已有缩放布局导入，必须显式反归一化，不能再乘一次 DPI |
| 所有权 | UI 构建不可变快照或有明确租约的缓冲；消费者不能读取正被修改的 `MetricItem` 集合 |
| 设备访问 | 每设备一个明确的渲染 owner；即时上下文及资源销毁串行，不能把同一上下文交给两个主题线程 |
| 跨线程提交 | 场景和背景各保留最新待处理项，有界队列；落后时丢旧帧，不堆积延迟 |
| 代次 | 主题、句柄、尺寸/DPI、显示拓扑、设备分别有代次；过期帧和设备资源不得发布到新会话 |
| 容量 | 场景快照有界；捕获帧池建议 2–3 帧，具体以 API 要求为准并冻结；无无界历史纹理队列 |
| GPU 帧 | 声明纹理设备/适配器、像素格式、颜色空间、时间戳、覆盖矩形、租约与释放条件 |
| 停止 | 发起停止、完成停止、资源已释放分别可观察；前一会话未退出时不得启动第二个会话 |
| UI 调用 | 不在 UI 线程等待捕获、GPU fence 或同步回读；不允许“UI 等后台，后台同步 Invoke UI” |
| 热路径 | GPU 结果正常显示不回读到 Bitmap；截图导出作为显式冷路径；文字只在内容或布局变化时更新缓存 |

新路径可使用原布局的输出，但不能为抽象场景而全量重写旧 GDI+ 绘制顺序。旧主题仍直接使用原路径。

### 5.4 分层与几何

建议效果顺序：背景输入 → 材质采样/折射 → 散射与着色 → 结构/纹理 → 局部光晕 → 清晰前景 → 非阻挡状态提示。

- 模糊光晕可降分辨率；折射必须保留足够清晰的采样分支。
- 对透明内容的文字抗锯齿方式单独验证，避免 ClearType 彩边；新主题文字可采用合适的灰度抗锯齿，旧路径保持原输出。
- 统一轮廓同时驱动遮罩、边框、阴影边界和命中区域；不得各写一套略有差异的圆角/切角。
- 外发光若超出客户区，R03 必须证明可呈现且不破坏穿透/拖动；否则首版采用已确认的内向光晕，不擅自扩大窗口遮挡区域。
- 屏幕背景裁切预留折射/模糊采样边距；屏幕边缘有明确填充规则，不拉伸最后一列像素制造亮条。
- 采用一致的预乘 alpha 和颜色处理；避免直接在不匹配的空间做混合，HDR 情况单独验证。
- 文字不得作为发光材质的一部分反复模糊；指标语义、排序和分组标题继续复用现有来源。

## 6. 必须先完成的两项技术原型

### 6.1 R03：呈现与窗口行为

独立原型要模拟实际主窗体：无边框、置顶、`Opacity`、穿透、不同轮廓、多屏 DPI、隐藏恢复、句柄重建和托盘返回。

至少比较：

1. 当前 HWND 绑定合成内容的方案。
2. 仅新后端使用专用呈现宿主的方案；如使用附属窗口，验证 Z 序、焦点、移动同步、捕获排除和关闭关系。

注意：官方 API 支持某种窗口样式，不代表与当前 WinForms 的淡入、透明度、GDI 前景叠加都兼容。必须证明最终前景不会被不透明面板背景盖住。

输出 `rendering-decision.md`：选中路线、淘汰路线、演示命令、支持表、依赖、故障返回过程和截图/录像。

若新路线要求全局修改所有主题的 HWND 样式、取消原透明度或改变输入行为：停止生产接线，先提交具体影响与替代方案，不能以“新后端需要”为由直接全局改造。

### 6.2 R04：背景获取与自反馈

按受支持公开 API 比较 Windows.Graphics.Capture 与 Desktop Duplication；可以评估系统背景材质，但不能假定它能提供任意着色器可采样的清晰桌面纹理。

每条路线回答：

- 取得的是当前屏幕合成结果，还是排除本应用后的真实底图？本应用后面的移动窗口是否正确出现？
- 排除自己后是露出真实内容、黑块、空洞还是旧帧？不同捕获方式表现是否一致？
- 是否需要系统选择器、边框、权限或持续排除本窗口？如需要，按实际行为说明，不静默绕过。
- 与截图/录屏软件同时运行时，面板是否消失、变黑、闪动？
- 多屏、负坐标、混合 DPI、旋转、不同适配器、显示器拔插后是否正确？
- HDR/SDR、锁屏、UAC 安全桌面、远程会话、受保护内容、捕获权限拒绝如何处理？
- 全屏捕获、局部裁切、跨适配器拷贝和同步各花费多少？局部裁切不能被误报成后端只捕获了局部。

异步捕获必须核对实际帧时间：在设置 affinity 前收到的帧，不能因之后设置成功就被标为“已排除自身”。记录排除生效与帧来源关系，检查不同后端是否能提供可靠同步条件。

**禁止以先验假设通过的事项：**

- `WDA_EXCLUDEFROMCAPTURE` 并非只对本应用的捕获器生效；它会影响其他受支持捕获途径。旧 A06 的瞬时排除结论不能外推到所有新后端。
- 不默认持续排除自身，也不默认每帧切换 affinity 可接受；必须交付本地显示与外部录屏的并列证据。
- 不通过短暂隐藏真实窗口来假装“无反馈”；如研究中使用，必须标为实验，不得作为默认交付。
- 不把单窗口捕获称作“任意桌面背景”；不以固定壁纸冒充实时背景。

记录并恢复本模块实际修改的原 affinity，退出、异常和取消路径一致。双窗口方案要逐个记录 HWND，而非只处理控制窗体。

若只有会明显影响截图/录屏的路线可用，提交具体演示与取舍，由用户选择是否接受；这时不能宣称达成“不影响原有行为”。拒绝该取舍时，玻璃保留研究状态，赛博朋克继续。

## 7. 调度、资源与故障恢复

### 7.1 三种更新分开

- 数据更新：沿用现有采样频率。
- 背景更新：仅玻璃按需获取；赛博朋克为零，除非将来另加显式玻璃变体。
- 视觉更新：默认目标 30 FPS；60 FPS 作为通过性能验收后的显式选项，不是完成 V1 的前提。

静态内容无变化时复用缓存；动画使用单调时钟，不依赖硬件采样 Tick。运行时只维护一个活动 GPU 调度器，不因换主题重复创建定时器。

现有 `UIController.Tick` 不是新材质的动画时钟，且拖动期间存在跳过逻辑。新路径把显示器背景纹理与当前窗口的采样变换分开：持续拖动只更新位置/采样区域，不因每个位置事件销毁整套捕获会话、清掉全部当前帧。必须在实际拖动事件循环中验证，并在真正尺寸/DPI/拓扑变化时拒绝不兼容资源。

后台 API 即使持续产生帧，也应有明确消费上限和停止策略，不能只限制渲染却继续全速捕获。

### 7.2 资源规则

- 设备、交换链、捕获会话、帧租约、纹理、字形/文字缓存有唯一 owner。
- 缓存按尺寸、代次和字节量约束；不得只按条目数限制巨型纹理。
- 资源析构与正在提交的 GPU 工作协调；不能用 `Dispose` 后继续采样的纹理掩盖停机竞态。
- 主面板使用旧主题或关闭新后端时，**新增 GPU 模块**不创建设备、不启动捕获、不保留专用动画循环。旧 M2 仍按原主题与 `LiveGlassEnabled` 运行；不得为满足本条而关闭旧功能。用户显式打开 GPU 预览时，其独立资源另计并在预览关闭后释放。
- 切回旧主题或关闭 GPU 后，在可观察的停止完成点释放新后端专用资源。
- 预览设备和正式窗口设备不共享无合同的可变资源；共享只读 shader/素材可以，帧租约不可混用。

### 7.3 状态机

```text
Disabled → Probing → Initializing → Running
                                 ↔ Suspended
                     ↓ 失败或设备丢失
                  Recovering → Running
                     ↓ 恢复失败
                  Fallback
任意活动状态 → Stopping → Disabled
```

- 故障恢复和用户主动关闭均要停止捕获、归还租约、撤销窗口状态、恢复可操作前景。
- 设备恢复单次上限建议 2 秒，每次故障最多 1 次自动重建；连续失败进入可解释回退，用户可显式重试。R05 按 API 取消能力冻结超时实现。
- 不能安全结束的后台任务不得被遗忘并启动第二个；维持故障状态，保留旧面板操作入口。
- 用户启用意图与 HWND 暂时销毁分开保存；句柄重建只暂停/重建宿主，不把用户开关永久改为 false。测试必须包含“开启 → 销毁句柄 → 重建 → 恢复出帧”，不能只验证停止。旧代码链路的相同风险记录为基线问题，是否修复另由 owner 明确界定，不能混入新功能后消失在报告里。
- 原生 GPU 驱动故障可能终止进程，`catch` 不能保证拦住访问违例。需要“GPU 初始化中”启动标记、成功后清除、异常退出后的安全启动入口与禁用 GPU 参数，避免崩溃启动循环。
- 安全启动不能静默覆盖用户配置；显示上次 GPU 会话未正常结束，允许恢复普通模式后再选择是否重试。
- 异常会话标记不能依赖程序目录可写：R05/R19 选择按安装目录身份隔离的用户可写状态位置，避免不同副本相互误判。若无法可靠写入启动保护标记，本次不开启 GPU，返回普通面板并说明原因；不能因配置只读而失去崩溃循环保护。
- 旧 M2 与新 GPU 背景源互斥，任一时刻只允许实际选中的捕获路径运行。

诊断区分：请求后端、实际后端、请求主题、实际材质、捕获是否启用、最后有效帧年龄、故障原因、GPU adapter、恢复次数。不能把渐变回退显示为“实时玻璃已生效”。

## 8. 主题格式、设置与编辑器

### 8.1 增量格式

建议新增可空根对象 `rendering`，新主题使用 `version: 5`；具体字段和版本策略在 R05 冻结。

```json
{
  "version": 5,
  "name": "LiquidGlass_GPU",
  "rendering": {
    "backend": "gpu",
    "material": "liquidGlass",
    "parameters": {},
    "motion": {},
    "fallback": {}
  }
}
```

该示例只说明结构，不是可直接加载的完整主题。所有受支持的参数须在 R05 写出单位、默认值、范围、所属坐标空间、是否可动画、缓存失效条件。

要求：

1. 没有 `rendering` 的主题仍走原 GDI+，不因存在 `border`、`shadow` 等旧字段被自动升级。
2. 新后端需要显式开启；选择新主题时可提供一次明确的启用操作，取消则显示该主题定义的静态回退。
3. 玻璃捕获需要独立明确的开启与实际行为说明；不能沿用旧 `LiveGlassEnabled=true` 推定用户同意新的捕获方式。
4. 旧 `LiveGlassEnabled`、旧 FPS 上限、旧 `Opacity` 含义不变；新参数不能复用相同名字却改变语义。
5. `Form.Opacity` 所代表的整体透明度与玻璃材质透射率分别处理，不能相乘两次或为材质擅自把整体透明度改为 1。
6. 未识别字段在根对象及嵌套层保留；大小写冲突清理、深拷贝、保存、撤销和取消均覆盖新对象。
7. 未知材质、未知后端、坏数值、NaN、非法路径有确定回退和原因；不得执行任意表达式或外部代码。
8. 新主题内置普通背景/颜色作为回退，保存时不把回退状态写回主题参数。
9. 新主题被旧二进制读取时，应至少显示可读的传统布局与颜色；若旧版不保留新字段，必须在兼容说明中限定“编辑后回存”的支持，不能宣称无限向后兼容。

主题选择的稳定标识沿用 `Settings.Skin` 对应的文件标识，不能用 `Theme.Name` 显示名替代；存在两者不相同的旧主题。不得仅凭 `version >= 5` 或文件名含 `GPU` 就启用后端，实际路由由可选配置段及用户开关决定。

`Settings.DeepClone()`、`SettingsChanger.Merge()` 必须检查：若新增嵌套设置，需深拷贝，运行时设备状态不入持久化配置。现有 Settings 不能像主题模型一样保证保留所有未知设置，降级旧版后保存可能丢新字段；回退需保留新版配置副本，不承诺跨版本无损往返。

应用新主题失败时的事务行为在 R17/R19 固定：选择意图可保留并显示明确回退，但不得先保存一个会导致反复崩溃的启动配置，再失去返回普通面板的入口。写入继续走现有安全写入与只读保护，不新增直接覆盖设置文件的路径。

### 8.2 编辑器与预览

- 编辑器暴露少量有意义的材质参数；区分普通设置与高级调节，不建设通用 shader 编辑器。
- 快照、恢复、另存为、未知字段、取消不保存、只读配置保护都有覆盖。
- 逐项检查 `AppearanceThemeConfig.CloneConfig/RestoreConfig`、`ThemePreviewControl.CreatePreviewTheme`、冲突清理与 `ThemeFileService.SaveTheme`；它们不是新增一个属性后自然全部生效的入口。新对象必须同步复制，保存继续走安全写入。
- GPU 预览使用固定背景、固定时间、固定数值、固定随机种子；不创建桌面捕获源，不申请录屏权限。
- 使用与正式面板相同的场景、材质、shader 和颜色处理；只替换宿主与输入。
- 若嵌入式 GPU 预览在 R03 中不可行，V1 使用独立预览窗口；必须明确呈现并关闭旧的假实时预览，不用 GDI+ 模拟一份相似图。
- 无 GPU 时提供明确标记的静态回退预览，不能把它当作新主题真实效果。

## 9. 性能预算与测量口径

以下为本计划建议的 V1 工程门槛，不是已达成的数据。R00 锁定参考机器，R03/R04 实测后在 G1 冻结；Agent 不得自行放宽门槛。若无法满足，先提出有证据的取舍。

### 9.1 场景与档位

| 档位 | 必测配置 |
|---|---|
| S0 关闭态 | 旧经典主题、旧 CyberPunk_Mech；新 GPU 关闭 |
| S1 普通 | 1 GPU，主面板默认尺寸/缩放，分别测试横竖 |
| S2 大档 | 4 GPU、用户 2× 缩放；记录实际物理宽高、DPI和面积 |
| S3 动态 | 相同面板，背后可重复移动文字/棋盘/视频，拖动跨屏 |
| S4 资源 | 30 分钟运行、100 次换肤、100 次显隐、30 次横竖切换、20 次 DPI 往返 |

参考平台至少一个核显/低功耗环境和一个独显环境；无法取得的环境标为未验证，不算通过。S2 超出 API 单纹理尺寸或已冻结面积上限时，显示清楚的限制与回退，不擅自缩小用户面板。

### 9.2 建议门槛

| 指标 | S0 旧路径 | S1 新主题 | S2 新主题 |
|---|---|---|---|
| GPU 新模块初始化/捕获/动画调度 | 均为 0 | 按所需能力开启 | 按所需能力开启 |
| 新增托管分配 | 稳态额外 0 字节/旧绘制帧 | 无按帧持续扩大的分配/缓存；记录 B/s 与 GC | 同左 |
| 进程 CPU 增量 | 普通 ≤5 ms CPU/秒；大档 ≤10 ms CPU/秒，差异必须可测 | ≤40 ms CPU/秒 | ≤80 ms CPU/秒 |
| GPU 材质+前景工作 p95 | 不适用 | ≤4 ms/帧 | ≤8 ms/帧 |
| 实际呈现节奏 | 不改变旧节奏 | 目标 30 FPS；连续动画时 p95 帧间隔 ≤40 ms | 目标 30 FPS；p95 ≤40 ms |
| 玻璃背景年龄 p95 | 旧 M2 合同不变 | ≤100 ms | ≤100 ms |
| 本模块 GPU 常驻资源 | 0 | ≤128 MiB | ≤256 MiB |
| 私有内存增量 | ≤8 MiB，且无持续增长 | ≤64 MiB | ≤128 MiB |

说明：

- 新主题 CPU 增量指同一业务配置下，相对关闭新 GPU 的普通面板之差，包含提交、捕获调度、拷贝和前景更新，不只测 shader。
- 赛博朋克捕获调用数必须为 0；不需要用玻璃的预算为它启用桌面捕获。
- 不用单独一个“GPU 占用率”判定性能：记录进程 GPU 引擎时间、GPU pass 时间、适配器、拷贝量和整机/DWM变化；测量不可用时标注不可判定。
- S0 若差异落入噪声内，不能宣称已证明无额外成本；延长或补测，保留原始数据。旧 CyberPunk_Mech 的已知成本计入其自身基线，不要求消除。
- G1 冻结预算时须附背景源 CPU/GPU/带宽成本，尤其核显和跨适配器路径；不能仅因材质 pass 达标就通过。

### 9.3 测量协议

1. 固定提交、Release 构建、运行参数、主题哈希、显示拓扑、DPI、面板像素尺寸、GPU 驱动和电源模式。
2. 同一业务负载做至少 5 对 A/B 交错测量，预热各 30 秒，采样各 120 秒；写明 A/B 顺序，不把不同批次绝对值直接相减。
3. CPU 使用进程 CPU 时间增量；经过时间另列。整机百分点仅按 `CPU ms/s ÷ (10 × 逻辑处理器数)` 换算并标为推算，不冒充直接整机实测。
4. shader 用 GPU 时间戳/支持的工具测量；检测 disjoint/无效样本。呈现节奏另用呈现事件或可信工具，不用 `Draw()` 返回时间冒充显示完成。
5. 帧年龄以同一单调时钟计算；记录捕获时间戳、提交和使用时间。无可比较时钟时先完成校准。
6. 动态背景和指标使用可重放脚本/种子；真实传感器结果另做完整进程检查，不混用两种口径。
7. 输出每轮原始数据、p50/p95/p99、配对差异、异常样本及原因；剔除规则预先声明，不只保留最优轮次。
8. 每条命令记录实际运行场景；未知主题/参数直接失败，不静默换成默认主题。

### 9.4 资源压力判定

- 先预热，再分别测静止、换肤、显隐和故障恢复；不能只凭最后一张任务管理器截图。
- 所有自有对象计数必须归零：活动捕获、待归还帧、渲染 worker、定时器、设备专属缓存。
- GDI/USER/系统句柄和私有内存与同机基线比较；既有 `AppearanceResourceProbe` 只是一部分，还需 GPU 资源账本。
- 30 分钟稳态私有内存增长斜率建议 ≤1 MiB/分钟，且最后 10 分钟形成平台；句柄/GDI/USER 最后稳定段应无持续正增长，不能只套用历史较宽松阈值掩盖新泄漏。
- 停止完成后，新模块资源账本归零，显存与系统资源回到基线波动范围；驱动缓存不能用来解释仍被本模块持有的资源。

### 9.5 超预算处理

先优化重复合成、静态缓存、光晕分辨率、裁切与无效调度，再重新比较画面和性能。

不得静默删掉折射、霓虹层次或修改用户已确认画面以通过预算；也不得自动套用旧 M1 的超预算豁免。确需“画面优先/节能”档位时，给出并列样板和测量，用户选择后更新门槛。

## 15. 回退、发布与兼容策略

### 15.1 三种回退分别处理

1. **运行故障回退**：新后端初始化失败或无法恢复时，切为该主题的静态普通表现，保留数据/操作与原因提示；不修改用户主题文件。
2. **用户退出新效果**：显式关闭 GPU、切旧主题或安全启动，停止新模块并恢复原窗口行为。
3. **版本回退**：保留旧可运行产物、旧配置备份和新配置副本；验证旧版能启动，不要求旧版编辑器理解所有新参数。

故障回退不等同于自动降低已确认画质。帧率或画质偏好改变必须显式可见；未经批准不以删效果掩盖性能失败。

### 15.2 发布前要求

- Release、shader、主题、纹理、许可证、绑定库/原生组件全部进入打包清单；校验哈希和运行架构 x64。
- `pack-release.ps1` 会处理并删除暂存目录下的 `resources/assets/`；新素材放在独立目录并显式复制，不能误以为放进 assets 就必然进包。
- 在无 SDK、无源码、无 shader 编译器的新目录启动；至少验证旧模式、新模式、GPU 不可用、安全启动和配置只读。
- 延续现有 framework-dependent 发布时，明确要求兼容的 x64 .NET Desktop Runtime；“无 SDK”不等于“无运行时”。在已安装运行时和缺运行时的干净环境中分别核对成功启动与准确提示，禁止依赖开发机偶然存在的 DLL。
- `resources/shaders/`、`resources/materials/` 和所需原生 DLL 的构建复制/发布路径必须写入 manifest，并从最终 ZIP 实际验证，不只检查源目录或 bin 目录。
- 旧更新/恢复组件行为保持；新增文件不得破坏原有更新校验和路径限制。
- 现有更新器的“主 EXE 存在”不等于新 GPU 成功启动，也不能据此假定自动保留旧包。V1 至少在更新事务外保留一个明确可用的完整旧产物和对应配置副本，并演练还原；如需改更新器保留策略，另列独立补丁与更新器测试，由发布 owner 负责，不能夹带大规模更新器重写。
- 推荐将旧包完整解压到独立恢复目录后恢复对应配置，而非把旧包覆盖到残留新 DLL 的目录。新版首次启动失败/更新中断后的恢复过程必须有证据；保留材料的路径、保留时机和清理条件明确写出，不依赖更新器成功后可能已清除的内部备份。
- 启动脚本提供明确的普通启动/安全启动方式；主窗口仍只有一个稳定的逻辑身份，避免重复标题让实机脚本误选宿主窗口。
- 默认不把新实验主题设为所有用户启动主题，不自动迁移旧设置。
- 发布说明列出实际支持的 OS/会话/GPU能力、截图录屏行为、已验证平台和未验证平台。
