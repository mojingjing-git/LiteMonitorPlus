# #166：CPU 电压上面板/任务栏实施计划

## 1. 当前结论

这是现有功能的核实与补齐任务。当前代码已有：

- `SettingsHelper` 中 `CPU.Voltage` 监控项，默认隐藏，用户可分别用于面板/任务栏。
- `SensorMatcher` 中 CPU Voltage 匹配，包含 core/cpu/vcore/vid，并排除部分其他电压轨。
- `MetricUtils` 中 Voltage 类型、V 单位、CPU.Voltage 进度显示范围。
- 语言标签、普通值缓存和 Web 取值通路。

因此先检查现有设置能否满足用户，再针对证据修复。需求见 [上游 #166](https://github.com/Diorser/LiteMonitor/issues/166)。

## 2. 目前可以从源码确认的缺口

1. 匹配逻辑只在 `HardwareType.Cpu` 分支中处理电压；主板/SuperIO 的 CPU 核心电压可能未被选入。
2. Vcore 与 VID 被归入同一个键，没有区分测得的供电电压和请求/参考电压。
3. SensorMap 对同优先级候选基本依赖首次匹配，可能受枚举顺序影响。
4. Generic fallback 可复用最后有效值，需防止来源丢失后长时间显示旧电压。

这些是实现层缺口，不等同于已实测某台 i9-14900HX 缺失。必须记录真实硬件、LHM 版本及传感器来源。

VID 的含义应根据处理器/传感器实现确认；它代表电压控制请求，不能直接称作测得的核心供电电压。参考 [Intel VID 电源设计说明](https://www.intel.com/content/dam/doc/design-guide/voltage-regulator-down-11-1-processor-power-delivery-guidelines.pdf)。本任务只读取和显示，不修改电压/BIOS，也不把监控读数作为处理器可靠性的保证。

## 3. 产品与来源规则

### 3.1 复用现有监控项

- 保留 `CPU.Voltage` 键、旧用户标签、排序和面板/任务栏选择。
- 默认显示选择不变，不重复新增 CPU 电压项目。
- 自动选择优先使用经 LHM 实现确认的核心供电遥测；只有 VID 时允许参考显示，但自动标签/提示明确“CPU VID”。
- 用户自定义标签优先级不变；即使用户覆盖了标签，来源提示仍须区分 VID。

### 3.2 候选和选择

建议引入小型 `CpuVoltageResolver`，输出数值、来源类型、硬件 Identifier、传感器 Identifier、采集时间和有效性。

| 来源 | 处理 |
|---|---|
| 经实现确认的核心供电遥测，如对应核心轨的 VR VOUT/SVI/Vcore | 自动选择候选，按来源可信度和 CPU 归属排序 |
| CPU 请求电压 VID | 独立标记 RequestedVid；不与测得电压平均混合 |
| 主板明确命名且确认 CPU 归属的 Vcore | 可作为自动候选，保留来源和采样周期 |
| SoC、GT、SA、AUX、DIMM、输入供电、5V/12V 等 | 不自动映射为 CPU 核心电压 |
| 仅名称泛称 CPU、来源含糊 | 自动模式不盲选；手动列表可显示来源待确认 |

同优先级用稳定 Identifier 排序，不能依赖传感器枚举顺序。名称规则只作为候选入口，最终需要核对当前 LHM 0.9.6 的实际语义，不能认为所有同名传感器在所有主板上都相同。

## 4. 实施任务

### V0：复现与功能盘点

- 在冻结基线验证：设置中能否启用 CPU 电压、能否分别显示在面板和任务栏。
- 记录硬件详情中全部电压候选：硬件层级、名称、Identifier、当前值与是否为 VID。
- 检查普通用户/现有驱动环境，区分“设置项存在”“传感器已提供”“最终显示成功”。
- 已经正常且来源正确的部分仅补说明和回归，不另建平行实现。

交付：功能盘点、样本及实际失败路径；不自动安装驱动。

### V1：纯候选选择与值有效性

- 新增 `src/System/HardwareServices/CpuVoltageResolver.cs`，采用可注入候选列表，先用假数据覆盖选择规则。
- 有效值要求有限、非负并符合来源定义；0V 可能来自休眠/门控，不能仅因为等于 0 就当失败，也不能强行套所有平台通用范围。
- 无效、来源消失和超期时返回缺失，不能永久沿用旧电压。
- 如果 VID 是每核心多个值，明确聚合策略并在标签注明，例如“最高核心 VID”；本版只在确认语义后选择一种策略，不能任取第一核。

### V2：采集、配置与来源失效

- 在现有 SensorMap 重建/预缓存中准备候选，真实 Update 仍由共享采样入口执行。
- 只启用 CPU 电压时也应触发所需 CPU 更新。若选中主板来源，把该来源纳入现有主板慢扫描需求，默认沿用 3 秒节奏并披露刷新速度。
- 自动和手动来源选择建议保存为稳定传感器 Identifier；旧配置缺字段即 Auto。
- 新增 `PreferredCpuVoltageSensor` 的精确名称由集成 owner 确认；手动来源消失显示“来源不可用”，不悄悄改用另一种含义的电压。
- 设置列表仅枚举已发布候选，不在 UI 中调用 hw.Update、重新 Open 或启用额外控制器。
- 来源切换、热重载和失效时清除本项代次缓存及最后有效值/元数据，避免旧值与新来源标签组合。
- `UseWinPerCounters` 不影响电压来源；不把 CPU 负载计数器当电压回退。

### V3：显示与兼容

- 共用一份电压格式和来源说明，单位 V，低电压保留必要小数，例如 `1.23 V`。
- 面板、任务栏、提示、Web 与当前 GPU 场景适配都验证；无数据为缺失状态。
- 进度条最大值不当作硬件安全阈值；本版不新增统一“安全电压”告警。
- 9 个语言包同步来源类型、Auto、不可用等必要文案。
- 如果新增 Web 来源字段，采用向后兼容的可选字段；现有数值字段仍为数值，不能混入 `VID:` 字符串。

## 5. 修改范围

核心候选路径：`SensorMatcher.cs`、`SensorMap.cs`、新 resolver。

共享接线：`src/System/HardwareMonitor.cs`、`HardwareValueProvider.cs`、`HardwareScanner.cs`、`src/Core/Settings.cs`、`src/UI/Settings/SystemHardwarPage.cs`、`MetricUtils.cs`、必要提示/Web 代码和语言包。

根目录：`G:/TOOL/LiteMonitor-fork`。新 GPU 渲染分支的修改由其 owner 集成，不直接覆盖当前未提交代码。

## 6. 自动化验收

| 场景 | 必须断言 |
|---|---|
| Vcore、VID 和 SoC 同时存在 | 选择已确认的核心电压，来源正确，SoC 不混入 |
| 只有 VID | 标签/元数据标记参考值，不冒充实测电压 |
| CPU 下无电压，SuperIO 提供 Vcore | 可选入并接到既有慢扫描需求 |
| 同优先级候选乱序 | 选择结果稳定 |
| 手动源不存在/热重载后 Identifier 改变 | 缺失提示，旧值/旧来源不残留 |
| null、NaN、Infinity、负值及来源允许的 0 | 有效性符合来源规则 |
| 100 ms UI、多 Web 读取 | 不增加普通硬件 Update；同代次复用 |
| 设置迁移、旧用户标签/排序/可见性 | 不重复新增指标，不覆盖用户选择 |
| 1.234V 的面板/任务栏/Web | 小数、单位及来源一致，缺失不显示 0 |

建议文件：`CpuVoltageResolverTests.cs`、`CpuVoltageWiringTests.cs`、`CpuVoltagePresentationTests.cs`。

变异至少覆盖：去掉 VID 类型区分、恢复枚举首项选择、去掉来源切换失效。每条对应测试应变红；正常来源显示提供阳性对照。

## 7. 实机与完成条件

- 在可获得的 Intel、AMD 设备中分别记录来源；目标 i9-14900HX 无法获得时明确未验证，不宣称已支持该机型。
- 与同源传感器对照；不要要求 Vcore 与 VID 数值完全相同，也不要拿不同刷新时刻的小幅差异当 bug。
- 至少核实一次面板、任务栏和来源切换。睡眠/唤醒、重新加载后来源与数值一致。
- 无硬件支持时清楚显示未提供数据，主程序及其他指标仍正常。
- 通过当前全量回归，保留硬件不支持的边界；提交按“resolver/测试 → 接线/来源 → UI/语言”组织。
