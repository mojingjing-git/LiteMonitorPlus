## 4. F01：按 HWND 代次累积呈现历史（P1）

### 生产约束

窗口历史与某一 GPU 宿主的即时状态不同。同一 HWND 代次内，Unbound → Bound → PresentAttempted → Presented 只能向前；宿主释放、换皮、启动失败、重试、切 legacy 都不能抹去历史。只有确实进入新的 HWND 代次后才重置。

### 实现步骤

1. 修改协调器 `RecordBindingState()`，对同代次状态做单调推进；显式按枚举含义排序，避免依赖未经确认的数值顺序。
2. `OnHandleCreated()` 核对代次，只有较新的真实句柄代次才重置历史为 Unbound。重复回调不重置，过时代次不得回滚当前代次。受控／非受控首次创建保持现有启动边界，不能因重置自动创建 GPU。
3. 审阅 UIController 所有记录入口；保留新宿主原始状态供诊断，但不能直接降低协调器的 HWND 历史。若存在跨宿主／跨句柄滞后的回调，使用已有代次判据丢弃，不能污染新代次。
4. 统一回退继续使用原有 `RequiresControlledRecreate()`；不要绕过关闭优先级、UI 安全点或受控重建失败处理。

### 验收矩阵

- Bound / PresentAttempted / Presented 后分别记录 Unbound，仍要求重建；Presented 后记录 Bound 保持 Presented。
- 没有历史的冷启动失败仍可以不重建；不得把所有失败粗暴改成必重建。
- 实际调用生产 `ScheduleGpuFailureFallback()`，旧窗口有呈现历史、新宿主绑定前失败时保持重建判定。
- 真正推进 HWND 代次后历史清空；同代次重复 HandleCreated 不清空；旧代次回调被丢弃。
- 隐藏窗口、关闭优先、首次 HandleCreated 不启动 GPU、重建失败状态及既有故障原因保留测试继续通过。

真实桌面 GPU 设备故障及像素回读仅在环境和既有安全探针允许时执行。无法执行时保留未验证标记；纯状态测试证明判定修复，不虚报完整画面验收。

## 5. F02：明确恢复逐轮接管未解决责任（P2）

1. `TryRearmForExplicitRecovery()` 只选择 Failed、确曾修改 affinity、尚未 Reclaimed 的同代次责任。
2. 先登记携带精确原始 affinity 的新责任，登记成功后再标记被接管责任；登记失败不丢原责任。保持每代次至多一个非终态责任及同实例登记幂等。
3. 不改写旧责任的 Failed / exhausted 审计状态，不把“停止重试”改成“恢复成功”。
4. 若存在多个未解决责任，应明确接管关系而不能悄悄把不相干的责任都标完成；首先维持现有生产的一代次责任链不变量。

验收：A 耗尽 → B 耗尽 → C 成功后解除闸门；再失败再恢复的多轮链；无未解决条目时拒绝凭空重建责任；已有 pending 时不增加责任；精确原值、旧代次、未修改过 affinity 和登记失败都保持正确。

## 6. F03：热加载后对账插件运行任务（P2）

### 设计

新增明确的“是否已启动调度”状态，区分启动前的 LoadPlugins 与运行中的热加载。启动前只加载／恢复，不提前创建任务。运行时加载完成后按模板和实例的组合指纹对账；真正的 Stop 后不能因随后的 Load 自动复活调度。

### 实现步骤

1. 先读取并构造新的模板集合，再替换，保留原有去重和失败处理规则。不要一边枚举运行回调一边无锁修改共享调度字典。
2. 组合指纹包括实例参数及完整执行模板的语义内容（URL、headers、body、extract、process、outputs、interval 等），不能只比模板显示版本号；同版本内容变化也要重启。
3. 对删除／禁用实例，先在生命周期发布门内原子提交代次退役、移除调度身份、清除旧实例缓存和数据／标签／单位；门外取消旧等待者 CTS、停止并释放资源。新的代次只能在旧代次退役／清理完成后建立。清理键必须匹配完整实例名及点分隔命名空间，不得用裸前缀误删 A 与 AB 等不同实例。
4. 对模板变化的已启用实例退役旧任务、清实例缓存、按新模板同步监控项并启动恰好一个新任务。稳定未变实例保持原任务，避免普通“应用设置”造成全部重启。
5. **必须建立原子发布协议**，不能仅在 await 后或写入前检查 token／代次。每次执行持有内部生命周期身份／发布租约，校验当前身份与提交共享副作用在同一门内完成；与退役使用同一门或有明确单向锁序。网络与解析在门外准备，门内只做短提交。成功值、api_text、错误、标签／单位／颜色、KeyCache、步骤缓存写入／过期删除／淘汰、失败计数及调度收尾全部纳入协议，保持公开执行入口及现有测试接缝兼容。
6. 计时器重装的身份核对、表项核对与 Start 必须与退役有原子顺序，防止核对后才退役又重装。外部网络重置等动作必须有失效身份无法执行的授权／串行执行协议，不能只在门外做一次检查后继续无保护执行。不得持发布门或 `_scheduleLock` 等待网络／任务、取消 CTS 或调用任意外部观察器；退役身份先提交，取消与资源释放在门外进行。
7. 当前 OnSchemaChanged 未见生产触发，本轮不增加通知功能；若实现触及通知，门内仅形成带真实代次的通知意图，门外分发，由消费端过滤过期身份或与退役共用串行投递。订阅者重入 Stop／Reload 不得死锁。旧等待者取消仍不能传播至共享 HTTP 请求的其他等待者或底层共享请求。
8. 启动、RestartInstance、Reload、热加载使用同一指纹规则。市场页保持薄调用，不在 UI 层复制任务对账。

### 验收

- 手动计时器驱动真实 PluginManager；旧模板 URL 改为新 URL 后只执行新模板，新间隔生效；同版本 JSON 改正文／解析规则也生效。
- 卸载后调度数归零，强制触发旧计时器也不执行／重装。即使可见性探针为 true（对应网页运行态），结论仍成立。

- 用真实执行器或生产发布接缝，在旧执行“最后一次身份检查之后、共享写入之前”设确定性屏障；完成热加载／卸载及新值发布后放行旧执行，分别验证成功和异常完成都不能覆盖数据、错误、标签／单位／颜色或缓存。

## 7. F04：市场安装记录与文件提交保持一致（P2）

### 持久化合同

只有插件文件及相应 settings 安装记录都成功提交后，安装才算成功。设置保存失败时，已修改的内存列表必须恢复；回滚未确认完成前不删除仍必要的备份／事务日志。

### 实现步骤

1. Agent C 修改 SettingsHelper 的共享保存协议。所有 Save／TrySave 先进入共同保存门，再检查 GlobalBlockSave、序列化、写盘与失败临时文件清理；不得继续锁外序列化或锁外删除共用 tmp。保持 public Save 静默失败及 TrySave 返回 bool 的兼容性。
2. 提供内部事务保存入口：市场前态快照、仅当前记录的变更、序列化／写盘、失败时内存恢复全部在该共享保存门内。通用 Save 无法捕获暂态列表；不能用市场独立锁代替。仅恢复事务触及的 MarketPlugins 条目，不替换 Settings 单例或旧整份 Settings，不回退同期无关字段。记录读取使用同一访问协议。门内只执行受控设置操作，不回调安装器、调度器或 UI。
3. 锁序明确为安装／恢复事务门在外、共享保存门在内，保存门内绝不反向取得安装／恢复锁。Commit 与 Recover 必须共用串行事务门或明确单向锁序，防止活动提交被恢复清理交错。
4. 区分回调尝试、已持久化、已撤销内存和文件已确认恢复；事务专用失败使用可识别结果／异常表明内存已恢复。初次保存失败且内存已撤销时不再次调用必然失败的记录补偿。兼容一般回调“先改内存后抛出”的现有合同，不能只在回调返回后置 recordTouched。
5. **选择以持久化记录为提交证据的恢复协议**：新记录已持久化后发生 afterRecord 故障，优先确认旧记录补偿成功，再恢复旧文件／删除新文件。补偿失败时保留与新磁盘记录一致的新文件及 journal／backup，后续恢复可以按已提交记录向新版本一致收尾。不得先消耗唯一备份再尝试可能失败的记录补偿。若补偿成功但文件恢复失败，保留必要材料，恢复必须能依据持久化旧记录恢复旧文件；必要时扩展可校验的阶段／前态元数据，不能假设仅“目标不匹配新 hash”就已恢复。
6. 恢复使用独立持久化记录读取或经过共享门确认的提交快照，不能无条件把 Settings.Load 实时单例当磁盘证据；读取失败保持 pending，不把默认配置当无记录，不永久替换单例。必要的文件 Move／Delete 必须反馈成败，只有记录与文件确认一致才标 handled 并删除日志；垃圾清理与一致性所需操作分开，不能用 SafeDelete 吞失败当成功。
7. 复核安装／更新及卸载调用点。若强化 Remove 的失败语义会导致“文件已删、记录仍在”，须同步提供卸载补偿或保留兼容包装。保持源锁定、hash、插件 id、路径重建与重解析点边界；新增 journal 字段同样视为不可信，不扩大路径信任。

### 验收矩阵

- 新安装：先保存基线设置，再实际独占锁住 settings.json，安装必须报失败；解除锁并强制重载后无新记录、无孤儿插件文件。
- 更新：旧文件／旧记录存在，保存失败后两者都仍是旧版；内存与重新加载结果一致。
- 正常新装／更新成功后记录能重新读取，最终 journal 与备份按原合同清理。
- 使用 GlobalBlockSave 的失败路径也不能报告成功；实际文件锁测试不能被仅 mock 返回 false 替代。
- 确定性屏障暂停市场暂态变更区间，并发发起真实通用 Save；市场失败恢复后通用 Save 才能序列化。内存、独立磁盘读取和旧文件一致，无关设置修改不丢失；保留独占文件锁和 GlobalBlockSave 用例。
- 真实提交新记录后注入 afterRecord 故障，分别让记录补偿失败、文件恢复／删除失败；新装与更新都覆盖。释放故障、丢弃测试内存前态后，按独立磁盘记录运行生产恢复，只能得到一致旧版或按明确提交点确认的新版本。未完成时材料在，确认一致才清理。
- 保留回调先改内存再抛出反例，并加 Commit／Recover 交错屏障测试；既有安装 crash point、SettingsRecovery／保存备份和路径边界套件继续通过。

## 8. F05：插件主机表示统一规范化（P2）

1. 抽取内部唯一主机规范化辅助过程，供声明集合、凭据目标比较、HTTP 重定向、native fallback／redirect 使用；不再维护多个不同口径的 StripPort。
2. 先划定完整静态 authority（原始语法保留），拒绝动态 authority，再验证完整 authority 的语法及消费边界；通过后提取规范主机，按既有合同忽略合法端口和合法 userinfo。不能先剥 userinfo／端口把非法输入洗成合法声明；区分完整 authority 和已解析主机输入。静态主机、动态路径／查询参数仍可声明，native 内嵌 URL 保留 `&` 等外层参数边界。保留方括号 IPv6 的可用表示，压缩零段、前导零和大小写等价写法一致。
3. 规范化返回失败时必须拒绝；不能返回空字符串后把空主机当相等。不能把不同 IP、域名后缀或非法 userinfo 归并；对 DNS 不做实际解析，不接受 wildcard，不扩大端口／协议政策。
4. 本轮明确拒绝 scoped IPv6。在原始 URI／authority 仍保留 scope-id、尚未取丢失信息的 `Uri.Host` 前识别，数字 scope 和编码形式都拒绝；只检查 IPv6 authority，不误杀路径／查询中的百分号。政策统一用于声明、直接／凭据目标、HTTP 逐跳 redirect、native fallback／redirect，并在缓存查找及加入在途请求租约之前执行，覆盖 CanonicalizeUrl／RequestIdentity，不能让被拒地址通过缓存命中绕过。保留普通非 scope IPv6 及原协议合同。

验收：完整／压缩 IPv6、前导零、大小写／合法 userinfo／端口等价；`fd00::1` 与 `fd00::2` 不相等；双 `@`、非法端口、不完整方括号不得贡献声明或为动态目标授予凭据资格。保留无路径 query／fragment、静态主机动态路径／参数正例、动态 authority、跨主机 redirect、https 降级反例。数字／编码 scope、有／无 scope、不同 scope 均不能被当成等价可用目标，覆盖普通 HTTP、凭据、HTTP redirect、native fallback／redirect，并断言在请求／缓存／在途复用之前拒绝，未发请求。实际驱动对应生产边界方法，保留 LM-078/079/080/081/082/094 套件及反射薄包装兼容。
