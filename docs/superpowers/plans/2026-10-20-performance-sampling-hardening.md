## 1. 要解决的问题与完成目标

在界面选择 100 ms 刷新时，当前 `UIController.Tick()` 同时高频调用硬件更新。实测本机的 NVIDIA 整卡更新成本明显高于 CPU 硬件对象更新，高频采集显著增加进程 CPU 时间。另有整数秒取模引起的重复慢扫描/维护、无人访问 Web 时全量采集、Web 快照意外触发 FPS、FPS 失效 PID 未清理等问题。

本轮要交付以下行为：

1. 界面仍可以按现有频率刷新、平滑数值；普通硬件传感器采集有独立的时间门限，最高每秒一次。
2. UI、WebSocket 和 HTTP 快照共享一个采集入口，无法通过多个消费者叠加采集频率。
3. 慢扫描、保存、自动 GC 请求、工作集维护均按经过时间执行，每次到期只执行一次，恢复后不突发补跑。
4. 仅开启 Web 服务且没有合法客户端需求时，不扩大硬件采集范围；有人访问时保留现有普通指标展示能力。
5. FPS 必须有明确需求才启动外部服务；Web 不会因为遍历全部配置项就悄悄启动 FPS。
6. FPS 的失效/长期闲置 PID 记录能回收，同时保护实时计数与重新出现的进程。
7. 通过可重复测量说明 CPU 是否下降，并保护最近的 GPU 多卡、Intel 核显预热、映射缓存刷新与故障日志修复。

### 本轮边界

- 不重写 WinForms/GDI 渲染器，不替换 LibreHardwareMonitor，不升级 NuGet 包。
- 不重做插件执行器、主题、设置页架构、任务栏嵌入或 WebSocket 协议。
- 不加入浏览器指标订阅协议。当前网页是自动展示服务器快照，没有浏览器端指标选择机制。
- 不把“隐藏主窗体”直接等同于“所有消费者都不需要数据”：任务栏、悬浮提示、历史记录和 Web 可能仍在使用。
- 不通过删除监控项、固定显示值、关闭错误日志或屏蔽多卡来满足性能指标。
- 不改驱动安装、自动更新、品牌/许可证逻辑。性能测试不安装或卸载驱动，不修改用户常用实例的设置。

## 4. 本轮技术决策

### 4.1 保留现有调用结构，采集入口统一限频

本轮在 `HardwareMonitor` 建立单一采集协调入口。UI 定时器继续处理界面逻辑，Web 访问也通过同一入口请求采样；不再为每次界面 Tick 无条件启动一次硬件更新任务。不增加一个与原定时器并行的常驻硬件更新循环。

建议保留兼容的 `UpdateAll()` 外观，并为 UI/Web 提供类似 `UpdateIfDueAsync()` 的入口。具体命名可调整，但同步探针和异步调用必须经过同一个时间门限与并发保护，不能各自维护时钟。

普通硬件的有效周期：

```text
localPeriodMs = max(1000, normalized RefreshMs)
effectivePeriodMs = 有已鉴权的 Web 数据需求 ? 1000 : localPeriodMs
```

`RefreshMs` 无效时回退到现有默认值 1000；合法慢刷新值继续生效。因此 UI=100 ms 时硬件最高 1 Hz；UI=3000 ms 且无 Web 需求时仍按约 3 秒采集，避免慢刷新用户反而增加开销。FPS 使用自身统计频率，不归入普通硬件整卡更新。

明确以下要求：

- 同一时刻最多一个真实采集任务。并发消费者共享进行中的任务，不排队累积多个更新。
- 构造后尚未开始异步初始化的短窗口，也不能被误判为可采集；`_isOpening == false` 本身不代表初始化已成功完成。初始化、重载与采样之间必须有明确的就绪状态。
- 未到期快速返回，不调用 `hw.Update()`，不清值缓存，不推进采集时间，不发“新样本”事件。
- 门限采用单调时钟。正常任务按采集起始时间安排下一次；超长任务结束后重新安排未来期限，不立即补跑错过的多轮。
- 初次初始化、成功重载和设备选择变更可标记需要重新采样；普通 UI/Web 请求不能借此无限绕过门限。启动/恢复的例外更新计数单独标记。
- 关闭过程中停止接受新请求，等待或安全结束进行中的任务后再关闭硬件；UI 的异步回调必须检查窗体/控制器是否已释放。
- 采样异常仍按正常周期重试，保留故障日志和旧有效数据，不能形成异常忙循环。

### 4.2 把值缓存生命周期从“界面 Tick”改为“采集代次”

`OnUpdateTickStarted()` 当前每轮清 `_tickCache`。限频后，这一步只能发生在真实新采样开始及必要的配置失效路径。否则 UI/Web 高频读值仍会反复执行 `PerformanceCounter.NextValue()`，达不到目的，还会破坏速率类计数。

- 一轮采样的有效读值供纵向、横向、任务栏、Web 复用。
- 合法的 0 必须缓存；最终不可用值应避免在同一代次反复走昂贵失败回退。缓存 null 时保留当前“有最后有效值则回退”的语义。
- 按现有锁保护缓存读取/失效，处理 Web 与 UI 并发。
- 设备偏好、显卡数量、映射重建、重载必须有明确的失效规则，不能跨设备复用旧代次数据。
- FPS、时间文字、插件值有自己的更新机制，不得被普通硬件缓存冻结一秒以上；也不能因更新它们而清空普通硬件缓存。
- 本轮可以继续使用受锁保护的懒取值缓存，不要求一次性重做全部指标的数据模型。

### 4.3 单调调度与流量计时

采用 `TimeProvider`/可注入单调时钟或项目内简单时钟接口。使用截止时间判断，不使用 `DateTime.Now.Second`、整数秒余数或 `Environment.TickCount` 取模窗口判定周期任务。

| 工作 | 约定周期/首次触发 |
|---|---|
| 普通硬件 | 4.1 的有效周期 |
| 主板/SuperIO、非目标网卡、活跃后台磁盘 | 不快于每 3 秒一次；启动必要预热独立处理 |
| 冷却中的后台磁盘 | 不快于每 10 秒一次，继续保留当前磁盘休眠规则 |
| 流量保存 | 首次约 5 秒，此后每 60 秒 |
| 自动 GC 请求 | 首次约 30 秒，此后每 180 秒 |
| 自动工作集检查 | 首次约 45 秒，此后每 300 秒 |
| 任务栏主题检查 | 约每 5 秒一次 |

同一到期时间最多消费一次；跳过若干周期后最多执行一次，然后安排下一次。周期状态属于正确的服务实例，不要用易互相污染的全局静态时间戳。

流量 `timeDelta` 必须取两次真实采集之间的经过时间，不能用 UI Tick 数乘刷新间隔。保留原生字节计数优先、SMB 扣除、网卡切换与首次计数初始化。休眠/超长间隔按明确的重置策略处理，不补造流量尖峰；系统墙上时间回拨不能得到负 delta。

自动 GC/裁剪本轮只修调度；不改变手动内存清理入口，不以反复清空工作集制造低内存截图。

### 4.4 Web 需求和 FPS 的确定策略

普通 Web 指标继续独立于面板显示标志，合法访问时保留原有快照字段、分组、多卡和普通指标范围，不直接把 Web 列表过滤成面板可见项。

`WebServerEnabled` 仅表示服务开关，不再单独代表全量采集需求：

- 已鉴权且尚未关闭的 WebSocket 连接计入需求；连接数变化不按浏览器发送频率增加采样频率。
- 全量普通指标需求不能无条件绕过显卡选择：从当前可输出的 GPU key 和监控卡集合确定需要的卡，更新未纳入监控集合且不在快照中的物理卡没有收益。`MonitoredGpuCount=1` 的 Web 不应隐式更新两张物理卡；配置两卡时两卡都必须更新。保留首选卡及编号规则。
- 已鉴权的 `/api/snapshot` 请求获得一个短需求租期，建议 2 秒，并请求一次共享采样；连续 HTTP 轮询延长租期。
- 未鉴权请求、仅取 HTML/favicon，不产生硬件需求或启动 FPS。
- 最后一个连接关闭且 HTTP 租期过期后，恢复本地需求范围。服务 Stop/重启清理全部旧需求。
- 第一次合法快照请求要能获得一次符合需求的样本：通过共享采集入口等待在途/下次允许采样，不能让高频 HTTP 绕过 1 Hz，也不能必须先打开桌面面板才能更新。
- 快照序列化本身不启动硬件服务或执行 `hw.Update()`。准备数据与 JSON 写出分开。
- 用取消/代次区分 Stop 前后的广播任务，防止快速 Stop/Start 后旧循环复活造成多重广播/采集。

增加一个明确且可持久化的选项：

```csharp
public bool WebFpsEnabled { get; set; } = false;
```

放在现有 Web 设置卡片，说明启用会产生额外采集开销。旧设置缺少此字段时为 false；不修改既有本地 FPS 显示选项。

```text
localFpsDemand = 本地 FPS 配置在面板或任务栏启用
webFpsDemand = 当前有合法 Web 数据需求 && WebFpsEnabled
fpsDemand = localFpsDemand || webFpsDemand
```

没有 FPS 需求时，Web 可输出 FPS 的 `--` 占位，保持现有字符串字段契约；不得把未启动误报为 0 FPS。若本地 FPS 已在采集，Web 可以复用结果。关闭 Web FPS 不得停掉仍由本地使用的服务；关闭本地 FPS 也不得停掉仍由 Web 使用的服务。

增加 `Menu.WebServerFps`、`Menu.WebServerFpsTip` 等必要语言 key，并给刷新频率增加清楚说明：它控制界面刷新，普通硬件数据最高每秒采集一次。九种语言文件同步，保留用户自定义标签和现有设置行为。不引入第二个普通硬件刷新率设置。

### 4.5 FPS 状态清理

- 明确已退出的 PID 及时从帧计数、累计历史、平滑历史、结果、名称缓存中移除。
- 长期不再产生帧的记录设置有界闲置期限，建议 30 秒；正常的短暂停顿不能立即抹掉全部平滑历史。
- `Unknown` 可能表示权限或瞬时查询失败，不等同于“已退出”。查询失败做有界重试/负缓存，建议同一 PID 至少间隔 5 秒再查，不能每 500 ms 抛同一个异常。
- 处理 `ParseLine` 与统计/清理并发：真实新增帧不能被过期清理永久丢弃，重新出现的 PID 能恢复统计；必要时使用带最后活动时间/代次的记录。
- `GetProcessById` 返回的 `Process` 用完释放。PID 重用时旧名称/历史不能永久套到新进程。
- 外部服务启动需要原子防重入；未启用状态不启动、不下载、不制造失败重试忙循环。
- 当前 `Dispose()` 被健康检查、空闲停止和重启复用。若修改后台任务生命周期，必须把可恢复的 Stop 与最终 Dispose 分开，避免空闲停止后永远无法再启动；不需要改生命周期时不要扩展重构范围。
- 保持现有 FPS 选取和平滑规则，除非测试证明为完成上述清理所必需。

## 6. 性能与功能验收矩阵

### 6.1 不依赖机器速度的硬性不变量

| 场景 | 必须观察到的行为 |
|---|---|
| UI 100 ms，普通硬件需要更新 | 每卡稳态最高约 1 次/秒，不是 10 次/秒 |
| UI 1000 ms，相同本地需求 | 与 UI 100 ms 的硬件更新次数同量级 |
| UI 3000 ms，无 Web | 保留约 3 秒硬件周期 |
| 10 个网页/高频合法 HTTP | 总采样仍受同一门限控制 |
| Web 开启、0 个合法需求 | 不额外更新本地没有需求的 GPU/主板/电池等 |
| 新样本未到 | UI/Web 不重复读性能计数器、不清采样缓存 |
| 慢扫描/保存命中同一期限 | 只执行一次 |
| 长任务、休眠、系统时间变化 | 不补跑一串任务，不产生负流量/流量尖峰 |
| 映射十分钟重建/设备重载 | 新缓存生效，失败保留旧有效结果 |
| 停止/关闭/重启 | 无重入采集、已释放对象访问或重复广播 |

计数时区分初始化/条件预热/重载和稳态更新；例如 60 秒稳态的一张卡应不超过约 60 次，边界允许一次计时误差，不能把启动例外计入后误判。

### 6.2 实机性能组

每组预热至少 15 秒、稳态至少 60 秒；最终比较至少三轮，使用中位数。先关掉与本轮无关的插件、真实 FPS，再单独验证其功能。记录后台负载，GPU 负载状态尽量一致。

| 组 | UI 周期 | GPU/消费者 | 目的 |
|---|---:|---|---|
| A | 1000 ms | 默认单卡，Web 关 | 保护默认模式成本 |
| B | 100 ms | 同 A | 验证高刷新不放大硬件采集 |
| C | 100 ms | GPU 项全关，Web 关 | 对照剩余基础成本 |
| D | 100 ms | Web 开、无人访问 | 验证空闲服务不扩大范围 |
| E | 100 ms | 单个合法网页，普通指标 | 连接活动时数据正确且限频 |
| F | 100 ms | 多网页 + HTTP 轮询 | 验证多消费者共用采样 |
| G | 100 ms | 多卡本地监控 | 每张启用卡均正确，成本随卡数合理增长 |
| H | 3000 ms | Web 关闭；再开合法网页 | 验证慢刷新省电和独立 Web 需求 |
| I | 100 ms | 本地/Web FPS 需求组合 | 验证明确启动、结果复用和空闲退出 |

记录：进程 CPU 时间增量、总经过时间、逻辑 CPU 数、整机 CPU 百分比、实际采样次数、每设备更新次数、平均/P95 采样耗时、分配量、工作集和 GC 次数。指标不足以测量时标明，不输出虚构的 0。

**性能目标：** 在此前能复现高开销的本机条件下，B 组“采集循环”的 CPU 中位数相对 Task 0 基线降低至少 60%。A 组没有明显额外工作；同机比较建议用“高于基线 25% 且增加超过 0.05 个整机 CPU 百分点”作为默认模式退化的排查线。不是所有机器都保证同一绝对百分比；目标未达到时分析更新计数/调用耗时并如实报告，不把降低 UI 刷新率当作达标。

完整可见窗口另外测：100/1000 ms、100%/200% 缩放、纵向/横向、任务栏开/关、主窗体显示/隐藏。将绘制 CPU 与硬件采集数据分开，避免用 GDI+ 位图基准代替真实窗口。若采集已降而可见窗口仍高，再开独立绘制优化任务。

## 8. Agent 协作、提交与风险控制

单 Agent 可以顺序执行全部任务。多个 Agent 时建议：

| 负责方 | 可独立负责 | 依赖和交接 |
|---|---|---|
| 主 Agent / A | 采集协调、缓存、调度、`HardwareMonitor` 集成 | Task 1–3；拥有共享硬件入口的最终修改权 |
| B | Web 需求/设置/语言与测试 | 等 A 冻结共享采样接口后接入；不要同时重写 `HardwareMonitor` |
| C | FPS 内部 PID 清理和查询限速 | 可在基线后并行；FPS 需求入口与 A/B 先约定 |
| D | 基线探针、数据整理和复测 | 基线先完成；不要与其他性能测量同时运行以免相互污染 |

建议按任务形成小提交：基线工具、调度策略、采集/缓存接入、维护修复、Web/FPS 需求、PID 清理、验收文档。类型与粒度可按实际依赖调整，但每个提交保持可构建、可解释。

共享文件重点：`HardwareMonitor.cs`、`HardwareValueProvider.cs`、`Settings.cs`。派发时明确所有者，先约定接口再并行。未提交改动由哪个任务产生不清楚时先核对归属，不用 reset/clean 覆盖。

关键风险与检查：

| 风险 | 必须采取的检查 |
|---|---|
| 只限 `hw.Update`，仍每 UI Tick 清缓存 | 同代次性能计数器调用次数测试 |
| Gate 放在错误位置，流量仍按 UI 时间算 | 固定速率/字节差值的流量测试 |
| Web 改成只取面板项，普通网页指标丢失 | 面板隐藏项仍可在合法 Web 需求下更新 |
| HTTP/多个网页绕过采样门限 | 并发压力下实际硬件更新计数 |
| 缓存旧 FPS 值延长服务存活 | 无需求先拦截、停止后不刷新访问时间 |
| Dispose 被当作可恢复 Stop | 关闭全部需求后再次启用 FPS 的测试 |
| Intel/多卡修复被限频改动覆盖 | 原测试、条件预热和失败保留旧映射检查 |
| 为消除 CPU 而吞日志/显示固定值 | 数值变化、错误注入、日志频率一起验收 |
| 基线/后测实际包含不同版本或配置 | 每轮记录 HEAD、dirty 状态、程序集哈希、配置摘要 |

有权限或硬件缺口时继续完成可测部分，并在 verification 标记未验证项目；不得通过安装驱动、改用户常用配置来补齐本计划未授权的环境操作。需要额外授权时给出已经完成的证据、所需操作与原因。
