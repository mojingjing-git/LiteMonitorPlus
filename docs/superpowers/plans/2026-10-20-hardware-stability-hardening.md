## 1. 目标、交付与范围

解决以下三类问题：

1. NVIDIA/NVML 陈旧句柄引起的原生访问违例：采用已有上游修复，并建立可限制故障影响范围的采集边界。
2. 启动或热插拔时识别所有磁盘，导致机械盘唤醒、外置设备断连：磁盘访问策略在第一次识别前生效。
3. SMART/磁盘识别空引用：覆盖第三方库自己的识别线程，单设备失败不阻止其他模块更新。

分两次可独立验收的交付完成：

| 里程碑 | 范围 | 允许作出的结论 |
|---|---|---|
| M1：已知根因修复 | Task 0–7：磁盘策略、系统计数器、配套依赖修复、单设备异常处理 | 已修复已验证的访问策略及已知库缺陷；不能承诺任意原生故障都不影响主进程 |
| M2：故障隔离 | Task 8–11：GPU/SMART 子进程、快照、故障恢复、发布集成 | 在验收的用户态崩溃/阻塞场景下，主界面和其他采集模块继续工作 |

里程碑用于组织提交和验收，不自动引入再次审批步骤。实施者按依赖推进；缺少某项实机条件时记录未验证范围，不能把缺少证据写成通过。

保留 GPU 多卡身份和排序、每卡分组、显存来源/容量修复、Intel 核显预热、缓存重建和现有硬件错误日志。保持现有指标键与用户监控项，传感器不可用时显示不可用，不删除配置或固定显示 0。

本计划不重写渲染器、插件系统或主程序自动更新逻辑。实施与故障验证不安装/卸载驱动，不在用户当前会话中自动重启 GPU 或刺激外置阵列。

## 2. 已确认的事实与边界

- 当前主项目固定 `LibreHardwareMonitorLib 0.9.6`，实际依赖 `DiskInfoToolkit 1.1.2`。
- `HardwareMonitor` 构造时设置 `IsStorageEnabled = true`。LHM 的 `Computer.Open()` 会创建存储组并触发识别，首选盘过滤发生在之后。
- 1.1.2 存储识别包含物理盘枚举；旧 LHM `StorageGroup.Close()` 为空，库有静态监听线程，事后关闭属性不能视为彻底停止。
- `#196/#579` 堆栈来自 `DevicesChangedListener()`。应用围绕 `hw.Update()` 的 catch 覆盖不到这个独立线程。#582 只有附件，研究时尚未取得附件，保留待核实。
- LHM PR [#2539](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor/pull/2539) 已合并，提交 `3aa9c6c5bfc45fd15f4166bd35d73609b2bb126c`；修复 NVML 句柄重取、设备身份和关闭竞态。0.9.6 中仍是旧实现。
- 研究日的联合升级候选为 `0.9.7-pre767`，其 net8.0 依赖包含 DiskInfoToolkit >= 2.2.1；这是预览版本，必须经过本项目验证。
- DiskInfoToolkit **2.2.1 标签源码**提供 `Storage.ExcludeUsbDevices`，默认 false。这个开关不等于任意设备白名单，不能覆盖所有非 USB 外置盘或内置机械盘。
- 真实原生访问违例不能靠增加托管 catch、全局回调或 `Task.Run` 可靠恢复。手工抛出同名托管异常也不能模拟这种故障。

## 5. 统一设计约定

### 5.1 磁盘模式与旧配置

新增 `DiskProbeMode`，与运行时纯策略类 `DiskProbePolicy` 配合。序列化沿用项目现有约定；缺失或未知枚举值归一化为基础模式，不丢弃整份用户配置。

| 模式 | 允许访问 | 默认行为 |
|---|---|---|
| `CountersOnly` | Windows 性能计数器及必要的缓存元数据 | 新安装和缺少新字段的旧配置均采用；不创建 LHM StorageGroup |
| `SelectedSmart` | 显式允许列表中的设备，并满足排除规则 | 允许列表为空时不识别任何盘；不能把“自动”解释成允许所有盘 |
| `AllSmart` | 明确选择此模式后，识别排除规则之外的全部设备 | 不使用允许列表；设置界面说明访问范围，不作为失败回退 |

新增 `SmartDiskDeviceIds` 允许列表，设备 ID 来自系统已有的设备身份信息；排除 USB 的选项默认开启。USB/UASP/硬盘盒可能报告为固定磁盘，不能用 `DriveInfo.IsRemovable` 或名称猜测连接类型。身份或连接类型无法确认时，受限模式拒绝识别并给出原因。

优先级固定为：基础模式全部拒绝 SMART；USB 排除规则优先于允许列表；`SelectedSmart` 再匹配允许列表；`AllSmart` 省略允许列表检查但仍执行排除规则。访问 USB 盘需要明确关闭 USB 排除并选择相应设备/模式，不能因设备在允许列表中就绕过排除。

所有规则必须在库打开设备、读 SMART、识别型号、容量/分区扫描之前应用，并同样约束初次发现、物理盘兜底枚举、热插拔和重载。**禁止先调用全量 `GetDisks()` 再按允许列表过滤。** 如果库没有相应前置接口，就在其源码适配层补充；不能用应用层后置筛选冒充访问控制。

保留旧 `PreferredDisk` 文本。新增或使用独立稳定 ID 表示速度统计目标，通过不发起 SMART 的目录映射旧名称：唯一匹配时迁移；歧义或设备缺失时标为待选择，不任意选另一块同名盘。用户原本选择“自动/总计”才允许使用 `_Total`。

旧温度项、排序、别名和可见标志全部保留。基础模式中温度显示 `--` 或既有不可用样式，设置页说明需要启用 SMART；不能因为旧配置勾选了温度就自动开启识别。

### 5.2 不可用与回退

基础模式中的磁盘速度不受通用 `UseWinPerCounters=false` 变成 SMART 回退；它由磁盘模式明确指定系统计数器。计数器缺失时返回不可用。

读取路径至少保留有效性、采集时间和来源。禁用、故障或设备移除后清理该来源的旧缓存，不把历史最后值永久显示为当前值；历史、阈值告警和 Web 均应识别无效样本。对现有 JSON 消费端保持兼容，必要时新增可选状态字段，不引入逐指标订阅协议。

M2 中工作进程确认退出/源被禁用时，当前读数立即置为不可用；进程仍在但没有新采集结果时，过期阈值默认取 `max(3 × 有效采样周期, 5 秒)`。最后有效样本可供诊断保留，但不能作为当前有效读数返回。阈值与单调时钟可注入测试，避免依赖长时间真实等待。

### 5.3 运行时切换

M1 中只要当前依赖无法证明能停止全部磁盘监听，就使用应用受控重启来应用 SMART 的开启/关闭，而不是只切换一个属性。先保存设置、停止后续采集并安排重启；重启完成前明确显示“待重启生效”。

基础模式启动期间可以动态切换速度统计目标，不得启动 SMART 来填充选择列表。M2 中由停止/重建对应工作进程应用磁盘模式，主界面继续运行。

**依赖：** 库内部分依赖 Task 3 固定的源码/API，并与 Task 4 由同一存储库 owner 推进；共享 `Storage.cs` / `StorageManager.cs` 的修改按顺序落地。应用侧单设备异常边界可在 Task 2 接口确定后独立准备，不必等待 Task 4 全部验收。**文件：** `HardwareMonitor`、`HardwareErrorLog`、存储库识别/监听代码、相关测试。

- [ ] 在同步更新中按设备捕获普通托管异常并继续处理其余设备，替换 `UpdateAll` 最外层无信息空 catch。
- [ ] 在库内部每个识别事件及设备创建边界处理普通异常；不依赖应用 `hw.Update()` catch 去接另一个线程的异常。
- [ ] 对缺失型号/控制器/SMART 结构采用明确的无效设备结果，禁止空值对象发布为有效硬件。
- [ ] 异常路径同样使用 SafeHandle/try-finally 释放资源，隔离事件订阅者异常，避免处理循环永久退出。
- [ ] 单设备连续失败默认最多立即尝试一次，之后进入有上限的退避；结构性识别失败隔离到明确重试。一次失败不触发全盘重扫。
- [ ] 日志包含模块、阶段、稳定设备 ID、异常类型、依赖版本和退避状态；相同错误限频，保留首次及状态变化。

验收：注入空信息、识别异常、更新异常和订阅者异常后，其他设备继续；无句柄泄漏和重复扫描风暴。真实原生访问违例交给 M2 隔离。

### Task 7 — M1 界面、发布与验收

**依赖：** Task 2、4、5、6。**文件：** `SystemHardwarPage`、设置应用、Web/告警/历史、语言包、发布脚本与 verification。

以上是 M1 最终验收依赖；界面可在策略、设备目录和读数状态接口冻结后先行开发，Web/历史的无效读数适配可使用假快照并行完成。

- [ ] 呈现模式、允许设备和不可用原因；设备选择列表不通过 SMART 探测填充。
- [ ] 缺失新字段的旧配置采用基础模式，并给出一次非阻塞说明；温度项不删除。
- [ ] 旧依赖需要重启才能彻底停止时，界面如实显示生效状态，不假装已经停止。
- [ ] 检查 Web、任务栏、历史和告警不会使磁盘权限扩大或把无效读数当真实 0。
- [ ] 在干净发布目录验证依赖、资源及版本，避免旧 DLL 影响结论。
- [ ] 执行 §8 的 M1 自动测试和可用实机项目，记录剩余限制。

验收：M1 的用户行为与配置迁移可复核；报告区分“已修已知根因”和“仍未建立原生故障隔离”。

## 7. M2：把原生故障留在采集进程内

### Task 8 — 快照、目录与进程协议

**准备依赖：** §5 的策略、读数状态及进程边界合同冻结，不依赖 Task 7 完成。建议新增 `LiteMonitor.HardwareContracts` 与纯父进程监督器，名称可按仓库规范调整。协议、纯状态机和假工作进程可以与 M1 并行开发；主进程正式切换和 M2 验收仍须通过 M1 门槛。

- [ ] DTO 包含协议版本、角色、工作进程代次、配置代次、设备身份、指标键、数值、单位、Max 语义/重置规则、采集时间与有效性。
- [ ] 硬件目录包含层级、传感器名称/类型/ID、完整标记和修订号；跨进程不传 `IHardware`、`ISensor`、句柄或委托。
- [ ] 本机 Named Pipe 以随机会话标识和当前用户权限连接，限制消息长度；工作进程按父 PID/进程句柄管理。
- [ ] 每角色最多一个在途采集请求，合并后续请求；旧代次结果不能覆盖新配置。
- [ ] 兼容现有 `HardwareMonitor.Get` 的数值外观，但改为读已验证快照；Get、网页序列化和绘制不得同步等待原生查询。
- [ ] 工作进程离线或返回未完成目录时不收缩 `MonitoredGpuCount`、不运行破坏性迁移；只有完整有效目录才允许设备数量同步。

验收：通过协议/监督器测试覆盖断帧、未知版本、旧回复、取消和目录暂时缺失，不需要真实硬件。

### Task 9 — GPU 与 SMART 独立工作进程

**依赖：** Task 8 的协议与公共宿主；GPU 分支还依赖 Task 5 的配套库，SMART 分支还依赖 Task 4、6 的存储修复。建议新增一个 `LiteMonitor.HardwareProbe` 可执行项目，以 `--role gpu` / `--role storage` 启动两个独立实例。两种角色的实现和目录界面适配可分别派发；`Program.cs`、项目文件及主采集入口保持唯一写入者。最终主进程切换在 Task 7 验收后集成。

- [ ] 主进程 LHM 永久关闭 GPU 和 Storage，防止 Open、预热、传感器浏览或重载再次进入高风险路径。
- [ ] GPU 工作进程持有完整 GPU 生命周期；按 LHM 条件保留 Intel GPU 所需 CPU 枚举，避免核显消失。
- [ ] SMART 工作进程仍在首次 Open 前执行策略；基础模式不启动这个进程。
- [ ] 把 GPU 名称、卡序、分组所需注册信息、显存相关传感器和硬件目录同步到主进程；保留现有键及稳定身份映射。
- [ ] 调整 `HardwareScanner`、设置页、`HardwareInfoForm` 与 `LiteTreeView`，通过合并目录显示远程传感器，保留 Value/Max/复制行为。不得为了兼容旧原始树入口在主进程重新启用模块。
- [ ] 主进程统一发布目录、GPU 注册信息和快照，避免 `SensorMap` 的本地 Clear/Replace 覆盖远程卡信息；UI Tick、设置保存与迁移均检查目录完整性，不能因短暂离线删改 GPU 数量或标签。
- [ ] 同一个驱动/控制器不在主进程与工作进程中重复轮询；必要的 CPU 枚举也应实测其新增成本。

验收：从首次启动到退出，GPU/SMART 原生调用均位于对应工作进程，主界面仍能显示和配置这些设备。

### Task 10 — 监督、退出与发布

**准备依赖：** Task 8 的协议、进程控制及时间接口；纯监督器、退出策略和发布脚本可与 Task 9 并行准备。**集成验收依赖：** Task 9 两个角色接通。**文件：** 监督器、主窗体生命周期、设置应用、各 csproj/sln、开发/发布脚本。

- [ ] 同时监视工作进程存活、请求开始时间和采集完成序号；独立心跳存活不能掩盖采集线程已永久阻塞。
- [ ] 初始截止时间建议 GPU 启动 30 s/单轮 10 s，SMART 启动 60 s/单轮 15 s；可由 Task 0 实测调整，并在 verification 记录理由。
- [ ] GPU 故障采用有界退避：2 s、10 s、30 s；10 分钟内三次自动恢复失败后停用到本会话明确重试，避免无限重启。
- [ ] SMART 进程崩溃或超时后默认停止自动重启，保留计数器速度统计；由用户明确重试恢复，避免坏盘反复受扰。
- [ ] 仅终止本会话创建并持有句柄的工作进程；父进程退出保证清理，可采用 Job Object。禁止按全局进程名称清理。
- [ ] 日志区分退出码、超时、协议故障和设备故障，记录最近阶段；不每 100 ms 同步写磁盘日志。
- [ ] 所有新增项目从主项目默认 Compile/资源 glob 中排除；开发和发布都包含工作进程、运行时文件及精确配套依赖。
- [ ] 缺少工作进程时明确降级为模块不可用，禁止悄悄恢复为主进程内原生采集。

验收：正常退出无孤儿；更新替换文件前工作进程已释放；缺文件、崩溃和超时均可诊断且不形成重启风暴。

### Task 11 — 故障注入与 M2 验收

**准备依赖：** Task 8 的协议；假设备、延迟/挂起/退出/旧代次回复场景可提前开发，并与纯监督器互测。**最终验收依赖：** Task 9、10 的实际集成。建议在独立测试工作进程中实现假设备和故障场景，不把故意崩溃开关发布到正式工具。

- [ ] 终止 GPU 采集进程：主 UI、网速、设置继续响应；旧读数按时失效，恢复次数受限。
- [ ] SMART 进程出现真实原生错误或未处理后台线程异常：主进程存活，速度计数器继续，不自动重复探盘。
- [ ] 采集函数永久阻塞但心跳继续：超时监督仍然生效，不积累新任务。
- [ ] 配置切换、旧工作进程延迟退出、父进程退出、主窗口隐藏、Web 开关都不会产生重复进程或旧结果回写。
- [ ] 若验证真实原生访问违例，在自有测试工作进程中执行；`throw new AccessViolationException()` 不是等价测试。
- [ ] 记录完整进程树的 CPU/内存与启动时间，不能只统计主进程来宣称性能改善。

验收：M2 的存活保证有故障注入证据；真实驱动重启、睡眠/唤醒和外置阵列验证仅在合适测试环境执行，缺少条件就明确列为未验证。

## 8. 验证矩阵与证据格式

| 类别 | 自动验证 | 实机验证/观测 |
|---|---|---|
| 策略与迁移 | 缺字段、未知值、空名单、冲突规则、旧首选盘歧义 | 旧配置升级后速度和监控项仍保留 |
| 初始化访问 | 假工厂/访问记录证明未构造或打开排除设备 | Process Monitor/等价观测确认冷启动和页面访问没有目标盘探测 |
| SMART | 初始、热插拔、重载执行同策略；资源计数回零 | USB/UASP 固定盘、内置机械盘、目标 SSD；外置 RAID 有条件才测 |
| 托管异常 | 缺失型号/控制器/SMART、事件异常不终止循环 | 持续运行与设备变化，无错误刷屏或全盘重试 |
| GPU | 每轮句柄重取、PCI 身份校验、Close 同步；现有多卡/显存/预热测试 | 现有双 NVIDIA；Intel 真机有条件才标记通过 |
| 隔离 | 子进程退出、阻塞、旧消息、恢复上限、父进程退出 | 可见主窗口、任务栏、Web 同时工作时的状态变化 |
| 性能与发布 | 干净输出、依赖哈希、进程树清理 | 相同机器/配置/时长，统计全部相关进程并与 Task 0 对比 |

实施阶段使用项目实际支持的命令，例如：

```powershell
dotnet build LiteMonitor.sln -c Release
dotnet test tests/LiteMonitor.Tests/LiteMonitor.Tests.csproj -c Release --no-build
pwsh -File scripts/run-dev.ps1 -Configuration Release -NoLaunch
```

新增项目后相应补充构建与发布检查。测试只在隔离配置/输出目录运行，禁止通过删除或修改用户的真实配置使测试通过。检查点应记录命令、退出码、构建哈希、模式、目标设备、结果和限制。

研究时 #582 附件尚不可读：实施时如果能够取得，补录实际堆栈再归类；不要把 issue 标题当作已证实的同一根因。

## 9. 提交、回滚与完成条件

建议独立提交配置/策略、基础计数器路径、固定依赖/补丁、SMART 访问控制、异常边界、M1 验收、协议/监督器、工作进程集成、M2 验收。源码依赖的修改来源和构建记录与对应补丁一起保存。

回滚依赖时必须回滚一整套配套输出。对于新版本写入的磁盘策略，旧二进制可能忽略新字段并重新全盘识别，因此不能将“直接启动旧版”当作安全回滚。优先回滚到仍保留基础模式和初始化前开关的构建，或提供独立验证过的安全迁移版本。

完成时应交付：

- [ ] 对应范围内的实现、明确的依赖/补丁版本、可重建发布产物。

- [ ] M1/M2 分别可核实的验收记录，包含全部相关进程性能数据。
- [ ] 发布说明说明 SMART 默认策略、不可用读数和恢复方式。
- [ ] 所有未验证硬件或现场证据明确列出，不把候选版本、catch 或模拟异常当作实机稳定性证明。
