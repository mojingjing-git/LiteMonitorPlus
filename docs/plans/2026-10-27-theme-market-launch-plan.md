## 0. 审核结论（2026-10-27）

**有条件通过，可进入 TM00；执行前先落实以下四点，均已并入对应任务：**

1. **本地化回退口径要写实。** 当前 `LanguageManager.GetOriginal` 只回退到 key 后缀，没有 `en.json` 底表；本计划说“zh/en 完整、其余走现有回退”会让 de/ja 等语言显示裸 key。TM04 必须为新增文案补齐 9 个语言文件，或先实现英文底表回退并加缺 key 测试；不得把“key 后缀”当英文回退。
2. **同一市场页实例的去重要覆盖三处。** `SettingsForm.AddNav` 可以把同一 `PluginMarketPage` 注册到 `PluginMarket` 与 `ThemeMarket` 两个 key，但 `ApplySettings()` 会按 key 重复调用 `Save()`，`DisposeCachedPages()` 会对同一实例重复 `Dispose()`，`SwitchPage()` 也没有“进入哪个类别”的意图参数。TM04 必须按引用去重保存/释放，并在切换时显式请求 `MarketCategory.Themes`；验收要覆盖“两个入口来回切、确定/应用/取消、关闭设置”。
3. **远端仓库的实际基线已核对。** 本地只读克隆在 `G:\TOOL\awesome-litemonitor-plugins`；`scripts/gen_index.py` 目前只扫描 `plugins/`，`.github/workflows/gen-index.yml` 的触发路径也只有 `plugins/**`、`scripts/**`，且 `updated_at` 每次取当前时间。TM03 必须同时扩展主题/审核目录扫描、工作流触发路径、确定性 `updated_at` 和 `PLUGINS.md` 生成，不能只改生成器脚本；不得覆盖或重排插件段。
4. **共享校验器必须把计划里的硬约束真正落地。** 现有 `ThemeMarket.ValidateThemeContent` 用 `Encoding.UTF8.GetString`（默认替换非法字节）和原始文本 `http(s)://` 检查，无法拒绝“无效 UTF-8”和 JSON 转义后的远程引用；且在 `PluginMarket.DownloadBytesAsync` 的 8 MiB 上限之前没有主题 256 KiB 限制。TM01 必须补严格解码、解码后引用检查、声明大小/实际大小一致、主题大小上限及对应正反例。

## 3. 数据、目录与兼容合同

### 3.1 远端目录与本地文件名

```text
awesome-litemonitor-plugins/
  themes/
    market-aurora-gpu/
      theme.json
      submission.json
      preview.png
      README.md
  reviews/themes/
    market-aurora-gpu.json
  index.json
```

- 远端允许每主题一个目录；本地仍安装成 `{id}.json`。`file` 填 `theme.json`，安装目标始终由合法 ID 推导，不能由远端文件名决定。
- `preview.png` 仅用于仓库展示；客户端继续校验载荷后本地渲染快照/预览，不新增远程图片通道。
- ID 首期统一小写 `market-*`，满足现有 1–64 位字母/数字/下划线/连字符规则；按 Windows 大小写不敏感语义检查唯一性。
- CI 检查当前支持客户端内置文件名清单；客户端仍检查实际目标文件与安装归属。无市场记录的内置主题、手动主题不得覆盖。
- 显示名称允许重复，不作为安装身份；主题改名不改变 ID。首期拒绝更换已有 ID 的内容归属。

### 3.2 投稿元数据与版本

现有 `Theme.Version` 是主题格式版本整数，现有导出 `submission.version` 沿用该整数；市场条目的 `version` 是发布版本字符串。两者必须分开。

首期在既有投稿摘要上附加字段，不破坏当前字段含义：

```json
{
  "id": "market-aurora-gpu",
  "name": "极光",
  "name_en": "Aurora",
  "description": "适合深色桌面的液态玻璃主题",
  "description_en": "Liquid glass for dark desktops",
  "author": "作者名称",
  "version": 3,
  "market_version": "1.0.0",
  "license": "MIT",
  "route": "gpu",
  "material": "liquid_glass",
  "file": "theme.json"
}
```

- 示例仅展示关键字段；导出继续保留 `sha256`、`byteCount`、`previewRoute`、`previewIsFallback` 等事实。
- 资料准备界面增加 ID、发布版本、双语描述、许可证填写；旧投稿包可以补齐这些字段后上架，无须重写主题载荷。
- 发布版本首期限定 `major.minor.patch` 非负整数三段；同 ID 更新必须递增。相同版本修改载荷应拒绝；只修说明或元数据允许独立提交。
- 生成器将 `market_version` 映射到索引 `version`，绝不能把格式版本 `3` 自动猜为发布版本。
- 首批许可统一 MIT，并确认作者拥有分发权；市场元数据保留许可，仓库文档说明适用范围。

### 3.3 索引生成

生成器扫描 `themes/*/submission.json`，读取最终 `theme.json` 原始字节，产生当前 `MarketThemeEntry` 支持的字段：

`id/name/name_en/description/description_en/author/version/file/download_url/page_url/sha256/size/route/material/status/verified`。

- URL 从固定仓库、分支、合法 ID 和文件名构造，不直接采用投稿者给出的任意下载 URL。
- SHA-256 与大小由生成器计算；摘要针对最终提交字节，哈希后不得再格式化文件或变换行尾。
- `themes_total` 是主题数；`total` 保持现有插件统计定义。插件条目不得因主题生成而消失、重排出错或改变摘要。
- 使用现有生成器扩展，先核对其入口；禁止另起一个会覆盖插件段的独立全量生成器。
- 排序、序列化固定；相同输入应产生相同有效索引，若维护更新时间则固定其来源，避免每次运行无意义改动。
- 输出先写临时文件、验证完整索引后替换；仓库中主题载荷、审核信息与索引作为同次发布变更交付。
- `schema` 保持 1；验证最旧受支持客户端仍能读取插件段及主题附加字段。

### 3.4 审核与版本兼容

- 投稿者不能通过 `verified=true` 自行授信。首期审核证据存放在维护者控制的 `reviews/themes/`，绑定 ID、发布版本和载荷 SHA-256。
- 审核记录至少包含应用版本、系统、GPU/驱动、DPI、实际渲染路线、首帧/切换结果、兼容外观结果、截图和审核结论。
- `verified` 仅由有效且摘要匹配的审核记录生成；载荷变动后旧审核自动失效。UI 解释为“已按记录环境验证”，不承诺所有硬件兼容。
- 首批主题只使用最旧受支持市场客户端已认识的能力，并用该版本实测。TM00 固定该版本号，未固定前不允许上架。
- 不以新增 `min_app_version` 字段代替客户端拦截：旧客户端会忽略它。需要新能力的主题暂不进入首期同源索引，后续先设计可执行的兼容策略。

## 4. 校验与仓库 CI

### 4.1 共享内容校验

从 `ThemeMarket.ValidateThemeContent()` 提取无网络、无文件写入、无 Settings/窗口初始化副作用的校验单元。可暂命名 `ThemeMarketValidator`；复用 `ThemeRenderingConfig.Validate()`，不重新手抄规则。

- 输入：最终载荷字节及路线、材质等声明；输出：稳定错误码与可读诊断。
- 客户端原有异常对外合同保留，由薄适配层转换结果。
- 仓库 CLI 复用同一校验实现。TM01 确定可在 Windows CI 运行的最小依赖路径，避免为首期拆分整套渲染架构。
- CLI 通过固定版本的受信构建产物或固定提交取得；仓库记录校验器版本，客户端与仓库都跑同一组正反例。禁止复制两份校验逻辑后各自维护。

### 4.2 硬校验清单

1. ID 合法、唯一、目录与 ID 一致，不撞内置名称；拒绝符号链接/重解析点越界、路径穿越和 Windows 保留设备名。
2. 投稿字段齐全，发布版本合法且满足递增规则，许可证明确。
3. `theme.json` 为严格有效 UTF-8、单一 JSON 对象；首期生成产物使用 UTF-8 无 BOM。无效编码不能被替换字符悄悄接受。
4. 大小为 1–262144 字节；客户端对主题下载同步执行 256 KiB 上限，实际流读取有界。插件原有 8 MiB 上限不变。
5. `route/material` 与载荷一致，完整渲染参数校验通过；沿用缺 `rendering` 的纯 legacy 规则。
6. 沿用全文无 `http://` / `https://` 的主题内容合同，覆盖未知扩展字段；解码后的 JSON 字符串也不能用转义绕过。该限制不套用到仓库 README 的普通链接。
7. 摘要、实际大小与生成索引一致；不可把作者填的摘要当作可信计算结果。客户端同时核对声明大小，失败不得落盘。
8. GPU 主题必须有同一摘要对应的真实 GPU 冒烟记录；回退图不能作为真实 GPU 出帧证据。
9. 同 ID 同版本修改载荷、审核记录失配、无效条目均让发布生成失败，不默默忽略后产出“成功”的残缺索引。

### 4.3 工作流与权限

- PR CI：校验材料、对比已发布版本、生成候选索引、跑合同和正反例；只读权限，不发布。
- 首期 GPU 审核由维护者在独占实机时段完成，不要求普通托管 CI 假装有 GPU。
- 校验外部投稿时只处理数据；不执行投稿带来的脚本，不在有写凭据的工作流中运行不可信 PR 代码。
- 维护者在 PR 合并前生成并提交最终索引，CI 检查重新生成无差异；合并时主题、审核记录、索引一起进入主分支。首期不依赖合并后机器人二次提交。
- `main` URL 下新旧缓存可能短暂混用：客户端遇摘要不符必须失败并保留旧版本，刷新索引后允许显式重试，不关闭摘要检查、不承诺缓存层原子切换。

## 5. 客户端交互

### 5.1 独立入口与页面生命周期

- 设置侧栏保留“插件市场”，新增“主题市场”；两个入口指向同一个市场页实例，进入时明确请求对应类别并同步导航选中态。
- 复用既有类别切换，不维护第二套页面、下载状态或 GPU 预览。页面注册、上下文初始化、清理必须按实例去重；`SettingsForm.ApplySettings()` 的 `Save()` 与 `DisposeCachedPages()` 的 `Dispose()` 也必须按引用去重，`SwitchPage()` 切换两个入口时显式请求 `MarketCategory.Plugins/Themes`，避免同页重复保存、重复释放或停留在旧类别。
- 同一个页面内部切换分类时，侧栏状态同步；重复进入同类别不触发无意义重建。跨类别缓存、安装忙碌态继续受控，不能重复安装。
- 实际离页（含 `Parent` 被清空）、关闭设置、类别切换时停掉活跃预览；过期下载回调不能恢复已关闭页面。
- Theme Studio 的“浏览主题市场”作为同一入口的快捷跳转；复用已有设置窗口，保留未保存主题草稿，不新开第二个工作室或市场实例。
- 新文案走语言资源，至少 zh/en 完整；de/es/fr/ja/ko/ru/zh-tw 同步补齐，或先实现 `en.json` 底表回退并加缺 key 测试。当前 `LanguageManager` 只回退 key 后缀，不能把该行为当英文回退。

### 5.2 安装与应用

- 安装成功后刷新主题发现列表，显示“已安装”，提供独立“应用”动作，不未经用户操作切换主题。
- “应用”使用 `AppActions.ApplyThemeAndLayoutWithResult` 或其既有编排入口，展示实际 `Applied/Partial/Failed`，不以设置保存或文件存在代替运行时结果。
- GPU 开关关闭或 GPU 不可用时，可使用兼容外观，并明确当前路线；主题不能自行开启 GPU/抓屏设置。
- 市场动作与设置草稿协调：应用后更新对应的 Skin 草稿/基线，随后“确定/应用”不恢复旧 Skin，“取消”不撤销已完成的显式市场应用；其他未保存设置不得被顺带提交。界面注明安装/应用即时生效。
- 手动修改过的市场主题禁止静默覆盖；提示先在工作室另存副本。不添加绕过摘要保护的强制更新按钮。

### 5.3 更新、卸载与错误状态

| 场景 | 要求 |
|---|---|
| 未安装/已安装/可更新/记录存在但文件缺失 | 分别显示；更新和重装动作正确 |
| 更新非当前主题 | 事务更新文件与记录，失败保留旧版本 |
| 更新当前主题 | 区分“文件已更新”与“运行中已应用”；提供重新应用，确认使用新内容摘要，失败明确显示部分成功 |
| 卸载非当前主题 | 复用事务与归属保护，不删除手动主题或内置主题 |
| 卸载当前主题 | 先确认备用主题确实加载并运行，才删除；Partial/Failed 不算切换成功，不得只看 Action 未抛异常 |
| 切换成功但卸载失败 | 原文件/记录保留，当前画面可保持备用主题，如实提示；不得谎报整项成功 |
| 权限/只读/占用/磁盘写入失败 | 显示明确原因，不循环提权；事务和安装记录一致 |
| 拉取失败，有当前会话已成功加载列表 | 保留列表并标注刷新失败；安装仍重新验证载荷 |
| 拉取失败，无可用列表 | 显示失败空态与重试，不说成“市场没有主题” |
| 离页/刷新后旧请求完成 | 按代次丢弃，不回写新页面 |

首期不新增持久化离线索引；已有卡片快照缓存不代表离线索引或离线安装能力。

## 7. 验收与发布条件

### 7.1 自动化必测

- 复用并运行 `ThemeMarketContractTests`、`ThemeMarketPolicyTests`、插件市场合同/恢复测试、投稿导出测试与市场页面生命周期测试；新增用例优先验证可观察行为，不用源码字符串替代应用验证。
- 数据：缺字段/非法版本/大小写重复 ID/内置冲突/Windows 设备名/目录越界/无效 UTF-8/超大流/伪造大小/摘要不符/伪造路线材质/未知扩展远程引用及转义负例。
- 事务：首次安装、可更新、重装、用户修改保护；文件落盘和记录写入故障、安装中断后恢复；失败保留正确旧版本。
- 应用：主题实际切换、同名新摘要应用、Applied/Partial/Failed；GPU 关闭/不可用的路线提示；当前主题卸载必须依赖实际成功切走。
- 设置：即时动作后确定/应用/取消的 Skin 与其他草稿字段语义；两个市场入口导航一致，页面只清理一次，离页无活跃预览，旧回调无效。
- 仓库：重新生成无差异；原插件列表和安装仍可用；旧支持版本能读取实际索引。E2E 显式断言主题非空，不得遇空 themes 自动跳过后计为通过。
- CI 根据实际新增测试更新必要执行清单；汇总执行数、失败数、跳过及原因，零匹配不算通过。

### 7.2 实机与真实发布包必测

| 验收项 | 证据 |
|---|---|
| 从两个设置入口、工作室入口进入正确类别 | 截图/行为记录；无重复窗口或预览 |
| 每个精选主题的主面板、横向、任务栏及兼容外观 | 实际支持形态的截图；明确任务栏颜色受 Settings 驱动，不承诺主题接管颜色 |
| GPU 主题真实应用 | GPU 启用、设备/帧计数与实际出帧；回退截图单列，不冒充 GPU |
| 主动禁用 GPU/模拟不可用 | 可预览、可应用兼容外观，提示准确，无隐式打开开关 |
| 浅/深桌面、100%/150%/200% DPI | 主题卡片、按钮、预览和关键数字不遮挡；缺少对应屏幕则记录缺测 |
| 当前主题更新、卸载和故障恢复 | 文件摘要/安装记录/运行中主题与应用结果一致 |
| 独立目录解压的正式打包产物 | 从真实远端浏览→预览→安装→应用→更新→卸载→重启后状态一致 |

更新测试可用受控夹具完成 v1→v2；上架前还要验证真实索引与客户端白名单 URL、摘要、大小一致，不为了验收制造无意义的线上版本。

### 7.3 随本次 RC 发布的硬条件

1. N01–N03 等本次修复版既有阻断项按当前代码通过复核；市场通过不等于原 G1 通过。
2. TM01–TM07 必测无失败；4–6 个主题在真实仓库可用，实际安装/应用/更新/卸载闭环成立。
3. 同一冻结候选代码完成 Release 构建、当前完整回归、所需 GPU 门禁和打包验证。复用同一候选的现有有效证据，不重复全量凑次数；代码改变后重跑受影响门禁并在最终冻结时跑全量。
4. 未跑、跳过、仅夹具、仅回退都明确区分，不使用旧全量数字、空主题 E2E 或静态分类检测代签。
5. 原发布的 R11/R12/G1 等开放项保持独立状态，由原发布判断处理；本计划不借市场上线关闭这些项目。

若不满足：本次 RC 保持修复范围，市场新增入口不进入该发布候选，主题上架顺延。若入口变更已经集成，候选包须显式禁用未完成入口并验证，不影响原插件市场。稳定版不能因为市场通过而绕过原实机门禁。

## 8. 上架、撤架与后续

### 上架顺序

1. 固定并验证客户端候选版与共享校验器。
2. 完成远端主题、审核记录、索引的同次候选变更；生成检查和客户端真实 URL 合同通过。
3. 合并远端内容后检查实际返回字节；安装请求摘要失败时保留旧版本并允许重试。
4. 用实际发布包完成最终冒烟，冻结包/索引/主题 SHA-256，再按原发版流程发布。

本文是实施计划，不执行远端合并、推送或发布。

### 撤架与回滚

- 先验证当前客户端如何处理 `status`，不假定某个非 `ok` 值能立即阻止安装。首期紧急撤架从新索引移除该条目，已安装主题不远程删除。
- 缓存索引仍可能引用旧文件；若必须阻止该文件继续下载，维护者同步撤下对应载荷并验证新旧缓存行为，不承诺撤架瞬时全网生效。
- 已安装主题必须有本地管理入口可卸载；如果现有 UI 只能列远端索引项，TM05 补最小“已安装但已下架”行，按本地记录管理，禁止下架后无法卸载。
- 出现坏更新时停止分发该条目，保留用户现存文件；修复后提升发布版本重新上架，不静默篡改同版本文件。首期不提供历史版本浏览或一键降级。
- 客户端回退沿用原发布包和更新机制；市场文件、配置与安装记录的兼容性单独验证。

### 完成后再考虑

开放 PR 投稿运营、更多筛选标签、兼容版本的客户端拦截、用户目录与作品归属分离、历史版本下载。按使用反馈排期，不作为首期门禁。
