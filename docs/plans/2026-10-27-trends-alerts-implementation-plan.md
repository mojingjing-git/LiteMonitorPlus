## 1. 已有基础与目标

当前 [HardwareHistoryLogger](../../src/Core/HardwareHistoryLogger.cs) 按约 10 秒取样、按分钟汇总、保留 7 天；[HardwareTrendForm](../../src/UI/HardwareTrendForm.cs) 已有 1 小时/1 天/7 天视图和统计。当前 [UIController](../../src/UI/UIController.cs) 内的温度告警包含持续 5 秒和全局 3 分钟通知冷却。

首版增加四项用户价值：从某个指标直接打开趋势；最近一小时可查看更细的峰值和时间；曲线诚实显示缺口、设备切换与无效值；告警可解释、有恢复阈值，多个设备互不吞掉通知。

## 2. 首版范围与界面

- 保留现有历史窗口与长期记录入口，增加“查看此指标趋势”菜单。经典/GPU 面板及任务栏通过统一指标命令传入身份；GPU 若尚无可靠拾取，先从监控项菜单进入，不假装鼠标拾取已完成。
- 1 小时视图优先显示当前进程已收集的短时明细，1 天/7 天使用长期聚合；图中明确分辨率、采集开始时间和有效覆盖率。
- 悬停/键盘定位显示时间、值、单位和状态；摘要给出有效样本峰值、峰值时间、平均值。聚合桶只知道峰值所在时间区间时显示区间，不编造精确秒数。
- 查询按可视宽度合并绘图桶并保留最小/最大包络，避免长期历史逐点在 UI 线程重算；后台只保留最新查询，主线程绘制不可变结果，旧范围查询完成不得覆盖新选择。
- 告警编辑提供触发阈值、恢复阈值、持续时间、通知冷却、静音和规则启用；支持常用温度规则及数值上/下限。新建非温度规则默认关闭，用户启用后才增加需求。
- 首版不自动判断“网络故障”或“磁盘空间不足”：除非已有可靠对应样本/状态源并完成能力适配，否则在后续扩展，不把 0 KB/s 当断网。

## 3. 同一数据入口

主链路为：已发布 `HardwareSnapshot` → 统一质量/身份适配 → 短时缓冲、长期聚合、告警评估三个消费者。UI 只查询它们的只读结果。

1. 使用 [MetricSample / HardwareSnapshot](../../src/Contracts/SnapshotModels.cs)，不读取平滑后的 `DisplayValue`，不在图表或告警里直接调用 `_mon.Get`。
2. 每个 SessionEpoch + BatchId 只处理一次；重复读取、重复 IPC 投递不能增加历史样本数或告警持续时长。拒绝旧会话和倒序批次。
3. 稳定序列身份由 StableDeviceId + 指标种类/稳定传感器身份定义，目录提供外部 Key 的映射。GPU 序号变化不改写旧序列，拔插成另一设备不能拼成同一条线。
4. 别名仅按目录中明确的同源映射去重，不凭名称相同或数值相同合并两个设备。
5. 对 `Good/0`、Missing、Error、Stale 分别处理；按现有年龄合同在消费侧判断过期，不把缓存到达时间作为采样时间。采样周期变化时同时更新有效时效预算，不无限延长最后一个 Good。
6. 采样与告警持续时间采用单调时钟；UTC 只用于显示/持久化。跨进程年龄通过既有适配转换，不能直接相减不相容的相对时钟原点。
7. 全局 BatchId 变化不必然代表每个传感器都有新读数。适配器须提供可确认的源样本时刻/身份，利用现有 SampleAgeMs 等字段核对；相同缓存跨批次发布不重复增加有效计数或连续越限时长。当前合同无法可靠表达时，在 T01 对两端增量补齐，未完成前不声称具备秒级明细和连续性判断。

## 4. 短时缓冲与长期历史

### 短时明细

- 首版最多 32 条用户选择的指标序列，每条最多 3600 个秒桶，保留最近一小时；使用有界环形缓冲，满后覆盖最旧数据。超出指标配额时明确告知，不静默丢指标。
- 秒桶保留有效数量、平均/最小/最大、峰值实际样本时间、质量/缺口标记；同秒多个实际样本聚合，不能只保留最后一个值而抹掉尖峰。
- 超长停采、休眠、设备换代和无效样本形成显式断点，不补写旧值，也不在图上连成平滑直线。
- 默认利用已有采样保存明细，不为所有传感器隐式提高频率。窗口可见或用户明确启用后台明细时，登记相应采样需求；关闭窗口释放自己的需求，原有数据保留至正常过期。
- 点数硬上限为 115200 个秒桶。实现采用紧凑存储，目标额外稳态内存不超过 16 MiB，包含索引与桶；以实测验收，超预算优化结构或降低可配置容量，不能无限扩容。

### 长期汇总与迁移

1. 复用现有 7 天查询和图表，替换记录入口；新旧记录器不能同时对同一批次写入。
2. 保留当前长期取样/分钟聚合口径，新增短时明细不能悄悄改变旧文件统计含义。平均值按有效样本数加权，缺失桶没有有效平均值。
3. 引入有版本的历史记录格式，保存稳定序列身份和覆盖/质量信息。建议新文件 `HardwareHistory.v2.json`，后台原子写入，按时间/指标上限修剪；旧文件只读导入并留备份。
4. 旧 `GPU.Temp` 等序号型记录无法证明历史物理身份时，展示为旧格式历史，不猜成当前某张显卡。迁移失败不覆盖旧文件，不阻塞采样和开窗。
5. 新格式默认保留 7 天，文件设显式容量上限（建议 64 MiB）；超限淘汰最旧完整桶并记录截断原因。保存频率沿用批量写入，退出 flush 有截止时间。

## 5. 告警规则和状态机

拟新增独立纯规则引擎，接收标准化样本和可注入时钟；不持有窗体、采集器或通知 API。

规则至少包含 RuleId、稳定指标身份、比较方向、触发/恢复阈值、触发/恢复持续时间、最大允许样本间隔、通知冷却和可选持续提醒间隔。

| 状态/维度 | 语义 |
|---|---|
| Normal | 有效数据正常，尚无活动事件 |
| Pending | 有效数据持续越限，累计连续样本时间 |
| Active | 触发一个具有 IncidentId 的事件 |
| Recovering | 有效值持续满足恢复阈值，达到时间后确认恢复 |
| 输入不可用 | 暂停数值判断，清除未触发的连续时长；活动事件仍为未确认恢复 |
| 通知静音/冷却 | 只控制通知，不修改事件是否仍在发生 |

关键规则：

- 上限告警的恢复阈值低于触发阈值；下限告警反向。越界配置在保存前拒绝。
- 使用真实样本时间累计连续性。两点间隔超过规则允许值、中间有数据缺口或设备会话重置，不能用墙上经过的时间补成持续越限。
- 活动事件遇到缺失/过期不视作恢复；恢复有效数据后继续核实条件，同一活动事件不会因数据重新到达就再触发一遍。
- 冷却按规则/设备分别计时。多张显卡同时越温可合并展示，但一条规则的通知不会把另一台设备的事件吞掉。
- 每次活动/恢复/数据不可用状态变化写入诊断事件出口。通知失败不影响规则继续评估，并可在事件列表查看。
- 界面隐藏不停止已启用告警；锁屏时可抑制弹出通知但继续记录。醒来后不集中补发大量历史通知，给出合并摘要。

### 兼容既有温度告警

迁移 `AlertTempEnabled`、全局温度阈值、磁盘阈值公式、5 秒持续和 3 分钟通知冷却；迁移记录有版本，重复启动不会重复建规则。已关闭告警不被迁移开启。

恢复阈值采用明确的默认回差（温度建议 5°C）并在设置中可见。旧持续提醒若需要保留，以迁移规则的 3 分钟提醒配置表达；新规则默认只在触发/恢复时通知。只有新引擎接管并通过对照测试后撤除 `CheckTemperatureAlert` 的旧执行路径。

## 6. 需求与生命周期

- 应用级所有者持有趋势存储、聚合器与告警引擎；历史窗体只拥有展示订阅，关闭窗口不能停掉已启用告警。
- 首版与当前布尔 `SamplingDemand` 兼容，明确各消费者 ID；临时可通过既有 History 需求保证采样存活，不能将“告警”伪装成已打开的窗口。低功耗阶段再演进可区分的频率需求。
- 启用规则时检查该指标来源和可用能力；不自动开启被用户禁用的高风险探测策略。缺少来源时显示该规则暂不可用。
- 配置更改后串行更新规则；停用立即释放自身需求。Host 重连后重放有效需求，清连续候选时长，保留合理的事件身份，不跨会话补算持续时间。

## 8. 验收矩阵

1. 相同批次读取 100 次，趋势点数和告警累计时间不增加；换设备、换目录和 Host 重启有独立用例。
2. 有效零值绘制为零；缺失、过期、错误断线；同秒短峰在最大值和游标中可见；平均值与样本权重一致。
3. 假时钟验证临界值抖动、连续越限、长采样间隔、恢复回差、墙钟回拨、多个规则独立冷却、静音后恢复和通知异常。
4. 老告警启用/禁用、阈值和磁盘公式迁移保持可解释；重启不重复建规则；新旧执行器从未同时发送同一告警。
5. 历史文件坏数据、磁盘写入失败、旧格式身份不明、容量截断和退出超时均不拖住 UI/采样。
6. 单指标真实入口打开正确设备曲线；窗口最小化/关闭后展示刷新停止，告警按自己的需求继续。
7. 使用生成数据做 24 小时等效容量与状态测试，再做实机长时间运行；不能把加速时钟当作真实 24 小时资源证据。

## 9. 首版完成条件

用户能从一个监控项找到对应曲线、理解缺口和峰值，并配置不会抖动刷屏的温度/数值告警；所有消费者共用真实样本；历史身份和旧数据边界清楚；后台关闭与省电对告警的影响有合同。交付性能数据、迁移说明和已验证设备清单后，交给低功耗计划接入频率约束。
