## 3. S01：凭据保护失败时停止持久化

### 3.1 事实与落点

- `src/Core/Settings.cs`：`PluginSecretDictionaryConverter.WriteDict` 的 catch 将原值写入 JSON。
- 同文件备份净化路径保护失败会移除备份中的该字段，两条路径行为不同。
- `Settings.DeepClone`、`CloneForDiff` 也经过 JSON 序列化；直接让转换器抛异常可能影响设置页和应用编排。
- `src/Core/SettingsHelper.cs`：`TrySaveLocked` 先完整序列化，再执行原子落盘，已有保留旧文件的基础。

### 3.2 实现要求

1. 删除凭据保护失败后的原文持久化分支；空值及已经受保护的密文保持既有含义。
2. 增加明确的“凭据保护失败”保存结果，传递到实际保存调用方；不能由 `Save()` 吞掉后仍显示“保存成功”。
3. 持久化前完成全部凭据保护；任一必需凭据失败，本次保存整体失败，原主文件和有效备份保留。新值可留在内存/草稿中，但界面明确“未保存”，不能冒充重启后仍有效。
4. 已有密文解密失败继续保留原密文和错误状态，不删除、不转空、不覆盖为新明文。
5. 引入按用途创建的转换器及序列化选项：`Persistence` 读取时沿用解密与失败保留密文规则，写入时强制保护；`MemoryClone` 对字符串原值做深复制，不执行 Protect/Unprotect。内存中已解密的明文、原有密文和无法解密的密文都须保持各自原值，不能只复制密文而丢掉已解密值。
6. 旧明文配置继续可读取；下一次保护成功时迁移。遇失败不先销毁原配置。仅凭旧配置仍含明文，不能声称本批成功完成了迁移。
7. 给保护函数增加内部故障注入接缝，测试中可稳定模拟加密失败；生产仍使用当前用户作用域的 DPAPI。
8. `DeepClone`、`CloneForDiff` 显式使用内部 `MemoryClone` 入口；持久化使用独立 `Persistence` 入口。两套转换器实例和只读选项各自固定，不用进程级/线程级可变开关切用途，避免并发保存串用。
9. 现有 `PluginInstanceConfig.InputValues/Targets` 挂有属性级 `[JsonConverter]`，不能仅向 `JsonSerializerOptions.Converters` 增加工厂就假定覆盖成功。内存克隆选项使用 .NET 8 类型元数据修饰器，对这两个属性显式设置对应的 `JsonPropertyInfo.CustomConverter`；字典和目标列表转换器都必须传递同一用途，列表不能再静态调用默认持久化字典转换器。生产默认的属性转换器保持保护优先。
10. `MemoryClone` 结果和选项仅限内存复制调用方，不得用于文件保存、导出、诊断或日志；测试同时验证调用入口和实际保护次数，防止内存配置被误接入持久化。

### 3.3 验收

- 正常保存与读回，凭据值正确且落盘为保护格式。
- 注入保护失败：保存结果失败，旧文件摘要不变，本次临时文件、备份和日志不新增凭据明文；错误提示可见。
- 在同一故障下打开设置、深拷贝、生成差异，均无崩溃或凭据丢失。
- 覆盖 `InputValues` 与 `Targets[]`：内存克隆 Protect/Unprotect 调用数均为 0，字典/列表为独立副本，混合明文/密文字符串逐值保持；持久化仍触发保护并受故障注入约束。
- 并发执行内存克隆与保存，持久化不继承内存用途，克隆也不触发磁盘保护分支；属性级转换器不会覆盖选定用途。
- 保存失败后的市场记录变更仍能正确回滚，不出现文件安装成功、记录误报已保存。
- 成功迁移旧明文、失败保留旧配置、已有密文无法解密三个分支分别覆盖。

## 4. S02a：目标授权、地址预检与代理兼容

### 4.1 事实与落点

- `src/Plugins/PluginProcessor.cs`：`EnsureCredentialTargetAllowed` 无凭据即返回，职责仅限凭据去向。
- `src/Plugins/PluginExecutor.cs`：`BuildHopAllowedHosts` 把无凭据首跳加入集合；重定向主机检查不等于本地/私网访问限制。
- 默认及自定义代理使用不同 HTTP 客户端；既有 HTTP 请求关闭了自动重定向，应继续保持。
- 默认 `SocketsHttpHandler` 未关闭 `UseProxy`，会遵循系统代理；把所有系统代理用户改为待确认后才能联网会破坏存量行为。
- 两条客户端路径当前均设置约 2 分钟 `PooledConnectionLifetime`。复用既有连接不会因为每次请求的 DNS 预检而重新解析/连接；该时间也不是每两分钟强制中断所有活跃连接的保证。
- `DynamicHostAuthorizer` 与 `PluginPage` 已有按实例授权 origin 的基础，可以扩展复用。

### 4.2 固定的产品行为

| 目标类型 | 处理 |
|---|---|
| 模板明确声明的公网目标 | 正常执行，保留既有凭据规则；每跳检查 URL 与本地可获取的解析结果 |
| 用户填写的动态公网目标 | 对具体插件实例和完整 origin 显式授权；远端响应不能自行授权 |
| 本机、局域网目标 | 单独确认本地网络权限，绑定实例、具体 origin 和权限范围；模板声明本身不能授权 |
| 云元数据、未指定、多播等禁止目标 | 拒绝；普通“允许内网”授权不能放行 |
| 未声明且未授权的目标 | 不发出请求，无论是否携带凭据 |
| 系统代理，包括系统配置的 PAC/绕过规则 | 默认沿用操作系统配置，无须新增确认；不得因本批升级把存量用户统一断网 |
| 插件字段指定的代理 | 使用前由用户确认具体代理端点及实例范围；端点变化后重新确认，插件内容不能自行授权 |

旧的动态目标凭据授权只能继承原有权限，不能自动升级为本机/私网访问许可。现有插件和本地服务升级后的行为须有明确迁移说明；不为恢复旧行为提供总开关绕过全部检查。

### 4.3 本批实现要求

1. 将“是否允许发出请求”和“是否允许携带凭据”分为两个独立检查，所有生产网络请求必须先经过前者；首跳、重定向和链式步骤走同一策略。
2. 规范化 scheme、IDN 主机及端口；动态授权按完整 origin 比较。URL 和 IP 字面量分类覆盖 IPv6 映射、尾点或大小写等变体，不用字符串黑名单替代解析。
3. 集中定义地址分类，覆盖 IPv4/IPv6、本机、私网、链路本地和已知云元数据地址；禁止列表和例外必须有行为测试。
4. 直连请求发送前解析目标主机并检查候选地址；未授权的禁止类别或解析失败则拒绝，不发请求。对含公私地址混合的候选集，必须按请求的已授权范围判定整组候选，不能只挑一个公网结果就放行。每一跳重新做相同预检。
5. 本批继续使用 HTTP 栈自身的解析与连接池，故预检不是连接 IP 绑定。不得把“预检通过”记录成“实际连接地址已经验证”。保留既有连接池参数；权限或路由变更时使相关客户端池/合并请求/缓存失效，禁止新请求继续沿用旧权限。可取消的在途请求应取消或在交付结果前复核，但已经发出的流量不能承诺撤回。
6. 系统代理保持默认可用。界面/诊断区分系统代理、插件显式代理和可确认的直连事实；端点能从可信路由信息得到时展示去除凭据的主机/端口，PAC 或其他路由无法确认实际端点时显示“系统代理，端点未知”，不能把配置值或候选端点冒充本次连接事实。插件显式代理的授权校验在创建/使用其客户端前执行。
7. 代理请求继续检查目标 origin、IP 字面量、重定向和凭据范围；本地能够解析目标时补充地址分类预检。代理负责解析的企业名称不得仅因客户端本地解析失败而断网，此时保留目标授权并明确“最终地址由系统/已授权代理解析，客户端未验证终点 IP”。这类代理流量的最终地址限制属于已登记的残余风险。TLS 校验保持系统信任规则。
8. 目标授权未知或本批必需检查失败时明确拒绝；不能借代理兼容跳过 origin 授权、凭据规则或对已识别禁止地址的拒绝。正常公网直连、系统代理以及经用户授权的本地服务各自做兼容验收。
9. 插件模板新增目标或权限时不得继承旧范围之外的授权；实例删除、目标变更、权限撤销后清理对应授权和相关缓存。

### 4.4 本批验收与能力边界

- 无凭据首跳和带凭据首跳对未声明目标均拒绝，并确认服务端未收到请求。
- 合法公网请求、HTTPS、用户授权的本地测试服务正常工作；HTTP 的许可范围明确，不顺带放宽凭据规则。
- 公网到私网重定向、预检阶段检测到的 DNS 地址变化、混合地址集、IPv4/IPv6 变体、元数据地址、禁止协议、HTTPS 降级均有负例。
- 仅验证地址分类与连接前预检，不将“DNS 检查后实际连接仍不可变”列为本批通过条件。用受控解析器/服务记录该时间差的残余窗口；发布说明不得将 S02a 称为完整 DNS 重绑定防护。
- 企业系统代理、PAC、绕过规则和代理端解析名称维持既有正常联网；不新增统一确认弹窗。未授权插件代理被拒绝，授权后使用正确客户端；未知实际代理端点如实显示。
- 受控连接池场景验证复用连接与请求前预检的区别，记录约 2 分钟池生命周期并不保证本次连接使用新 DNS；权限/路由变更后客户端池和相关缓存失效，后续请求遵守新权限。
- 撤权、实例删除、插件目标范围变化后的请求与缓存行为符合新权限。
- 现有请求时限、响应体大小、并发槽位、取消、重试和凭据不跨域约束继续通过。

“把已验证 IP 绑定到新连接”和更严格的代理终点约束登记为 S02b 后续工作，见独立开放事项登记。S02a 是分阶段风险缓解，不足以关闭完整 SSRF/DNS 重绑定问题。

## 5. S03：持久化卸载恢复

### 5.1 事实与落点

`src/Plugins/PluginMarketUninstallCore.cs` 依次复制 `.uninstall` 备份、删载荷、删安装记录；异常处理可回滚，但强杀后没有持久化的操作身份和阶段信息。插件与主题都使用该核心。

### 5.2 事务合同

1. 扩展既有市场事务基础，使卸载日志能记录操作类型、事务 ID、资产类型、目标文件、旧记录、卸载前是否存在载荷、载荷/备份摘要与阶段。
2. 日志和备份均在受控目录，沿用既有路径防护与事务锁。删除目标文件前，持久化意图和所需恢复数据必须齐备。
3. 固定提交点为“安装记录已持久化移除”。提交点之前恢复旧状态；提交点之后完成清理。不能只凭进程内阶段变量判定提交。
4. 重启恢复先读持久化记录：旧记录仍在且身份匹配时恢复载荷；记录已移除时完成卸载；记录或目标已被其他操作替换时保留证据并报待处理，不盲目覆盖或删除。
   持久化记录不可读取时属于“无法确定”，不能当作记录已删除。恢复失败必须标记待处理，不能作为正常可用安装继续展示。
5. 有效旧文件在恢复中被保留；无法证明身份的孤立 `.uninstall` 文件不能自动恢复。清理失败可以重试，不能伪造“记录与文件一致”。
6. 插件加载和主题发现前完成该目录的恢复对账；沿用已有安装恢复顺序，避免恢复期间另一条安装/卸载进入。
7. 当前主题先切到备用主题仍使用真实应用结果；成功切走后才开始卸载。主题应用与文件事务分别反馈，不把删除成功当作画面切换成功。

### 5.3 验收

- 子进程在意图写入、备份完成、载荷删除、记录提交、清理五个边界被终止；重新启动后状态与合同一致。
- 单列最危险窗口：在 `File.Delete(target)` 已返回、`removeRecord` 尚未执行或尚未持久化时强杀。对于卸载前载荷完整、备份有效的资产，恢复后断言“记录在 ⇒ 载荷在”，且载荷摘要与旧记录/备份匹配；随后重复恢复一次仍成立。
- 卸载前文件已缺失、备份损坏或记录不可读取单独测试：不得伪造载荷或报告恢复成功，只能明确完成可证明的卸载或保留待处理状态。
- 每个恢复场景连续执行两次，结果幂等，无重复删除或重复写回。
- 记录写入失败、文件占用、目录不可写、备份损坏、目标被新文件替换分别验证；异常不能损坏其他资产。
- 插件和主题各覆盖一次完整中断链；既有安装 WAL 和升级恢复回归通过。

## 6. S04：颜色校验与兼容

### 6.1 固定合同

既有 `#RRGGBB`、`#AARRGGBB`、`rgba(r,g,b,a)` 和已知命名色保持原义；alpha 的既有取值约定保持不变。合法透明色是有效输入，解析失败是独立状态。

### 6.2 实现要求

1. 在 `ThemeManager` 附近增加共用 `TryParseColor`，返回成功状态、颜色和诊断；缓存不能把失败与合法透明色混成同一条“成功”记录。
2. 对空值、非法十六进制、未知命名色、越界 rgba、NaN/Infinity 和不支持的简写给出明确失败。命名色检查不能误拒绝合法 `Transparent` 等值。
3. 工作室对已知颜色字段使用同一校验器：指出具体字段与原因，修正前不允许保存/应用/准备有效投稿材料。加载失败文件时保留原内容，允许用户修复。
4. 主题市场共享校验器复用该规则，拒绝已知字段内的坏颜色；不要擅自将未知扩展字段都按颜色解析。
5. 生产加载旧手动主题时不因坏颜色崩溃；使用可定位的失败结果和字段默认值/已知有效主题，不能静默把文字变透明后报告完全成功。
6. 未编辑的合法颜色不强制改写字符串，不改变原始字节摘要；新增 UI 提示明确八位 hex 的 alpha 位置。

### 6.3 验收

- 合法格式的原颜色和 alpha 精确保持，含 `#80FF0000`、合法透明色和不同区域设置下的 rgba。
- 非法四位输入、未知名称、越界和非有限数可定位拒绝；编辑器、市场与运行时对同一输入给出一致结论。
- 坏字段不导致退出，修复后可正常保存和应用；旧主题、GPU 兼容外观及未知扩展字段保留。

## 7. S05：明确阈值来源，消除无效编辑

### 7.1 固定行为

当前着色通过 `MetricUtils.GetThresholds/GetState` 读取生效的设置或既有特殊指标规则；主题决定安全/警告/危险状态对应的颜色。继续沿用该实际行为。

### 7.2 实现要求

1. `ThemePropertyCatalog` 不再将 `Theme.Thresholds` 暴露成能改变当前运行结果的可编辑属性。
2. 工作室增加只读说明：“状态阈值来自当前生效设置；主题负责颜色”，并显示所选普通指标的有效阈值或特殊规则说明。旧主题字段的存在不能被描述为已生效。
3. 保留旧 `thresholds` JSON 字段和读写能力；另存、导出、恢复和应用不能偷偷删除该块或修改用户设置。
4. 预览、主面板、任务栏、GPU 场景沿用统一状态结果；测试比较状态等级，不要求被不同设置控制的表面颜色完全相同。
5. 预览明确读取当前已生效设置；其他设置窗口里尚未应用的阈值草稿不应被说成已生效。生效设置更新后，工作室的说明和预览刷新。
6. 温度、负载、网络/磁盘速度、显存/内存、电池反向阈值与自适应指标沿用各自既有判断及单位；状态着色不顺带修改告警规则。
7. 编辑器针对旧阈值的撤销、重置和属性定位入口同步调整，避免留下仍可写入但无效的隐蔽入口。
8. 增加会话级清理：识别大小写等价的 `thresholds`、其子树及叶字段 overlay，移除尚未提交的阈值覆盖（含删除标记），并让 Draft 的对应内容恢复到当前源文档值。只撤销本次未保存编辑，不删除或重写源文件中已经存在的阈值，也不触碰其他 overlay。
9. 清理在会话接入、恢复快照后、构建保存/另存/导出载荷前复用同一入口；同时清理撤销/重做及快照里的相关变化，修正历史快照中对应阈值，防止 Undo/Redo 或恢复再次带回覆盖。其他字段的历史保持有效；空事务移除，修订号/dirty 状态按实际剩余编辑重算。
10. 用户有旧阈值未保存编辑时提示“该字段仅作保留，不参与着色，已撤销本次阈值修改”。源摘要冲突且恢复副本已失去原字段基线时，不猜测原值或静默清除整个阈值块；保留副本内容并标注来源无法还原，阻止其被描述为已完成阈值恢复。

### 7.3 验收

- 在同一生效设置和采样值下，主面板、任务栏与 GPU 场景状态一致；预览的等价演示值得到同等级。
- 改主题颜色能改变状态配色，换主题不会修改用户阈值或告警设置。
- 生效设置更新、未应用草稿、旧主题带独立阈值三个场景说明准确。
- 原主题阈值字段及未知字段经过保存/导出仍被保留；已停用的编辑入口不再产生“调了却没效果”。
- 构造同时含阈值、配色、布局编辑的会话：清理后阈值回到源值，其他修改保留；撤销/重做及新旧恢复快照不能重新引入阈值 overlay。保存、另存、效果图/投稿载荷都覆盖该场景。
- 源 JSON 原先没有阈值块时，清理不合成新的块；原先存在时保留原字段值与未知子字段。源摘要冲突的恢复副本另测，不能把原值未知算作恢复通过。

## 8. S06：清楚且有界的 GPU 手动恢复

### 8.1 事实与落点

`GpuStartupGuard` 已提供保守状态、原因和 `AllowExplicitManualRetry`；渲染设置页展示状态码，并在开启 GPU 设置时请求重试。这里完善用户可操作性，继续复用既有状态机。

### 8.2 实现要求

1. 将未完成尝试、守卫存储不可用、普通未启用 GPU 等原因分别解释为易懂文案，原原因码保留作排障详情。
2. 保守状态下提供“重试 GPU”操作，复用 `GpuStartupRetryRequested` 和现有应用编排；明确按当前已保存的 GPU/捕获权限执行，不顺带提交无关草稿或开启抓屏。
3. 每次用户操作最多一次尝试；并发点击合并/禁用按钮，状态刷新和 Tick 不自动触发重试。
4. 仅在既有资源清理前置条件满足后开始尝试；存储不可用则说明原因，不直接删标记绕过守卫。
5. 首帧实际呈现才显示“GPU 已恢复”；配置保存、成功创建对象和清除标记都不能代替实际出帧。
6. 尝试失败保持兼容外观，明确反馈失败并允许以后再次手动操作；退出重启后的保护行为保持原合同。
7. 生产守卫与工作室预览守卫的作用域分别说明；重试主面板不能假称已修复独立预览守卫，预览使用自身的同义恢复操作。

### 8.3 验收

- 模拟遗留标记后进入保守状态：用户可看到原因并找到操作，无需猜测开关顺序。
- 清理未完成或存储不可用时拒绝尝试并如实提示。
- 一次点击仅一次尝试；离页、刷新和定时 Tick 不产生新尝试。
- 单独的 GPU 实机验证观察首帧与持续出帧；无 GPU 环境明确未验证，不用回退画面代签。
- 成功、受控失败、保留标记的放弃路径、子进程被终止后的下次启动分别覆盖。
