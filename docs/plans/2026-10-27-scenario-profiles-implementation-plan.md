## 1. 用户目标与首版交互

用户保存“办公”“游戏”“远程桌面”等场景，一次切换主题、显示布局、监控项和刷新偏好。切换前能看差异，切换后能知道哪些已生效；设备或屏幕不存在时不会悄悄绑定另一台。

- 托盘增加场景列表和“管理场景”，设置中提供同一管理入口。
- 支持从当前已提交配置新建、复制、重命名、排序、删除、设为启动请求场景，以及手动应用。
- 应用前按“外观/监控项/任务栏/位置/刷新”展示差异及缺失资源。无需为了看差异修改生产设置或实际切换主题。
- 已生效场景下用户手动改设置后显示“场景名 · 已自定义”，提供保存到场景或另存；不自动覆盖原定义。
- 从当前配置新建时，明确来源是已提交的用户期望配置，列出其中尚未实际应用的字段；不能把它称为“已生效状态快照”。电源策略产生的临时预算不进入定义。
- 首版不做进程扫描、游戏检测、计划切换或 RDP 自动触发。这些以后只作为同一应用服务的请求来源，不另写应用链。

主要接入 [SettingsProjection](../../src/Core/SettingsProjection.cs)、[SettingsChanger](../../src/Core/Actions/SettingsChanger.cs)、[AppActions](../../src/Core/Actions/AppActions.cs)、[ModuleServices](../../src/Core/Actions/Services/ModuleServices.cs)、[SettingsHelper](../../src/Core/SettingsHelper.cs) 及既有窗口位置恢复工具。

## 3. 显式字段范围

场景是受限的字段投影，不是整个 `settings.json` 副本。建立版本化的允许列表及字段到模块映射，新增字段默认不进入场景。

| 首版允许 | 规则 |
|---|---|
| `Skin`、横竖布局、宽度、用户缩放、透明度、置顶 | 主题引用本地文件身份；实际效果仍由运行时确认 |
| 监控项可见性、顺序、名称、显示单位 | 保存稳定设备/传感器映射；保留 null/空字符串的单位语义 |
| 任务栏显示、单双行、字体、间距、颜色 | 通过任务栏模块应用，不修改主题内容 |
| 主窗/任务栏的目标屏幕及位置锚点 | 逻辑尺寸与工作区相对位置，结合屏幕可信身份解析 |
| `RefreshMs`、显示动画偏好 | 用户期望值；不保存省电临时有效频率 |
| 主窗显隐、穿透/自动隐藏等已支持行为 | 继续满足至少有一个可恢复入口的安全可见性规则 |

首版明确排除：Web 监听/认证/信任代理、插件凭据与实例执行参数、凭据目标授权、开机启动、更新策略、磁盘/控制器探测策略、ETW/IP 排除开关、硬件来源切换、GPU 捕获授权和同意标记。

`GpuThemeEffectsEnabled` 等涉及用户启用的能力首版保持当前全局选择；场景可引用 GPU 主题，但不能凭场景定义或导入自动开启捕获/驱动等能力。主题不支持时预检说明兼容外观，而不是隐式授予能力。

## 4. 场景模型与保存

拟新增 `ScenarioProfile`、`ScenarioProfileStore`、字段投影与应用请求模型，放在现有 Core 配置/应用边界内；类型名开工核对。

定义包含：SchemaVersion、稳定 ProfileId、Name、DefinitionRevision、创建/更新时间、受限设置投影、监控项稳定引用及位置锚点。名称只作显示，文件读写使用固定库路径与 ID，不能把名字直接拼成任意路径。

- 建议使用独立 `profiles.json`，首次没有文件代表空库，不改写旧设置；上限 32 个场景、文件 2 MiB，超限拒绝并显示原因。
- 库写入复用原子写盘原则：同目录临时文件、验证、替换和可恢复备份。场景保存失败不破坏原库，不阻塞采样。
- 更新场景使用预期 DefinitionRevision，避免两个窗口或外部编辑互相覆盖；应用使用打开差异页时捕获的定义副本和修订。
- Settings 持久化“请求场景 ID/修订”，实际运行的 EffectiveProfileId/Revision 由模块结果确认。两者不能共用一个声称“已经生效”的标记。
- profile 库与 Settings 不是跨文件原子事务。定义先独立保存，应用时引用固定修订；请求引用不存在时启动报告未解析并保留可用当前配置。
- 未知新字段保留为不生效扩展信息，未知高版本不应用。首版不做场景包联网下载；导入/导出若后续扩展，继续使用相同允许列表。

## 5. 应用状态机与并发

按以下顺序执行：

```text
读取固定场景修订 → 校验/解析设备与主题 → 生成差异
→ 构建候选设置 → 持久化请求 → 按模块应用 → 确认实际结果
```

1. 预检、差异预览和取消不修改实时设置。缺失主题、非法数值等阻止提交；设备暂不可用可以明确保留未解析条目，不自动配到第一块同名设备。
2. 设置页保存和场景应用共用一个应用级串行提交协调点，提交时核对基础设置修订。设置页有未保存草稿时不静默覆盖它：应用后提示重新基于当前配置合并/重载，冲突字段由既有保存流程解决。
3. 用户连点 A/B 时，尚未提交的请求可被明确替代；已开始持久化/应用的请求按序完成并给出结果，不能仅靠取消等待假装运行时动作已撤回。
4. 按差异应用；只改外观不重建硬件，只改刷新间隔通过单飞采样配置路径，不执行硬件全量重扫。
5. 所有必须模块完成且目标主题/布局实际确认后，才显示场景已生效；隐藏窗口等待首帧可以是 Pending，并明确说明。
6. 部分失败显示各模块结果、实际配置和可重试模块。默认不声称全局原子回滚；“恢复切换前配置”是新的受控操作，也有独立结果。
7. 成功、部分成功、恢复、冲突和取消写入诊断事件。事件保存场景 ID/修订及字段名，不包含完整配置或秘密。

## 6. 设备和显示器变化

- 对设备优先采用当前目录提供的稳定身份。只有序号/显示名的旧条目保留低可信说明；换序后不能无条件绑定同名设备。
- 屏幕保存可用的稳定身份、工作区锚点与逻辑偏移；若仅有 `DISPLAYn` 等低可信身份，拓扑变化时按现有可靠恢复策略处理，不把同号显示器当原屏。
- 目标屏幕缺失时回退到当前可用主屏/工作区并钳制可见；报告位置降级，不把此次临时位置写回场景定义。屏幕重新出现后的自动迁回留待后续明确策略。
- DPI、任务栏方向/自动隐藏、RDP 连接恢复沿用已有位置与句柄恢复能力。场景不保存 HWND、物理像素缓存、渲染器状态或设备索引缓存。
- 可见性不变量必须在提交前及实际显示后复核：隐藏主窗、托盘和任务栏不能同时让用户失去入口。

## 8. 验收矩阵

- 场景字段往返保持 null/空值及稳定身份；未列入允许表的任意 Settings 字段不能被注入应用。
- A→B→A，实际主题、布局、任务栏和刷新偏好一致，单纯切换不污染原场景定义。
- 保存失败没有运行时副作用；主题成功但任务栏失败显示部分成功；重试只影响失败模块；恢复失败不宣称已回到 A。
- 设置页草稿存在、外部修改 profiles、同时点击两个场景、Host 重连、应用中退出均有有界结果。
- 设备同名/换序/拔插、屏幕离线、混合 DPI、任务栏方向变化后位置可见且不错误重绑定。
- 场景只改显示项不会触发 Web 重启、插件重新执行、计划任务修改或磁盘/控制器重新打开。
- 手动调整已应用场景会出现“已自定义”；保存与另存不会偷存省电临时频率、口令或捕获授权。
- 开关管理窗口 50 次，无后台队列、事件和资源持续增长；CPU/采样对照记录实际影响。
