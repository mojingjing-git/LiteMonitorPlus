## 2. 本次已落地的部分（与发布策略**无关**，现在就可以生效）

这三项不改变任何信任关系，也不依赖发布侧做什么，因此先行落地。

### 2.1 让失败对用户可见（标记 + 消费）

- **更新器侧**：单参数被拒时，除了写 `update_error.log`，还在**主程序目录旁**写一个机器可读标记
  `update_legacy_bridge.json`（`LiteMonitor.Updater/LegacyBridgeMarker.cs`）。
  内容包含：`schema` / `code` / `reason`（为什么被拒）/ `guidance`（"自动升级通道与当前版本不兼容，请手动下载新版本。"）/ `manualDownloadUrl` / `updaterVersion` / `timestamp`。
  标记里**只有诊断信息与公开的发布页地址**，不含任何私钥材料。
- **主程序侧**：启动时（`UpdateChecker.CheckAsync()` 的**最前面**，排在任何网络请求之前）读取该标记，
  弹窗明确提示"自动升级通道与当前版本不兼容，请手动下载新版本"，并给出原因与发布页地址；
  读完即**消费**（删除标记），因此不会每次启动都重复弹同一件事
  （`src/System/UpdateChecker.cs` 的 `TryConsumeLegacyBridgeNotice` / `ReportLegacyBridgeNoticeIfAny`）。

> 为什么提示由**新**客户端来弹：旧客户端早于本机制，它自己读不了这个标记（也没有"读到就提示"的代码）。
> 标记的价值在于：旧客户端那次静默失败**留在磁盘上**，等用户装上带本机制的新版本时能被明确告知
> "自动升级通道在你这个版本上不可用，请手动下载"，而不是让用户反复重试。

### 2.2 "可信摘要来源"机制骨架（可注入 ⇒ 可测试，默认仍然拒绝）

- 新增 `LiteMonitor.Updater/TrustedDigestSource.cs`：
  - `ITrustedDigestSource`：更新器在"调用方没给摘要"时可以向哪里去取期望摘要；取值语义是 **fail-closed**（拿不到 ⇒ `null`）。
  - `NullTrustedDigestSource`：默认实现，**永远取不到** ⇒ 单参数调用**仍然被拒绝**，现状行为完全不变。
  - `SignedVersionMetadataDigestSource`：**方案 (B) 的骨架** —— 用**与旧客户端同一把**内嵌公钥验签 `version.json`，
    从签名载荷里取 `sha256` 作为期望摘要。`version.json` 的取法是**注入**的（`Func<string?>`），
    生产路径不注入任何实现 ⇒ **默认不联网**。
- `UpdaterRunOptions.TrustedDigestSource` 是装配点；`Program.RunFromArgs` 在单参数分支先问来源，
  拿到合法摘要才继续走 `RunUpdate`（**该摘要仍要过摘要比对**，比对不过照样拒绝）。
- 更新器工程保持**自包含**（不引用主工程）：验签逻辑在更新器侧独立实现一份，
  与主程序的载荷定义/公钥拷贝是否漂移，由测试对拍钉住。

### 2.3 明确**没有**做的事（不得被"顺手放宽"）

- 没有撤销"拒绝无摘要调用"的完整性校验；没有任何"验不过也放行"的分支。
- 默认不联网抓取 `version.json`（是否开启 = 发布策略决策，见第 4 条）。
- 没有改动旧客户端的行为（改不了，也不需要）。

## 3. 桥接方案对比

### 3.1 (A) 过渡发布 + 钉住摘要 —— **原样形态不可实现（自引用循环）**

#### 3.1.1 论证

旧客户端下载的发布包记为 `ZIP`，其内容里包含更新器可执行文件 `U`。
旧客户端的流程是：① 从 `ZIP` 里取出 `U` 覆盖本地更新器（`PreUpdateUpdater`）；② 以单参数启动 `U`，
而 `U` 收到的路径指向的**正是它自己所在的那个 `ZIP`**。

`U` 在解压前必须拿到"期望摘要" `E = H(ZIP)`，才能约束"校验过的字节 == 解压出来的字节"。
旧客户端不会把 `E` 传给 `U`（它只会传路径），于是 `E` 只能由 `U` 自行获得。可能的来源只有三类：

| # | 来源 | 可行性 |
|---|---|---|
| (a) | 命令行参数 | ❌ 旧客户端不传。 |
| (b) | 包内文件（`ZIP` 里带一份"钉住摘要"的清单 `M`，`M` 的内容是 `H(ZIP)`） | ❌ **循环**（见下） |
| (c) | 编进 `U` 自身（把 `H(ZIP)` 编译进更新器二进制） | ❌ **同一循环** |

**(b) 的循环论证**：`ZIP` 由 `M` 与其它条目拼成，因此 `H(ZIP)` 依赖 `M` 的每一个字节；
而 `M` 的内容又必须是 `H(ZIP)`。改 `M` 的任意一位都会改变 `H(ZIP)`，而 `H(ZIP)` 又必须写回 `M` ⇒
必须构造 SHA-256 的**不动点** `M = f(H(⟨M, rest⟩))`。构造这样的不动点等价于求 SHA-256 的原像
（代价 ~2^256 次尝试），**实际不可行**。

**(c) 的循环论证**：`U` 是 `ZIP` 的一个条目。把 `H(ZIP)` 编进 `U` ⇒ 改 `U` 就改 `ZIP` ⇒ 改 `H(ZIP)` ⇒
又得改 `U` ⇒ 回到同一点。

#### 3.1.2 结论

> **任何"把期望摘要钉在包内"的方案都无法自洽。**

补充两点，避免误伤：

- **非循环变体**：如果"钉住摘要"指的是**上一个**发布包的摘要（用来验证"当前已安装的包"），
  那它不循环 —— 但它解决不了本次的问题：本次要校验的是**正在被安装的新包**。
- **(A) 唯一可实现的退化形态**：把 `E` 放到**包外**的可信来源里 ——
  要么是"已验签的 `version.json`"（= 方案 (B)），要么是"人工/旁挂文件"（信任降级到人工，归入 (C) 的范畴）。

⇒ **(A) 与 (B) 不是两个并列的可选项；(A) 在数学上等价于 (B)。**
（若仍想保留"过渡发布"这个说法，可保留一个别名形态 (A′)：过渡包 + **旁挂**签名清单文件，
但它的信任级别与 (B) 相同、且多一份分发物，不推荐。）

#### 3.1.3 (A)/(A′) 的其它属性

- 信任锚：与 (B) 相同（内嵌公钥）或更弱（人工）。
- 需要谁配合：发布侧必须真的签名；客户端侧要装配来源 + 多一个分发物。
- 改动面：比 (B) 多一个"旁挂清单"的下载/校验环节。
- 验证方式：同 (B)，外加"旁挂清单与包的一致性"检查。

### 3.2 (B) 更新器自行用内嵌公钥验签 `version.json` 取得期望摘要

- **做法**：更新器进程自己去取 `version.json`（HTTPS），用**与旧客户端同一把**内嵌公钥验签
  `version\nsha256\nreleaseDate` 载荷，取出 `sha256` 作为期望摘要，再走既有的摘要比对。
- **信任锚**：**编译期内嵌的 ECDSA P-256 公钥**
  （SPKI base64 `MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAElF/yF1mc8EdJOeUhr/u5vxFJQXVm7oI1cEDuugjRmj5vWM9b14bZ5os1OZD9pDm0Gvj8GXevjHnl10G7kMeOuw==`，
  指纹 `25E6659D954A92A9FCCF1E2622F30F68A7FA9C84390B419B33F3EB0F11F97572`，即该 base64 **文本**的 SHA-256）。
  私钥只在发布流程里出现，绝不进版本库。TLS 只保护传输、不产生信任。
- **与旧客户端的信任级别对比**：**完全相同，不削弱**。旧客户端是"主程序进程验签 → 取 sha256"，
  (B) 是"更新器进程验签 → 取 sha256"，信任锚与验签算法都一样，TLS 环节也一样（系统信任链）。
  差别只有"谁去取元数据"。
- **需要谁配合**：
  1. 发布侧**必须真的签名**（`scripts/sign-release.ps1`），且 `version.json` 的 `sha256` 必须与实际发布的包一致
     —— 这正是 S5.1/S5.2 的真实签名绑定；
  2. 客户端侧装配 `SignedVersionMetadataDigestSource`（骨架本次已落地，默认关闭）。
- **改动面**：更新器：1 处装配 + 1 处抓取 + 公钥拷贝一致性守卫；
  发布：签名流水线必须在**每次**发版时强制产出签名（`release.yml` 已有签名与独立复验步骤，
  见 `.github/workflows/release.yml:198-228`）。
- **验证方式**：
  - 单元：自造密钥对、自签自验（本次已落地用例）；
  - 跨实现对拍：更新器的载荷/公钥与主程序逐字节一致（本次已落地用例）；
  - 端到端：真实旧版本安装包 + 真实签名发布（**需要真实环境，当前 NOT_VERIFIED**）。
- **已知局限（必须写进发布决策）**：更新器抓到的 `version.json` 必须与客户端**实际下载的那个包**对应。
  若在"下载完成 → 启动更新器"之间发布了新版本，摘要会不匹配 ⇒ 仍然拒绝（fail-closed），
  用户重试即可（重新下载最新包）。这不是漏洞，但会造成"偶尔失败一次"的现象。

### 3.3 (C) 仅支持手动升级

- **做法**：不修旧客户端的自动通道；对旧版本明确提示"自动升级通道与当前版本不兼容，请手动下载新版本"，
  由用户从发布页手工下载安装包。
- **信任锚**：**没有新的信任锚**（不引入任何新的自动信任路径）。
- **与旧客户端的信任级别对比**：**对旧客户端是降级的** ——
  旧客户端的自动通道本来是"验签 `version.json` + 摘要绑定"（最强），
  走 (C) 后旧客户端只能靠浏览器 HTTPS 下载，**应用本身不再对该包做任何验签/摘要绑定**
  （与 `UpdateChecker.ReleasePageUrl` 注释里写的代价一致："该包不经过签名核验（见 W1.2）"）。
  对**新客户端无影响**：新客户端的"验签 → 摘要比对 → 钉住句柄交接 → 更新器重算比对"链路保持不变。
- **需要谁配合**：发布页提供可直接下载的包 + 发布说明写明"旧版本请手动下载"。
- **改动面**：客户端：本次已落地的标记与提示（已完成）；发布：无流程改动。
- **验证方式**：手工升级演练（旧版本安装包 → 提示 → 手工下载 → 安装）。

### 3.4 对比总表

| 维度 | (A) 过渡发布 + 钉住摘要 | (B) 更新器自行验签 `version.json` | (C) 仅支持手动升级 |
|---|---|---|---|
| 可实现性 | ❌ 原样形态**自引用循环，不可实现**；退化形态 = (B) | ✅ 骨架已落地（默认关闭） | ✅ 提示已落地 |

| 与旧客户端的信任级别对比 | 等价于 (B) | **相同，不削弱** | **对旧客户端降级**（不再验签/绑定摘要） |

## 4. 推荐

**推荐：立即按 (C) 发布；(B) 留作中期方案，等签名流水线强制化之后再按开关开启；(A) 判定为不可实现。**

理由：

1. **(C) 立刻消除"静默失败"**，而这正是本次缺陷的核心症状。本次落地的标记 + 提示已经把
   "应用自己关掉、什么都没有"变成"明确告诉你自动升级通道不可用、请手动下载"。
2. **(C) 不引入任何新的信任路径**，零完整性风险；而 (B) 会把"信任锚"从主程序进程搬到更新器进程，
   并**依赖发布侧每次都真的签名**。在 S5.1/S5.2 的真实签名流水线落地并被 CI 强制之前开启 (B)，
   一旦某次发版忘了签名，受影响的是**全体用户**（"更新源不可信" ⇒ 永远升级不了）。
3. **(B) 的机制骨架本次已经落地且默认关闭**（`ITrustedDigestSource` /
   `SignedVersionMetadataDigestSource` / `UpdaterRunOptions.TrustedDigestSource`），
   决策可以推迟到"签名流水线是否可靠"这个问题有答案之后，**不需要再改一次更新器**。
4. **(A) 不推荐**：自引用循环不可实现（§3.1），继续在它上面投入没有产出。

**如果主人选择 (B)**，开启方式与必须同时满足的条件：

- 在更新器的生产入口装配来源（`new SignedVersionMetadataDigestSource(fetchVersionJson)`，
  `fetchVersionJson` 走 HTTPS + 同样的字节/期限上限）；
- 更新器内置的公钥与主程序内置的公钥**逐字节一致**（本次已用两条对拍用例钉住，换任一份都会红）；
- 发布侧每次发版都产出真实签名，且 CI 独立复验通过（`release.yml` 已有该步骤）。

## 5. 发布流程影响

- **本次改动本身**：发布侧**无需任何改动**；默认行为与改动前完全一致（单参数调用仍被拒绝、退出码仍为 `6`）。
- **按 (C) 发布**：发布页需要提供可直接下载的包；发布说明写明"旧版本请手动下载新版本"。
  建议在过渡期同时**保留**旧版本可下载，避免旧用户被卡住。
- **按 (B) 发布**：每次发版必须真签名（`scripts/sign-release.ps1`），且 `version.json` 的 `sha256`
  必须与实际发布包一致；`release.yml` 已有"生成签名后的 `version.json`"与"独立复验签名"两步，
  但**是否强制**（失败即中止发布）需要在发布策略里明确。
- **回滚**：标记是"一次性状态文件"，读后即删；回滚到旧版本后若再次触发旧客户端路径，标记会重新写出，
  不存在"标记残留导致误报"的情况（更新成功时更新器会主动清掉过期标记）。
