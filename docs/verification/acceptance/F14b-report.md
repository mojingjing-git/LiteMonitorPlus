## 2. 关键设计：为什么控件必须自己申明语义

`SettingsThemeApplier.Remap` 是「按色值反查语义槽位」的兜底路径。它有一个**结构性缺陷**：

> 只要同一套配色里有两个槽位取了相同 ARGB，该色就会一律命中槽位数组里**排在最前**的那一个。

修复前，浅色下 `CardBg` / `SurfaceBg` / `InputBg` / `MenuBg` / `PreviewBg` **全部是 `Color.White`**，深色下 `CardBg` = `MenuBg`、`SurfaceBg` = `GroupHeader`。结果是：切到深色时输入框被刷成卡片色（反之亦然），且**只在反方向切换时才暴露**，手工观感检查极难发现。

**修法（根因，非补丁）**：给容器类与正文字类的槽位各差 1–2 级。

| 槽位 | 浅色原值 → 现值 | 深色原值 → 现值 |
|---|---|---|
| `CardBg` | White → **255**（不变） | 37,37,38 → 不变 |
| `SurfaceBg` | White → **252** | 45,45,48 → 不变 |
| `InputBg` | White → **249** | 28,28,30 → 不变 |
| `MenuBg` | White → **254** | 37,37,38 → **39,39,41** |
| `PreviewBg` | 249 → **246** | 24,24,24 → **26,26,26** |
| `GroupHeader` | 248,249,250 → 不变 | 45,45,48 → **47,47,50** |
| `TextMain` | 32 → 不变 | 230 → 不变 |
| `InputText` | 32 → **34** | 230 → **232** |
| `MenuText` | 32 → **36** | 230 → **234** |
| `TextDisabled` | 150 → 不变 | **120 → 168** |

亮度影响：浅色侧 0.913~1.000（肉眼无法分辨），配色观感不变。

> **为什么不是"调 `Remap` 数组顺序"**：那只是把串味对象从 A 换成 B，换个槽位继续串。真正的修复是让槽位两两可辨。

**豁免的同值（有意复用，非缺陷）**：`Primary` = `InputLineFocused`（聚焦描边就该用主色）、`CardBg` = `MenuSelectedText`（一底一字，都是白）、`SidebarBg` = `Separator`（同为分隔灰）。它们即便被 `Remap` 命中，语义也落在同一处。豁免理由已写进测试注释。

## 3. 收尾期修正的三类失败（执行体中断，协调者接手）

F14b 执行体在「值重映射歧义」修复途中中断，工作树留有 2 个编译错误与 3 条失败。接手后逐一定位并修复：

### 3.1 编译错误 CS0103 —— `_explicitColor` 字段声明丢失（2 处）

`LiteUnderlineInput` 的 `ApplyTheme()` 引用了 `_explicitColor`，但字段声明没写进类（执行体那次编辑只改了一半）。

补上声明，并在构造函数保存 `fontColor`：调用方显式指定的字色（阈值输入框的告警色/危险色）**优先于主题色** —— 否则切到深色时告警色会被主题覆盖掉。

### 3.2 `TextDisabled` 深色太暗，读不清

测试门槛是**相对亮度 ≥ 0.35**。原值 `FromArgb(120,120,125)` 的亮度只有 **0.1891**，在深底（#252526）上几乎糊进背景。

```
120 → lum 0.1891   ✗
155 → lum 0.3295   ✗
160 → lum 0.3533   （TextSub 已在此，禁用文字不能跟它一样亮）
168 → lum 0.3935   ✓
```

取 **168,168,173**：亮度达标，且比 `Hint`(170) 略暗、比 `TextSub`(160) 略亮，层级不撞。注释写明理由：**禁用态要传达"不可操作"，而非"不存在"** —— 用户得先看见它，才知道它不可点。

### 3.3 测试自身前提写反

`控件树切到深色后不再残留浅色的白底黑字` 中，刚 `PushToUIColors(Light)` 就断言 `HasLightArtifact(host, darkExpected: true)` 为假 —— 浅色下判"应为深色"必然残留，与实现无关。

按执行体原意修正：先 `Apply(host)` 让控件按当前（浅色）配色取一次色，再断言 `darkExpected: false`（此时不该有深色残留）。

## 4. 新增护栏：槽位两两不同

新增用例 `同一套配色内没有两个槽位取相同色值_否则重映射必然串味`，只校验**真会串味**的两类（容器底色 / 正文字色），深浅两套各验一遍。

这条护栏的价值：它把上面 §2 的**根因**钉成不可回退的不变量。以后任何人把两个容器槽位调成同值，这里立刻红 —— 而这类缺陷在手工观感检查中几乎不可见。

**该护栏在收尾期又抓出 5 组我原先没预想到的同值冲突**（`TextMain=InputText=MenuText`、`InputBg=PreviewBg`、`SidebarBg=PreviewBg` 等），说明它的覆盖面比人工枚举更完整。
