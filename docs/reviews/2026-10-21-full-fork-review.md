## F1 · P1：覆盖失败的当前文件没有进入回滚清单

位置：[更新器 Program.cs](../../LiteMonitor.Updater/Program.cs#L148)，第 148–163 行。

`replaced.Add(...)` 发生在覆盖、长度校验、二进制摘要校验全部成功之后。如果 `File.Copy` 已改动目标的一部分再抛出 I/O 异常，或复制后的校验失败，当前目标文件已经被改动，却还没有登记进 `replaced`。异常处理只回滚这个清单，漏掉的恰好就是失败文件；原文件即使已经备份，也不会被恢复。失败涉及主程序或 DLL 时，安装目录可能无法启动或混用两个版本。

**已做故障注入复现。** 隔离工程直接链接未修改的生产更新器源码，只为 `File.Copy` 注入“目标写入 PARTIAL 后抛 IOException”，同时用不执行系统操作的替身替代进程枚举、启动及等待。结果：退出码 5；复制重试 10 次；备份仍为 `ORIGINAL-CONTENT`；目标仍为 `PARTIAL`；`originalRestored=false`。见 [原始结果](evidence/full-fork-20261021/updater-fault-results.json)。这不是物理磁盘故障实测。

建议在第一次修改目标前登记恢复信息，并使异常、校验失败、部分写入都经过同一恢复流程；更稳妥的是把新文件写入同目录暂存文件、校验后原子替换。回滚应返回实际恢复结果，不应在恢复失败后仍统一记录“已回滚到原版本”。新增回归应覆盖当前文件部分覆盖、覆盖后校验失败和恢复失败。

关联检查：未提交的 [MainFormBizHelper.cs](../../src/UI/Helpers/MainFormBizHelper.cs#L423) 对 `update_in_progress` 提示“程序未被替换”，也不能成立：标记在开始替换前写入，中断可能发生在任意文件替换之后。提示应保留“可能部分更新”的事实和备份位置。

## F2 · P2：卸载重新信任安装记录中的 id，能越界删除 JSON 文件

位置：[PluginMarket.cs](../../src/Plugins/PluginMarket.cs#L346)，第 346–361 行。

安装时会严格验证 id，卸载时却只验证 `record.File == record.Id + ".json"`，没有重新验证 `record.Id` 的字符集，也没有检查最终路径是否仍在 `PluginsDir` 下。如果记录损坏或被篡改为 `Id="../../review-victim"`、`File="../../review-victim.json"`，这个相等性检查仍然通过，后面的 `Path.Combine` 和 `File.Delete` 会越出插件目录。

**已调用生产 `Uninstall` 复现。** 在隔离输出目录放置测试 JSON，注入上述安装记录后，函数返回 true，插件目录外的测试文件被删除。见 [运行期结果](evidence/full-fork-20261021/runtime-repros-results.json)。影响范围是可访问的 JSON 文件；正常安装流程不会自行生成这种 id，此问题依赖损坏或被篡改的记录。

建议在卸载入口对条目和持久化记录都执行与安装等价的 id 校验，并对规范化后的完整路径做目录边界检查；拒绝损坏记录而不删除文件。新增回归应同时篡改 id 和 file，并断言目录外文件完整保留。

## F3 · P2：HTTP 授予租期与 Stop 不互斥，停止后硬件需求可永久停在 true

位置：[WebSessionManager.cs](../../src/System/WebServer/WebSessionManager.cs#L755)，第 755–758 行。

HTTP 请求先比较 `connectionGeneration`，随后才执行 `GrantHttpLease()`，两步没有与 `Stop()` 共用 `_clientsGate`。如果请求通过比较后暂停，`Stop()` 可以先清空需求并停止需求监视；恢复的旧请求随后又授予租期并通知同步器，将硬件端需求置为 true。租期到期后，已经停止的同步器不再负责把 false 传回硬件层，硬件侧会继续按 Web 的 1 秒采样周期运行。

**已用生产组件和同步点复现。** 通过反射取得需求锁，让请求在代次比较后等待；控制线程执行 Stop 后再放行请求。可控时钟推进 3 秒后，Web 租期已失效，而硬件端最后应用的需求仍然为 true：`demandAfterLeaseExpiry=false`、`hardwareDemandAfterLeaseExpiry=true`。见 [运行期结果](evidence/full-fork-20261021/runtime-repros-results.json)。

建议把“服务仍运行、代次仍一致、授予租期”放进与 Stop 相同的临界区，通知继续放在锁外；也应防止已停止的同步器被晚到通知重新应用 true。新增回归应把同步点放在代次比较与授予租期之间，而不仅仅在读请求头之前暂停。

## F4 · P2：没有新捕获帧时，每次重绘都会丢掉仍有效的玻璃背景

位置：[LiveGlassController.cs](../../src/UI/LiveGlassController.cs#L382)，第 382–390 行。

`BeginPaint()` 无条件先释放上一张租约，再尝试接管 pending 帧。实时捕获默认每秒 2 帧，界面允许更高刷新率，也可能因拖动、遮挡恢复等额外重绘。当下一张捕获帧尚未到来，第二次重绘会把有效帧释放掉，`TryGetFrame` 返回 false，背景退回静态降级层。结果是玻璃与底色交替出现。

**已用合成位图复现。** 生产捕获服务仅发布一张 8×8 合成帧，连续调用生产控制器的 `BeginPaint()` 两次，得到 `firstPaintHasFrame=true`、`secondPaintHasFrame=false`。未显示窗口，也未捕获桌面。见 [运行期结果](evidence/full-fork-20261021/runtime-repros-results.json)。

建议在没有替代帧时保留仍有效的当前租约；拿到新租约后再交接释放旧租约。主题、句柄、几何变化导致旧租约失效时，仍应正常降级。新增回归应覆盖“连续多次绘制、期间没有新捕获帧”，而不只验证首次接管和释放。

## F5 · P2：移动主窗口没有更新玻璃捕获的屏幕坐标

位置：[MainForm_Transparent.cs](../../src/UI/MainForm_Transparent.cs#L246)，第 246–268 行；[LiveGlassController.cs](../../src/UI/LiveGlassController.cs#L273)，第 273–289 行。

生产接线只在尺寸、DPI、句柄或主题变化时刷新捕获请求，没有处理 `LocationChanged` 或 `Move`。拖动只修改窗口 `Location`，同一显示器内移动通常不触发 Resize 或 DPI 变化。捕获请求保存的却是绝对屏幕矩形，后端继续使用旧的 `PhysicalClientBounds`，所以会把原位置的桌面内容画到新位置窗口里；靠边移动也会遇到这个问题。

这是已核对完整调用链的源码问题，本轮没有做桌面抓屏实测。后端映射见 [BackdropCaptureAdapters.cs](../../src/System/Backdrop/BackdropCaptureAdapters.cs#L267)，实际抓屏使用传入矩形，未自行重新定位窗口。

建议把位置变化纳入几何请求刷新，并推进几何代次以拒绝移动前在途帧。新增回归应在尺寸、DPI 不变时移动窗口，断言后端收到新的屏幕矩形且旧位置帧不再可用。

## F6 · P2：自启迁移未核对任务归属就删除原版计划任务

位置：[AutoStart.cs](../../src/System/AutoStart.cs#L30)，第 30–37 行；调用点第 68 行。

首次启用 LiteMonitor++ 自启时，代码直接删除名为 `LiteMonitor_AutoStart` 的任务，没有先检查它的实际启动路径。如果用户在另一个目录保留并使用原版 LiteMonitor，该任务属于另一个安装实例，启用派生版自启就会把原版的自启关闭。当前对新品牌任务已经有启动路径比对，但旧任务清理没有相同的归属保护。

这是源码确认的条件性兼容问题；本轮没有创建、删除或修改用户机器上的计划任务。

建议读取旧任务 XML，仅在启动目标能确认属于本次迁移实例时清理；原版独立安装的任务应保留。新任务还应在创建并核验成功后再清理可迁移的旧任务。回归可使用进程调用替身，分别提供当前安装与另一目录安装的任务 XML，检查只清理前者。
