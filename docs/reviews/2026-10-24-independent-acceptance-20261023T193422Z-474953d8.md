## 5. 新发现

### P3-01　门禁的「期望程序集」断言是单向的，期望清单可被静默削窄

- **触发条件**：把 `EXPECTED_TEST_ASSEMBLIES` 的值改成少一个程序集，而该程序集的 TRX 仍在结果目录里。
- **最小复现**（验收者独立复验，非仅采信执行者报告）：

  ```powershell
  pwsh -File .github/workflows/assert-test-counts.ps1 `
    -TrxRoot <本次 Debug 结果目录> -MinTotal 1831 `
    -ExpectedAssembly 'LiteMonitor.Tests, LiteMonitor.Updater.Tests' `
    -MaxSkipped 1 -MustExecuteTestClass MarketIndexContractTests -MustExecuteTestClassMinCount 6
  # 实际退出码 = 0，门禁输出「=== 测试发现数校验：通过 ===」
  ```

- **期望**：出现未在期望清单中的程序集时应当判红（否则清单可被削窄而不被发现）。
- **实际**：退出码 0，**门禁放行**。
- **生产位置**：`.github/workflows/assert-test-counts.ps1:372-377`——只断言「期望 ⊆ 实际」，没有反向断言「实际 ⊆ 期望」。

  ```powershell
  foreach ($want in $expectedNames) {
      $hit = $selected | Where-Object { $_.Assembly -ieq $want } | Select-Object -First 1
      if ($null -eq $hit) { $problems.Add("缺少测试程序集 '$want' ...") }
  }
  ```

- **影响与定级**：**P3**。实际暴露面窄——真把某程序集的 TRX 拿掉时，总数阈值仍会拦住（已复现：移除 `LiteMonitor.GpuNonperformance.Tests` 的 19 条后，合计 1812 < 1831，退出码 1 变红）。所以这不是「假绿」漏洞，而是**一道可被静默削窄的冗余防线**：它只保护「清单与实际程序集集合一致」这一条性质。
- **归属**：**本批新引入的修改范围相关**。本批交付清单包含 `assert-test-counts.ps1`（修改），但该次修改**没有**补上反向断言。
- **证据**：`E:\litemonitor-acceptance\acceptance-20261023T193422Z-474953d8\gate-mutation\gate-mutation.json`、同目录 `logs\M3*.log`；验收者独立复验产物 `run\m3-verify\`。
- **建议修复**（不在本次验收范围，未修改候选代码）：在断言循环后追加反向检查——`foreach ($r in $selected) { if ($r.Assembly -notin $expectedNames) { $problems.Add("出现了未在期望清单中的测试程序集 '$($r.Assembly)' —— 期望清单可能被削窄") } }`。

### P3-02　更新器的三种产物形态并存，csproj 与打包脚本口径不一致

- **事实**：同一个 `LiteMonitor.Updater` 项目当前存在三种互不相同的产物形态：

  | 产物 | 大小 | 取得方式 | 独立可运行 | 会进发布包？ |
  | --- | ---: | --- | :-: | :-: |
  | `bin\<config>\net8.0-windows\win-x64\LiteMonitor++.Updater.exe` | 9,644,544 B | `dotnet build`（A01 的解决方案构建产物） | **否**——单独拷到空目录 `--selfcheck` 失败，退出码 `0x80070002`（`The application to execute does not exist: 'LiteMonitor++.Updater.dll'`），必须与同目录 186 个松散运行时文件共存 | 否 |
  | `dist-updater\LiteMonitor++.Updater.exe` | 192,050 B | `dotnet publish -r win-x64 --self-contained false` | 是 | **是**（`scripts/pack-release.ps1:124-125` 正是此参数，并刷新 `resources\LiteMonitor++.Updater.exe`） |
  | `dist-updater-selfcontained\LiteMonitor++.Updater.exe` | 67,540,120 B | `dotnet publish`（csproj 默认 `SelfContained=true` + `PublishSingleFile=true`） | 是 | 否 |

- **根因**：`LiteMonitor.Updater.csproj` 写死 `SelfContained=true`，而打包脚本用 CLI `--self-contained false` 覆盖它。两者产出**完全不同**的二进制（192 KB vs 67.5 MB），中间还夹着一个 9.6 MB 的 build 输出。
- **影响**：**当前不构成缺陷**——真正随包分发的 192 KB 框架依赖单文件版已在本报告中验明（9/9 用例通过），且两种 publish 形态行为完全一致。但存在两个隐患：① 任何人误把 `bin\...\win-x64\` 下那个 9.6 MB 文件当作发布产物发出去，它在缺少 186 个伴随运行时文件时会直接启动失败；② 旧随包二进制 185,906 B 与新发布产物 192,050 B 的尺寸差异，本质就是「构建口径不一致」的历史沉淀，也是旧二进制无法自证一致的原因之一。
- **建议修复**（不在本次验收范围，未修改候选代码）：在 csproj 中用条件区分（例如 `<SelfContained Condition="'$(RuntimeIdentifier)'!=''">false</SelfContained>` 或引入 `PublishSelfContained` 开关），使 csproj 默认口径与 `pack-release.ps1` 一致；并在打包脚本中加入断言——发布产物的 SHA-256 必须等于写入 `resources\LiteMonitor++.Updater.exe` 的字节。

### 11.2 缺陷 P1-01：实时玻璃的捕获服务在窗口句柄重建后被整停，且没有任何恢复路径

- **现象**：用户侧「三个液态玻璃全是假的」。全新配置下三开关默认全关时，主题按合同降级为渐变（这本身是设计行为）；但**即使显式打开「实时玻璃」，真实程序里玻璃也从不生效**。
- **黑盒证据**（候选 Release 实机，修复前）：

  | 观测项 | 实测值 | 含义 |
  | --- | --- | --- |
  | `liveglass.log` 的 `StartService` 行 | 1 行 | 服务启动过 |
  | `liveglass.log` 的 `状态=… 生效模式=…` 行 | **0 行** | 绘制路径从未交接帧 ⇒ 从未确认生效 |
  | 窗口显示亲和性（40 ms 轮询 12 s，覆盖 2 fps 抓屏节奏） | **恒为 `0x0`** | 抓屏引擎**一张帧都没抓过**（抓屏期间会瞬时置 `0x11`） |
  | 同一进程内主窗口句柄 | `1057400` → `2950984` | 窗口句柄在运行中被重建 |
  | 捕获请求 vs 实际窗口 | 日志 `句柄=2885448 / {320,360,420×236}` vs 实际 `(1924,121) 240×767` | 服务绑定的是**构造期的临时句柄与临时矩形** |

- **单元测试为什么每次都过**：同一代码路径在单元测试里每次都写出 `状态=Running 生效模式=Glass 后端就绪=True 已发布帧=1`——因为测试直接构造 `MainForm` 并驱动绘制，**窗口句柄从不被替换**。这是典型的「单测全绿 / 实机全废」形态：**缺陷藏在窗口句柄重建这一实机事件上，而单测根本不产生该事件**。
- **根因（三段代码）**：

  1. `src/UI/MainForm_Transparent.cs:521` `OnHandleDestroyed` → `_ui.StopLiveGlassForHandleRecreate()` → `LiveGlassController.StopService()` → **`_service = null`**（注释写明「句柄重建后由 UIController 按配置恢复」）。
  2. `src/UI/LiveGlassController.cs:463-466` `RefreshRequest()` 首行 `if (svc is null) return;` —— **服务已被整停时直接返回，不重启**。
  3. 唯一能重启服务的 `RestoreIfEnabled()` 只在**两处**被调用：`LiveGlassController.HandleRecreateFailed()` 与 `UIController.cs:1736-1739`（**GPU 受控重建**的收尾步）。**纯 legacy 渲染路径上没有任何地方调用它**——注释承诺的「重建完成后自动恢复」在实机上并不存在。

  于是 `BeginPaint()` 首行 `if (svc is null) { ReleaseHeldFrame(); return; }` 永远命中 → 从不取帧 → `BackdropModeResolver` 永远走「降级 1：glass → gradient」→ **背景恒为静态渐变，即用户看到的假玻璃**，且**全程零报错**。

  值得记录的是，`RefreshRequest()` 上方那段 A16 复核注释**已经把同一缺陷描述出来了**（「服务永远不抓屏，玻璃永远不生效，且没有任何报错」），但当时只修了「服务**存在**但没启动」这一半，**没修「服务**已经不在**」这一半**。
- **定级**：**P1**。功能在真实程序里 100% 失效且静默——日志无错误、UI 无提示、单测全绿。
- **归属**：`src/UI/LiveGlassController.cs` 与 `src/UI/MainForm_Transparent.cs` **不在**本批 31 文件交付清单内（属既有代码）；本批验收范围也不覆盖「实机窗口句柄重建」这一路径，所以没被测出来。

### 11.3 修复

单点修复，落在 `src/UI/LiveGlassController.cs` 的 `RefreshRequest()`：

if (svc is null)

    //   ⇒ StopForHandleRecreate ⇒ StopService ⇒ _service = null），这里**不能**直接返回。
