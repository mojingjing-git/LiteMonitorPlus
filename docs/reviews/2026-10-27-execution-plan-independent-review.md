## 1. 审核结论

**裁决：不通过（不建议签署 G0 门禁；须完成 Must-fix before G0 整改后重新提审）。**

### 核心阻断原因（3 项 P0，4 项 P1）
1. **[P0] 命名空间灾难性碰撞**：计划将基础与合同任务命名为 `F00–F10`，与既有评审及修复计划确认的 11 项缺陷（`F01–F11`）完全同名同域，导致 WBS 依赖、日历说明、D0 决策和门禁签收产生严重歧义（如“签收 F03”到底是签收 GPU 门禁还是签收 C2 事件合同；“R3 依赖 F02/F06”是依赖缺陷还是依赖 E03 接线），依赖拓扑解析在工程上不可行。
2. **[P0] 发布切片与门禁体系严重倒挂**：计划声称拆分成 3 个独立发布切片（Slice 1 修复、Slice 2 诊断+趋势、Slice 3 场景+低功耗），但在门禁定义中，Slice 2 的出口门禁 G3 却强行捆绑了属于 Slice 3 的场景核心串行应用（S03–S04）与低功耗调度接线（P03）。一旦场景或低功耗受阻，Slice 2 无法发布，切片独立发布承诺彻底破产。
3. **[P0] 关键路径倒置与伪前置依赖**：§0 关键路径将真实 GPU 200 次循环与资源终验（R5）作为启动 D/T/S/P 开发的前置依赖，导致 Slice 1 的实机门禁阻塞新功能全部开发，且与 §8.1 波次表（W1 即并行启动 D01/T01/S01/P01）产生根本性矛盾，极大地放大了无 GPU 机器时的停摆风险。
4. **[P1] 单一写入者纪律在 WBS 中自我违背**：文件所有权表规定 `Settings.cs` 唯一写入者为 A，但任务 F08（开关与迁移）却指派给 B；且 B 负责的告警与省电均需直接在 `Settings.cs` 扩充字段；UI 壳文件 `UIController.cs` 出现 A/B 双写入者。
5. **[P1] 本地化 C4 合同与现有代码脱节**：现有 `LanguageManager.cs` 根本没有向 `en.json` 自动回退的运行时逻辑（查不到 key 时直接返回截断 key 字符串），计划允许 7 国语言缺失回退英文，若无底层代码改造，非中英文界面将大面积出现乱码和 raw key。
6. **[P1] 设置模型缺少 `[JsonExtensionData]` 导致降级破坏**：`Settings.cs` 未实现扩展属性字典，旧版本反序列化虽可忽略未知新字段，但旧版本任意一次写入都会永久删除新字段，使计划声称的“降级不删除新字段”成为伪命题。
7. **[P1] 采样需求合同 C3 语义畸形**：计划试图在现有的 5-布尔全局聚合模型 `SamplingDemand` 上硬塞单值 `MaxIntervalMs`，与 E02 引入的 `OpSubmitDemandV2` 按消费者独立提交需求及源计划模型冲突。

## 3. 详细发现清单（P0 / P1 / P2）

### 3.1 P0 级发现（阻断 G0 门禁会签，必须立即整改）

#### [P0-1] 双重任务编号体系严重碰撞，导致依赖图与门禁语义产生致命二义性
- **位置**：§0 表、§1.4 表、§3.2 D0-6、§4.1、§6.1 表、§7.1 表、§7.2 表、§16.1 Mermaid 图。
- **证据**：
  1. §7.1 表将 11 个基础/合同工作包依次编为 `F00` 到 `F10`（代表 Foundation）。
  2. 原审查报告 `docs/reviews/2026-10-27-all-recent-changes-review.md` 与修复计划 `docs/plans/2026-10-27-p1-p2-remediation-plan.md` 已将待修复的 11 项缺陷固定命名为 `F01` 到 `F11`（代表 Findings）。
  3. 执行计划全篇混用两套体系，造成灾难性歧义：
     - §0 第 17 行：“`R0–R5，F01–F11`”（此处的 F 指缺陷）；
     - §3.2 表 3.2 D0-6：“`无 GPU 不签收 F03`”（此处 F03 指 GPU 门禁缺陷，但 §7.1 中 F03 为 C2 事件合同）；
     - §7.2 R3 依赖 “`F02/F06`”（实际上是指基础任务 F02 C1合同与 F06 E03接线，但字面完全被理解为缺陷 F02 与 F06）；
     - §7.6 P01 依赖 “`F07`”（此处指基础任务 F07 生命周期收口，而 R1 交付中也有 F07 最小化停帧）；
     - §6.1 G1 必须通过：“`R1–R5；F01–F11 全部关闭；F06/F07 完成`”（一句话内同一个前缀指代两种截然不同的实体）；
     - §4.1 第 125 行：“`集成：F00、F10`”（此处 F10 指协作规则），而 §7.2 R4 交付的是“`F10 凭据头`”。
- **影响**：破坏了工作分解结构（WBS）的唯一标识原则，导致任务指派、依赖解析、工单系统、CI 判定和门禁验收发生严重错乱，执行人员与自动化工具无法明确当前操作的是缺陷还是基础库任务。
- **具体修法**：
  - 彻底隔离两套编号命名空间：
    - 将 §7.1 基础任务统一重命名为 `INF-00`～`INF-10`（Infrastructure）或 `B00`～`B10`（Base）。
    - 将既有缺陷统一命名为 `BUG-F01`～`BUG-F11`。
  - 同步更新 §0、§1.4、§3.2、§6.1、§7.2、§7.5、§7.6 及 §16.1 的所有 `depends` 引用。

#### [P0-2] 发布切片与门禁依赖严重倒挂，切片 2（Slice 2）被切片 3（Slice 3）的任务强行阻断
- **位置**：§0 表（第 15–20 行）、§6.1 门禁表（G2、G3 行）、§7.5 表、§7.6 表、§11.1 表。
- **证据**：
  1. §0 表及 §11.1 表明确承诺“三个独立可发布切片”：
     - Slice 1：修复（R0–R5，出口 G1）；
     - Slice 2：诊断 + 趋势告警（D01–D06、T01–T07，出口 G3）；
     - Slice 3：场景 + 低功耗（S01–S06、P01–P07，出口 G5）。
  2. 但在 §6.1 门禁定义中：
     - G2 必须通过：“D01–D04、T01–T03、**S01–S02、P01–P02**”；
     - G3（Slice 2 出口）必须通过：“D05–D06、T04–T06、**S03–S04、P03**”。
  3. S01–S04（场景配置全流程与串行应用）和 P01–P03（低功耗显示与 GPU 调度）完全属于 Slice 3 的范围，却被作为 G2 和 G3 的强制阻塞性通过条件。
- **影响**：切片独立发布的架构设计破产。如果开发 A 在场景应用（S04）或 GPU 调度接线（P03）上发生延期，即使诊断中心（D）和趋势告警（T）已全部就绪并通过验证，Slice 2 依然被阻断而无法发布，功能被重新拉回“大爆炸式捆绑发布”。
- **具体修法**：
  - 解耦 Gate 与发布切片：G2/G3 的通过条件中剔除所有 S（场景）与 P（低功耗）任务。
  - G2 修正为“只读诊断与趋势原型门禁”，范围严格限定为 D01–D04 + T01–T03。
  - G3 修正为“Slice 2 发布门禁”，范围严格限定为 D05–D06 + T04–T07 + L01（D/T 专项）。
  - 将 S01–S06 与 P01–P07 独立归入 Slice 3 门禁 G4 与 G5 中考核。

#### [P0-3] 关键路径倒置，R5（实机终验）被错误置于 D/T/S/P 开发之前
- **位置**：§0 关键路径（第 23–30 行）、§6.2 建议日历、§8.1 波次表（第 312–320 行）。
- **证据**：
  1. §0 关键路径图写明：
     `... → R1 → R2/R3 → R5 → G1 → D01–D04 + T01–T03 + S01–S02 + P01–P02 → G2`
     明确将 R5 作为启动 D01–D04、T01–T03 开发的硬性串行前置。
  2. §6.2 建议日历同样规定：W1–W4 仅做接口/纯逻辑，W5 跑 R5，W6–W9 才正式推进 D01–D04。
  3. 但在 §8.1 表 8.1 中，波次 W1（硬前置仅 G0）却列入 `D01–D02、T01–T02、S01–S02、P01–P02`；波次 W2 列入 `D03–D04、T03–T04`；R5 反而被排在波次 W3。
  4. 上游总索引 `docs/plans/2026-10-27-repair-and-product-roadmap.md` §1 明确指明：“D 交付前置为 R 的状态结果合同稳定；展示可先开发... 数据模型、纯规则与只读界面可以提前准备”。R5 是真实 GPU 200 次切换及资源泄漏测试，只属于 Slice 1 发布门禁，不是新功能代码开发的底层前置。
- **影响**：若遵照 §0 关键路径，开发人员 B 在 W1–W5（长达 5 周）期间无法开工 D01–D04 与 T01–T03，产能严重闲置；且一旦物理 GPU 机器排期延误（风险 X2），新功能将全线停摆。
- **具体修法**：
  - 修正 §0 关键路径拓扑：将 R5 标记为 Slice 1（G1）的独立出口分支，从主干新功能开发链路上剥离。
  - 统一 §6.2 与 §8.1：明确在 W1–W4 期间，开发 B 全力推进 D01–D04、T01–T03 的服务与数据层开发，与开发 A 推进的 R1–R3 并行。

### 3.2 P1 级发现（高风险，严重影响工程质量与协作）

#### [P1-1] 单一写入者纪律在 WBS 中自我违背，共享文件所有权冲突
- **位置**：§4.2 表（第 131–142 行）、§7.1 表（F08）、§7.4 表（T05/T06）、§7.6 表（P06）。
- **证据**：
  1. §4.2 明确规定：`src/Core/Settings.cs` 的 Owner 是 **A**（“F08 迁移/开关；新增字段保持旧版可忽略”）。
  2. 但在 §7.1 表中：任务 F08（开关与迁移）的 Owner 却被指派给 **B**。
  3. 业务上，B 负责的趋势告警（T05/T06）需要在 `Settings.cs` 增加告警阈值配置；低功耗（P06）需要在 `Settings.cs` 增加电源策略配置。
  4. `src/UI/UIController.cs` 在 §4.2 规定 Owner 为 A（“唯一 writer”），但在 §7.3 和 §7.4 中，D03（诊断窗口入口）与 T04（趋势入口）的 Owner 却直接标为 **A/B**。
- **影响**：违反单 writer 核心规则，开发 B 无法在不修改 `Settings.cs` 和 `UIController.cs` 的前提下交付自身任务，导致频繁的代码分支冲突与合并阻塞。
- **具体修法**：
  - 将 F08 的 Owner 修正为 A（由 A 在 W0 统一落地开关字段结构与备份基础设施）。
  - 将 `Settings.cs` 拆分为分部类（`Settings.Alerts.cs`、`Settings.Power.cs`、`Settings.Diagnostics.cs`），物理隔离各特性的字段定义；或通过通用字典挂载扩展设置。
  - 将 D03 与 T04 明确拆解：D03a/T04a（后台服务与数据提供，Owner: B）+ D03b/T04b（窗体 UI 与托盘接入，Owner: A）。

#### [P1-2] 本地化合同 C4 假设与现有 `LanguageManager` 运行时机制脱节
- **位置**：§5 C4 合同（第 180–186 行）、§7.1 F09、§13.2。
- **证据**：
  1. C4 规定：“zh/en 必填；de/es/fr/ja/ko/ru/zh-tw 允许回退英文，但必须登记”。
  2. 检查现有源码 `src/Core/LanguageManager.cs`：
     - `Load(langCode)` 仅将 `{langCode}.json` 单层解析至 `_texts` 字典；
     - `GetOriginal(key)` 查询不到 key 时，执行：`int dot = key.IndexOf('.'); return dot >= 0 ? key[(dot + 1)..] : key;`；
     - 现有代码**根本不存在向 `en.json` 自动回退的二级缓存或底表机制**。
  3. 一旦德语（de.json）等语言未翻译新增的 `feature.section.control` key，系统在德语环境下将直接返回截断后的 `section.control` 原始 key 字符串，绝不会显示英文。
  4. 任务 F09（§7.1）仅规划了模板和 CI 检查，未包含对 `LanguageManager.cs` 底层回退能力的改造工时。
- **影响**：非中英文用户在新功能上线后将遭遇大面积的 raw key 碎乱界面，C4 的回退承诺在生产环境中彻底失效。
- **具体修法**：
  - 在 F09 中明确增加改造 `LanguageManager.cs` 的要求：支持底表机制（若当前语言非 `en`，预先常驻 `en.json` 作为后备字典；查询缺失时先查 `en`，最后才返回 key）。
  - 或者在 CI 门禁中加入脚本：若坚持不在代码中改动 `LanguageManager`，则必须在构建前自动将 `en.json` 的缺失条目回填至其余 7 份语言 JSON 中。

#### [P1-3] 设置模型缺少 `[JsonExtensionData]` 导致降级破坏
- **位置**：§11.2 第 406 行、§11.3 第 417 行、§12 X10 风险。
- **证据**：
  1. §11.3 第 417 条声明：“旧版不认识新字段时忽略，不删除；降级后不再次自动迁移”。
  2. 检查源码 `src/Core/Settings.cs`：该类使用 `System.Text.Json` 进行持久化（如 `JsonSerializer.Serialize(this)`），但**并未声明 `[JsonExtensionData]` 属性字典**（对比 `ThemeManager.cs` 和 `ThemeRenderingConfig.cs` 均已声明该特性）。
  3. 实际行为：旧版本读取带新字段的 `settings.json` 时虽不会崩溃，但旧版本只要发生任何一次设置修改保存（如开机自启、窗口拖动保存），`System.Text.Json` 在重新序列化时会将所有未知新字段**永久丢弃**！
- **影响**：用户一旦在升级后降级运行旧版本并保存设置，所有新特性的配置数据将被彻底清空，无法再次安全切回新版本。
- **具体修法**：
  - 在 F08 的完成判据中增加一条硬性技术改造：“在 `Settings.cs` 中增加 `[JsonExtensionData] public Dictionary<string, JsonElement>? ExtensionData { get; set; }`”。
  - 补齐对应测试用例：“模拟旧版读入新字段后再次保存，确认未识别的新字段依然完整保存在磁盘 JSON 中”。

#### [P1-4] 采样需求合同 C3 语义畸形，与底层 IPC 模型冲突
- **位置**：§5 C3 合同（第 173–179 行）、§7.6 P04、对比 `low-power-mode-implementation-plan.md` §5.1。
- **证据**：
  1. 现有代码 `src/Contracts/SamplingModels.cs:21`：
     `public sealed record SamplingDemand(bool Ui, bool Taskbar, bool Web, bool History, bool SensorWindow);`
     这是针对主程序内部 5 大模块的有界布尔聚合体。
  2. 低功耗源计划 `low-power-mode-implementation-plan.md` §5.1 明确警告：“在现有 keyed demand 上增量表达消费者身份、是否活跃、最大可接受采样间隔... 不把新字段偷偷塞进现有布尔值含义”。
  3. 但执行计划 C3 却写为：“在现有五布尔基础上增加：`MaxIntervalMs`、`Reason`、`Degradable`；旧聚合器忽略新字段...”。
  4. 现有 IPC 消息 `IpcProtocol.OpSubmitDemandV2`（`IpcMessages.cs:42`）已定义为 `{ consumerId: string, demand: SamplingDemand }`。若在带 5 个布尔的结构上再绑单个 `MaxIntervalMs`，会导致单个消费者（如 Web）在登记时既要面对 5 个布尔状态，又要携带自身频率，导致语义混淆（例如 Web 消费者登记时，Ui/Taskbar 布尔应置为何值？）。
- **影响**：破坏了低功耗源计划对 keyed demand 的正交设计，导致 P04 在协议演进和双端对齐时发生架构返工。
- **具体修法**：
  - 纠正 C3 合同设计：保留旧 `SamplingDemand` 作为单体布尔兼容层；新增专用于 keyed 消费者的合同模型 `ConsumerSamplingDemand(string ConsumerId, bool Active, int MaxIntervalMs, bool Degradable, string Reason)`。
  - P04 仅在 `ConsumerSamplingDemand` 基础上进行聚合计算，不再污染旧的 5-布尔 record。

#### [P1-5] 历史 v2 降级再升级存在“无双写”导致的数据断层
- **位置**：§11.2 第 407 行、§11.3 第 413 行、§7.4 T03。
- **证据**：
  1. T03 明确声明“无双写”（切换至 v2 JSONL 存储后，停止写入旧版 `HardwareHistory.json`）。
  2. §11.3 规定：“历史 v2 异常 → 回退 v1 只读”。
  3. §11.2 规定：“迁移记录版本化、幂等；无重复迁移”。
  4. 数据流漏洞推演：用户升级到 Slice 2 运行一段时间后，由于某种原因关闭开关或降级回 Slice 1。在降级运行期间，系统重新向 v1 写入数据。随后用户再次升级至 Slice 2。由于系统标记“已完成 v1 迁移（无重复迁移）”，用户降级期间产生的所有历史数据将无法被导入 v2，在 v2 中形成永久性的数据空洞。
- **影响**：历史监控数据在降级与重新升级路径中丢失，损害数据连续性。
- **具体修法**：
  - 在 T03 迁移设计中补充“增量时间戳同步机制”：v1 导入记录 `LastImportedTimestamp`，重新开启 v2 时比对 v1 文件最后写入时间，若有新数据则执行增量追加。
  - 或者在产品限制清单中如实声明：“降级期间记录的监控数据仅保存在 v1 中，再次启用新历史时不进行回填”。

#### [P2-2] 开发人员 A 在 Slice 1（W1–W4）面临严重超载风险
- **位置**：§4.1 角色分工、§6.2 建议日历、§7.1、§7.2。

- **影响**：开发 A 成为严重的单点瓶颈，极大概率导致 W5 的 G1 门禁延期。
- **具体修法**：平衡分工：将 F07（E04 生命周期收口与窗体注销）或 R2 中的任务栏快照/导出准备调整给开发 B 承担。

#### [P2-3] 证据目录硬编码旧日期 `2026-10-27-execution`
- **位置**：§9.4 证据目录（第 364 行）。
- **证据**：
  - 目录路径硬编码为 `docs/verification/2026-10-27-execution/Gx/`。
  - 整个计划周期长达 18 周（跨越至 2027 年），在跨月的门禁中使用 `2026-10-27` 违背了修复计划 §9 “实际实施日期变化时使用真实日期，不预填结果”的原则。
- **影响**：证据目录语义混淆，不利于多阶段证据归档。
- **具体修法**：路径统一改为 `docs/verification/execution/G{x}/` 或在 G0 会签时按实际启动周次规范命名。

#### [P2-4] 表 4.2 采样/IPC 行规则列合同引用笔误
- **位置**：§4.2 表 4.2（第 138 行）。
- **证据**：
  - 采样/IPC 行的规则列写为：“`C3/C4 合同；P04–P05 串行`”。
  - 查 §5 合同定义，C4 为“本地化 key 合同”，与采样/IPC 无关，属于笔误（应为 C3）。
- **影响**：合同引用错误，容易误导开发人员。
- **具体修法**：修正为“C3 合同”。

#### [P2-5] 性能门禁“静置后出帧为 0”缺少明确的时间收敛上界
- **位置**：§10.2 表 10.2（第 386 行）。
- **证据**：
  - 指标要求写为：“静置后为 0；仅保留必要的低频维护唤醒”。
  - 未定义“静置”的具体时间窗口（是 100ms、500ms 还是 5s）。
- **影响**：测试在断言帧率归零时，可能因后台调度在途异步排空而抖动失败，或者测试因过长休眠等待而极度拖慢运行效率。
- **具体修法**：明确量化指标：“最小化/隐藏触发后，在 `<= 500ms`（或 2 个调度周期）内出帧归零”。
