# 工程不变量与验证门禁

## 1. 本文描述什么

本文描述 LiteMonitor++ 当前生效的工程不变量与验证门禁：数据与错误语义必须满足的可判定规则、异常模型与进程存活语义、可空引用与编译警告的强制性门禁、模块协作与生命周期约束、异步命令中超时与取消与合并的关系、持久化的写入规则、发布签名与产物校验的职责划分，以及验证的三层结构与每层证据要求。

适用范围是全仓库：`src/` 下的全部工程、`LiteMonitor.Updater`、`tests/`、`tools/`、`scripts/` 与 `.github/workflows/`。

本文不重复其它文档已经承载的内容：模块边界与依赖方向见 `layering.md`，跨进程协议与故障监督状态机见 `process-isolation.md`，在途请求的请求身份与摘要算法见 `inflight-lease.md`，渲染路线的失败分级与恢复预算见 `rendering-transition.md`，更新链的签名机制与事务替换见 `update-chain.md`，配置文件的落盘位置见 `overview.md`。本文只规定"必须怎样"，并在需要时引用这些文档。

文中出现的类型名、方法名、枚举值、错误码字符串与文件路径是契约面的一部分，随代码演进。

## 2. 数据与错误语义不变量

每条规则都可判定：满足或不满足，不存在"尽量"。

### 2.1 错误不得伪装成正常值

- **失败必须有专属表示。** 采集样本的质量取值只有 `Good`、`Stale`、`Missing`、`Error` 四种；`Error` 必须携带 `MissingReason`，不得用 `Value` 承载错误信息。
- **异步操作结果必须区分"未受理"与"已受理但未完成"。** `HardwareOperationResult.Accepted` 为 `false` 时，`State` 必须是 `Rejected` 或 `Failed`，且 `FailureReason` 非空。
- **空结果不得推导为成功。** `ApplyOperationResult` 的外层状态由模块结果推导：模块结果为空时外层状态必须是 `Unknown`，不得是 `Applied`。
- **"已保存"与"已生效"是两个字段。** `ModuleApplyResult` 必须同时给出 `SavedState`、`EffectiveState` 与 `FailureReason`，界面不得用 `SavedState` 推断 `EffectiveState`。
- **失败码是稳定字符串，不是自由文本。** 主题校验的 `error_code` 取值、插件沙箱的原因码、渲染故障的 `FailureCode` 都属于对外契约；新增取值是兼容变更，修改既有取值的含义不是。
- **读取失败不得用默认值顶替。** 配置文件因 I/O 故障读不到时，会话以默认值继续运行，但当前会话必须禁用自动保存，避免用默认值覆盖磁盘上的既有配置。

### 2.2 缺失与合法的零严格分离

- **零是合法值。** `MetricSample.Quality` 为 `Good` 且 `Value` 为 `0`，表示"取到了，值就是零"。
- **缺失不是零。** `Quality` 为 `Missing` 时必须携带 `MissingReason`；`Value` 不得被消费者解释为 `0`。
- **采样层禁止用零表达"取不到"。** `MetricSample.Value` 的类型是 `float?`，采集层在取不到时给出 `Missing` 或 `Error`，绝不给出一个数值。
- **质量判定与展示格式分离。** 展示端可以决定缺失怎么画，但不得改变样本的质量判定；渲染契约中的 `MetricStatus` 取值为 `Normal`、`Warning`、`Danger`、`Missing`，映射规则由展示端自己承担。
- **各消费面看到同一份质量。** 界面、Web、历史与诊断消费同一份快照快照中的同一批 `MetricSample`，某一展示端的格式化不得回写样本。

### 2.3 恢复必须有界

任何重试、重启、重新拉起都必须有预算，预算耗尽必须转入可观察的终态。

- **渲染恢复预算耗尽产生稳定错误码。** GPU 呈现的自动恢复耗尽记为 `gpu_presentation_recovery_exhausted`；该记录未终结前，常规 Tick 不得自动再拉起 GPU 路线。
- **故障转换只能在 UI 安全点执行。** 故障报告先入队，转换动作由 UI 安全点统一执行；禁止在 `OnPaint`、窗口句柄销毁回调、GPU 帧绘制栈内递归执行转换。
- **采样异常按正常周期重试。** `HardwareSamplingCoordinator` 捕获采样异常后按正常周期安排下一次，不得形成异常忙循环；未到期的请求快速返回，不创建任务、不调用设备更新。
- **子进程重启有上限。** `HardwareHostSupervisorOptions` 固定了握手期限、心跳失联次数、采样无进展期限、初始化上限、关闭宽限，以及退避序列（1 秒 / 3 秒 / 10 秒）与退避窗口（5 分钟）内连续失败达到 `BackoffPauseThreshold` 即暂停自动重启并进入 `Degraded`。
- **插件步骤失败是可继续的单步失败。** 单步失败按插件自身退避重试，不影响其余步骤；沙箱的并发数、响应体积、正则耗时、步数与截止期限都是硬上限。
- **文件写入重试次数有界。** `SettingsHelper.AtomicWrite` 对 `IOException` 与 `UnauthorizedAccessException` 最多额外重试两次，退避 25 毫秒与 50 毫秒；其余异常立即失败。
- **预算耗尽不得转为"假装正常"。** 耗尽后的状态必须是显式的降级状态、错误码或停止状态，并可从界面或诊断读出。

### 2.4 界面与采样线程分工

- **采样只有一个入口。** 真实采集由 `HardwareSamplingCoordinator` 统一发起；界面、Web、历史与诊断消费同一份已发布快照，各自触发一次独立采样是被禁止的。
- **读取快照不推进采集。** `IHardwareClient.GetLatestSnapshot()` 同步返回已发布的完整快照，不触发采样、不改变 `BatchId`、不推进代次。
- **界面线程只读不采。** 界面不得为了补数据而触发一次真实采集；界面不得持有采集锁。
- **采样调度基于单调时钟。** 是否到期由单调时钟判定，墙上时间回拨不得影响调度；超长任务结束后安排未来的期限，不补跑错过的多轮。
- **界面刷新快于采样周期时以采样周期为准。** 界面定时器的频率不构成新的采样频率。
- **采集侧不响应等待者的取消。** 采集不因等待者取消而中断；取消与超时的语义见 `inflight-lease.md` 与第 6 节。

### 2.5 原生故障在正确边界解决

- **原生访问只在拥有它的层内发生。** LibreHardwareMonitor 的设备树与句柄只存在于采集层；硬件采样子进程承担原生崩溃的隔离，主程序不得直接触碰采集器对象。
- **原生异常必须先转成结构化报告。** 设备丢失与呈现失败先转成 `GpuFailureStage` 与 `FailureCode`，再交给统一调度处理；原生异常对象不得越过渲染层进入领域层或界面。
- **契约层是纯 CLR。** `src/Contracts` 只承载基础类型与不可变 record，不得出现原生句柄、指针、绘图对象、锁或文件句柄。
- **系统资源的清理归属其创建者。** ETW 会话与外部辅助进程的停止由采集层与退出路径负责，不得依赖界面正常关闭。
- **插件 native 步骤的失败在插件层转成结构化原因码**，不得把原生异常直接抛给调度方。

### 2.6 配置形状变更向后兼容

- **配置文件是用户可编辑的文本。** 新增字段必须有确定的缺省语义，使未含该字段的既有配置得到与作者意图一致的行为。
- **缺省字段不得改变文件字节。** 键不存在时不得写出来，也不得因为加载而重写整份既有配置。
- **迁移在加载期完成且幂等。** 同一份配置重复加载必须得到同一结果，且不得累积出重复项。
- **未知字段必须被保留。** 主题与情景模型使用 `[JsonExtensionData]` 承载未知字段；保存时未知字段不得被丢弃，否则跨版本往返会静默删数据。
- **主版本不兼容必须被拒绝。** 跨进程协议由 `IpcProtocol.MajorVersion` 与 `IpcProtocol.MinorVersion` 承载：主版本不兼容时拒绝连接，兼容的新增字段走次版本；消息 JSON 的属性名大小写敏感匹配，不得用宽松忽略掩盖主协议冲突；未知消息类型属协议违规。
- **读失败不得造成数据丢失。** 损坏的主文件先改名隔离再回落备份；I/O 故障时不回落备份，因为两个文件很可能锁在同一原因上。

### 2.7 运行时投影不落盘

- **投影是纯函数。** `SettingsProjection` 的派生方法无 IO、无单例读取、无副作用；投影是只读快照，不得回写存储模型。
- **运行时字段不进入存储。** `LastAutoNetwork`、`LastAutoDisk`、`ScreenDevice`、`MaxLimitTipShown`、`TotalUpload`、`TotalDownload`、`SessionUploadBytes`、`SessionDownloadBytes`、`LastAutoSaveTime`、`LastAlertTime` 属于运行时黑名单：既不参与草稿差异计算，也不被草稿覆盖。
- **凭据不进入投影。** `WebConfigProjection` 只携带"是否已配置口令"的布尔标志，口令明文与盐不得出现在任何投影中。
- **投影不得携带运行期事实。** 运行时计数、自动设备选择结果、采集错误与缓存都不属于投影内容。
- **探测策略只传原始整数值。** 未配置的探测档位以 `-1` 占位传递，策略语义由采集层解释，投影不得引用采集层类型。

## 3. 异常模型与进程存活语义

### 3.1 三类异常的责任边界

| 类别 | 触发条件 | 后果 | 责任方 |
|---|---|---|---|
| 界面线程未处理异常 | WinForms 消息循环内未被捕获的异常 | 由全局兜底处理，进程继续运行 | `src/System/Program.cs` 的全局处理器 |
| 后台线程未捕获异常 | 后台线程上逃逸到线程顶部的异常 | 进程终止 | 后台线程自身必须捕获 |
| 未观察的任务异常 | fire-and-forget 的任务抛出且无人观察 | 默认被忽略，问题不可见 | 发起方必须在调用点观察 |

### 3.2 界面线程未处理异常

- **全局兜底必须存在。** `Program.Main` 先于任何窗口的创建调用 `Application.SetUnhandledExceptionMode(UnhandledExceptionMode.CatchException)` 并挂接 `Application.ThreadException`。
- **兜底不得重新抛出。** 处理器把异常写入 `LiteMonitor++_Error.log` 并提示用户，然后正常返回；重新抛出等于把界面异常升级成进程终止。
- **异常内容必须留痕。** 处理器记录时间、来源、消息与堆栈。
- **界面代码仍应自行处理可预期异常。** 全局兜底是最后一道防线，不是常规错误处理手段。

### 3.3 后台线程未捕获异常

- **后台线程的未捕获异常必然终止进程。** `AppDomain.CurrentDomain.UnhandledException` 的处理器只负责留痕，不改变终止结论。
- **后台线程必须自捕。** 采集线程、插件线程、Web 连接处理线程都必须在自身边界内捕获异常并转成结构化结果，不得让异常逃逸到线程顶部。
- **采样异常计入统计而不中断调度。** 采集协调器捕获异常后计入 `HardwareSamplingStatistics` 的失败计数，并按正常周期重试。

### 3.4 未观察的任务异常

- **不得依赖进程级兜底。** 进程内没有注册 `TaskScheduler.UnobservedTaskException` 处理器，该异常在默认配置下被忽略，不能作为错误通道。
- **每个 fire-and-forget 调用必须在调用点观察异常。** 惯用形态是包一层异步方法：方法体内 `try` 捕获并记录，`finally` 归还计数名额。`LiteWebServer.HandleClientGuardedAsync` 是这一形态的样板。
- **资源归还不得依赖异常逃逸。** 名额、租约、句柄的释放在 `finally` 中完成；异常被吞掉也不得造成计数泄漏。
- **不得用 `_ = Task.Run(...)` 承载需要观察结果的工作。** 需要结果的工作必须被 `await` 或显式观察其 `Task`。

### 3.5 异常留痕出口

| 出口 | 承载内容 | 位置 |
|---|---|---|
| `HardwareErrorLog` | 硬件层与设置层的可预期失败 | 硬件错误日志 |
| `LiteMonitor++_Error.log` | 未处理异常（界面线程与后台线程） | 程序目录 |
| `DiagnosticHub` | 进程内诊断事件 | 诊断中心 |
| 失败码 | 对外契约中的结构化原因 | 各模块的错误码表 |

留痕内容不得包含凭据、口令明文与用户隐私数据。

## 4. 可空引用与编译警告门禁

### 4.1 生产工程门禁口径

- **四个生产工程在 Release 下零警告。** `LiteMonitor.csproj`、`LiteMonitor.Updater/LiteMonitor.Updater.csproj`、`src/Contracts/LiteMonitor.Contracts.csproj`、`src/HardwareHost/LiteMonitor.HardwareHost.csproj` 各自在 `Condition="'$(Configuration)' == 'Release'"` 的属性组里设置 `TreatWarningsAsErrors=true`。
- **四个工程的 `Nullable` 均为 `enable`。** 可空引用检查是编译期约束，不靠代码评审保证。
- **只限 Release。** Debug 保留警告可见性，便于开发期定位；门禁本身以 Release 执行。
- **门禁落在工程自身，不落在仓库级属性。** 仓库根 `Directory.Build.props` 会被 `tests/` 与 `tools/` 隐式导入，在那里开启"警告即错误"会把测试工程与探针工程的历史债务一并升级为错误，使门禁永久红灯。

### 4.2 豁免白名单的语义

- **白名单登记的是"确实还存在"的警告码。** 每清理掉一个存量码就从清单中移除，门禁随之收紧；白名单是存量账，不是永久授权。
- **豁免不得使用"把这些码当作错误"的写法。** 编译器语义与"豁免这些码"完全相反，用错写法会把豁免变成强制。
- **禁止无差别地把全解决方案的警告整体升级为错误。** 全局升级会把存量债务变成红灯；正确形态是"整体升级 + 明确的存量豁免清单"。
- **豁免必须就近可见。** 工程自身的抑制清单写在工程文件里；仓库级属性只提供追加点，工程新增抑制码必须沿用追加形式，不得覆盖已有清单。
- **可空治理的目标是消除真缺陷，不是静默豁免。** 标注为"与可空治理无因果关系"的规则警告（如测试工程的分析器规则）登记为独立条目，不进入可空豁免的语义范围。
- **网络类告警不构成代码质量信号。** 构建期的漏洞审计告警受网络可达性影响，会造成门禁"假红"；这类告警在门禁作业中关闭，同一作业的依赖还原步骤仍开启审计，真实漏洞照常可见。

### 4.3 门禁执行方式

- **门禁以真实退出码判定。** 判定依据是构建命令的退出码，不看日志里是否出现 "warning" 字样。
- **门禁 1：生产工程零警告。** 对四个生产工程分别执行 Release 构建，带"警告即错误"，任何一个工程非零退出即判定失败，不允许降级放行。
- **门禁 2：全解决方案不新增警告码。** 对整个解决方案执行 Release 构建，整体升级为错误并附存量豁免清单，出现清单外的警告码即判定失败。
- **门禁在流水线中以独立作业运行**，与构建、测试作业分开，结论彼此独立。
- **豁免清单的变更是门禁的组成部分。** 新增豁免条目必须写明它对应的是哪一类存量问题；清理存量代码时必须同步移除对应条目。

## 5. 模块协作与生命周期约束

### 5.1 契约演进必须给出兼容方案

- **契约只使用基础类型。** 跨模块数据契约只允许 `string`、整数、浮点、布尔、枚举、`TimeSpan` 及由它们构成的不可变 record 与只读集合；不得出现控件、绘图对象、采集器句柄、锁、文件句柄、委托与事件。
- **两端的成功、时效与缺失含义必须一致。** 进程内适配器与管道客户端不得对同一次采集表达不同的结果；否则上层无法判断该信哪一侧。
- **演进顺序固定。** 新成员先保证两端兼容，再迁移消费者，最后撤除兼容桥。
- **兼容方案的形态是有限集合**：兼容新增字段走协议次版本；新增可选成员带默认实现；不兼容变更必须提供双读与迁移路径，或让旧端在协议层被明确拒绝，而不是让旧端静默误解新语义。
- **契约变更必须说明影响面**：哪一侧被改、另一侧是否需要同步、旧数据如何读取。

### 5.2 配置文件单一写入点

- **`settings.json` 的唯一写入者是 `SettingsHelper`。** 任何模块不得绕过它直接写该文件，包括主题模块、插件模块与市场模块。
- **同一进程内的写入必须串行化。** `SettingsHelper` 用进程内锁保证写入互斥；写入者不得在持锁期间回调界面或安装流程。
- **市场记录的写入走事务化入口。** `SettingsHelper.TryChangeMarketRecord` 与 `TryChangeThemeRecord` 先在内存中改写、整体落盘，失败时只回滚受影响的记录，其余记录不动。
- **模块自有状态文件由该模块独占。** `device-bindings.json` 由 `DeviceBindingStore` 写，`TrafficHistory.json` 由 `TrafficLogger` 写，`HardwareHistory.json` 由 `HardwareHistoryLogger` 写，主题与插件声明目录由各自管理器写；这些文件不得被第二个写入者触碰。
- **临时文件名带进程号。** 固定的临时文件名会成为多个写者与多个进程的公共踩踏点；加载时清扫残留，且清扫失败不得阻塞加载。

### 5.3 界面不得同步等待硬件锁与跨进程通信

- **兼容桥方法禁止在界面线程调用。** `IHardwareClient.ApplyConfig` 是同步兼容桥，契约上明确禁止在界面线程调用；界面路径只使用 `ApplyConfigAsync`。
- **界面读取硬件信息必须走无锁或短等待路径。** `HardwareMonitor.GetMonitoredGpuCount` 无锁读取已发布的缓存；`HardwareMonitor.TryGetDetectedGpuCount` 最多等待采集锁 10 毫秒，拿不到就退回扫描器缓存。持锁的枚举方法不得出现在界面的常规路径上。
- **采集锁可能被长时间持有。** 硬件重载期间采集锁可持续数秒，界面在这段时间内必须显示"数据不可用"而不是等待。
- **跨进程命令面是异步的。** `ApplyConfigAsync`、`RequestSamplingAsync`、`RequestFullRescanAsync` 都是异步方法；界面不得同步阻塞等待管道往返。
- **界面不得以触发采集的方式刷新数据。** 刷新只能读取已发布快照。

### 5.4 模块副作用不得包装成全局原子事务

- **设置提交会触发彼此独立的动作。** 采集配置重建、Web 监听重启、主题重绘、开机自启设置互不依赖，无法一次回滚。
- **结果模型必须区分三件事。** 已保存配置、实际生效状态、失败原因分别由 `ModuleApplyResult` 与 `ApplyOperationResult` 承载；不得用单一布尔包装多个模块动作的结果。
- **变更分组是解耦手段。** `ApplyPlan` 把变更划分为界面重建组、WebServer、Plugins 三个独立开关：颜色与语言变化不得触发硬件重建；设备访问策略变化才请求采集层重建；Web 端口变化只重启监听。
- **情景应用的顺序固定。** `ScenarioApplyCoordinator` 依次执行读取修订、预检、生成候选设置、持久化、按模块应用、由模块结果确认外层状态；保存失败时 live 设置保持不变，预检不通过时返回阻断原因且不触碰 live 设置。
- **部分成功是合法结果。** 外层状态 `Partial` 表示部分模块生效，这是可接受且必须如实上报的结局。

### 5.5 测试优先验证产品入口与真实组件边界

- **生产入口必须被真实构造。** 纯单元测试证明不了主程序能否启动：`MainForm` 构造期抛异常属于启动阻断缺陷，能穿过全部单元测试。流水线因此真实构造生产 `MainForm`（`tools/GpuHostLifecycleProbe` 的 `startup` 场景），刻意不跑消息循环，避免 Web 服务开始监听。该检查的退出码契约是：`0` 构造成功、`1` 构造抛异常、`2` 环境不具备、`64` 参数错误。
- **探针以被引用工程接入测试工程。** 相关回归护栏必须能真正调用探针内部的判定能力（持续送帧通道、隔离门判定、源码漂移比对），只读源码文本的断言太弱：改个变量名就失效，也测不出"失败会不会被如实报告"。探针的内部成员通过 `InternalsVisibleTo` 暴露，不扩大对外公开面。
- **契约测试使用真实夹具与真实组件边界。** 插件市场与主题市场的契约用例使用仓库内的夹具仓库路径，不用 mock 取代被验证的边界。
- **共享文件用例必须串行。** 会读写 `settings.json` 的用例挂在同一个串行集合内；同一台机器上不得并发执行依赖同一硬件库的测试套件。
- **测试工程可关闭可空检查，但不得掩盖真实缺陷。** 测试代码的可空标注噪音由工程自身的抑制清单处理，与生产工程的可空门禁分开记账。

### 5.6 生命周期与资源归属

- **组合根唯一。** `UIController` 的构造函数是当前的组合根，创建采集器、选择运行模式、注册网关、接线全局委托；其余层不得回指组合根。
- **消费者只释放自己订阅的资源。** 释放自己的采样需求、诊断订阅与图形资源；关闭一个窗口不得释放其它消费者共用的采集器。
- **释放顺序按依赖逆序。** 退出时统一取消并等待；关闭过程中不得重建宿主、不得恢复窗口亲和性、不得重新创建渲染资源。
- **资源归属唯一。** 渲染资源账本由 GPU 呈现控制器持有；窗口亲和性清理由界面生命周期持有，并以幂等方式终结。

## 6. 异步命令语义：超时、取消与合并

### 6.1 三者的关系

- **合并以请求身份为键。** 同一身份的并发调用必须合并为一次真实操作；影响响应的字段（方法、规范化 URL、请求体、全部请求头、转发端点、响应编码）一个都不许缺席，否则串用成立。
- **超时只终止本调用方的等待。** 超时不构成对底层操作的取消，也不得被表述为"底层已停止"。
- **取消只影响发起取消的等待者。** 共享操作的持有者不受任何等待者的取消令牌影响。
- **等待者的退出不得截断共享操作。** 一个等待者超时或取消，不得让仍在进行的操作从共享表中消失，否则后来的调用方会再发一条重复请求。
- **四种终止在结果类型上可区分。** `HardwareOperationState` 的取值为 `Queued`、`Running`、`Completed`、`Failed`、`Cancelled`、`Rejected`；调用方超时后的真实结局由 `OperationId` 后续查询。
- **合并不得跨越安全边界。** 命中在途不构成绕过目标授权与凭据策略的理由；每个等待者各自履责自己的策略判定。

### 6.2 调用方责任

- **调用方必须自行给出等待期限。** 组件不替调用方决定"等多久算超时"。
- **超时后必须按操作身份查询真实结局。** 不得把超时当成失败，也不得当成取消。
- **被拒绝的操作不得原样重试。** `Accepted=false` 一定带可解释原因，重试前必须先修正请求。
- **不得以同一身份重复发起来"补一次"。** 除非确认共享操作已经终结，否则重复发起会产生第二条真实请求。
- **等待者不得在等待期间修改请求身份要素。** 身份在加入共享时确定，事后变更语义等于发出另一个请求。

## 7. 持久化规则

### 7.1 配置原子写

`SettingsHelper.AtomicWrite` 的顺序是契约的一部分：

1. **写临时文件。** 路径带进程号（`settings.json.{ProcessId}.tmp`）；使用 `FileOptions.WriteThrough` 打开，写入后调用 `Flush(true)` 把内容真正刷到介质，再关闭流。编码固定为 UTF-8 无 BOM。
2. **回读校验。** 把临时文件读回并反序列化为配置对象；反序列化失败即放弃该次保存并抛出。此时半截内容既没有顶替主文件，也没有污染备份。
3. **刷新备份。** 备份的语义是"上一份有效内容"，因此必须先于主文件替换生成，且只有当既有主文件本身可解析时才生成。
4. **原子替换主文件。** 目标存在时用 `File.Replace`（同卷原子替换，保留目标文件的 ACL 等元数据）；平台或文件系统不支持、或目标被占用时退到 `File.Move(overwrite)`，同样是同卷原子替换。**任何路径都不得先删除主文件**，替换失败时既有配置原样还在。

- **主题文件走同一套语义。** `ThemeFileService` 同样是临时文件加 `Flush(true)` 再替换目标。
- **替换失败必须向上抛。** 调用方据此把结果归类为写失败，而不是当作成功。

### 7.2 写盘失败不得把明文原样落盘

- **凭据保护失败时整体保存取消。** 序列化阶段抛出的凭据保护异常使保存中止，主文件与备份都不动，结果是 `SettingsSaveOutcome.CredentialProtectionFailed`；磁盘上不得出现明文凭据。
- **备份内容必须与主文件同级。** Web 访问口令在备份里脱敏为空串，插件凭据在备份里是 DPAPI 密文；由 `Settings.SanitizeSettingsJsonForBackup` 统一处理，其余字段逐字保留，使备份仍是可回滚材料。
- **备份写入失败不得退回"原样复制"。** 原样复制会把加密前的明文凭据留在磁盘上的第二个文件里，使泄露面大于主文件。写不出备份时保持既有备份不动，宁可备份陈旧。
- **脱敏失败即不写备份。** 不得以"先原样留着回头再处理"为代价。
- **口令永不落盘。** 主文件里的口令字段由专用转换器强制写成空串，磁盘上只保存 PBKDF2 哈希与盐。

### 7.3 历史与统计数据的原子写

- **`HardwareHistoryLogger` 与 `TrafficLogger` 的 `AtomicWrite`**：写临时文件 → 备份既有文件 → `File.Move(temp, file, overwrite)` 完成同卷原子替换；既有文件不会被预先删除。
- **`TrendHistoryV2Store` 的清单文件**同样采用临时文件加覆盖移动。
- **写盘失败必须被记录**（`HardwareErrorLog`），不得静默吞掉。
- **写入强度低于配置文件**：这几处写入不含 `Flush(true)` 的落盘确认，配置文件写法则有。

### 7.4 落盘结果必须可判定

- **保存结果四态。** `SettingsSaveOutcome` 的取值为 `Saved`、`Blocked`、`CredentialProtectionFailed`、`WriteFailed`；界面必须能区分"凭据保护失败"与"一般写入失败"。
- **读取失败分型。** 损坏（`Corrupt`）与 I/O 故障（`IoFailure`）是两种结局：损坏文件被改名隔离留证，I/O 故障时当前会话禁用自动保存。
- **禁写标记必须记录持有者。** `SaveBlockOwner` 记录当前禁写的来源，一次成功读取只撤销自己置上的那一次禁写，不解除外部置上的禁写。
- **失败原因文本不得包含凭据值。** 只允许参数名与底层原因。

## 8. 发布签名与产物校验

### 8.1 签名脚本 `scripts/sign-release.ps1`

- **它是更新链路里唯一的信任产生点。** 客户端只验签、不信任下载 URL，因此签名脚本必须与客户端的载荷定义逐字节一致。
- **载荷是固定三行。** `<version>`、`<sha256>`、`<releaseDate>`，UTF-8 无 BOM，LF 分隔。刻意不签整段 JSON：序列化顺序、缩进或行尾的任何变化都会让签名失效。
- **算法固定。** ECDSA P-256 加 SHA-256，签名格式为 DER SEQUENCE（RFC 3279），与客户端使用的 `DSASignatureFormat.Rfc3279DerSequence` 一致。
- **摘要由脚本自己计算**，不接受外部传入，避免"签的不是发的"。
- **两道自检缺一不可。** 第一道：私钥导出的公钥必须等于客户端内置的 `UpdateSigningPublicKeySpkiBase64`（常量在 `src/System/UpdateChecker.cs`）；用错密钥会让所有客户端验签失败，而失败现象只出现在用户侧。第二道：签名生成后立即用同一载荷自验一次。
- **只回写四个键。** `resources/version.json` 的 `version`、`releaseDate`、`sha256`、`signature` 的字符串值被替换，其余内容（缩进、行尾）原样保留；缺键即失败，不做"缺键就插入"的结构改写。
- **私钥不进版本库。** 私钥文件在仓库的忽略规则内，脚本默认从 `secrets/` 读取。
- **退出码契约。** `0` 成功，`1` 前置条件失败（缺文件、私钥不匹配、自验失败）。

### 8.2 独立复验脚本 `.github/workflows/verify-release-signature.ps1`

- **它完全独立于签名脚本。** 只使用公钥，不接触任何私钥材料。
- **信任锚点唯一。** 公钥只从 `src/System/UpdateChecker.cs` 解析 `UpdateSigningPublicKeySpkiBase64`，与客户端信任的锚点同源。
- **它验两件事。** 一是 `version.json` 的签名能否用客户端内置公钥验证；二是"签的是不是发的"——给出发布包路径时，核对 `version.json` 的 `sha256` 与发布包实际摘要一致。
- **形态校验先行。** 四项字段必须齐备，`sha256` 必须是 64 位十六进制；任一项不符即拒绝复验。
- **载荷重建必须与签名脚本一致**，否则验签结论无效。
- **退出码契约。** `0` 复验通过，`1` 复验失败，`2` 用法或 IO 错误。

### 8.3 职责边界

- **签名脚本持有私钥，复验脚本不持有。** 二者不可互相替代：签名脚本的自验只证明签名自洽，既不证明客户端内置公钥能验过，也不证明签的就是发布的那个包。
- **复验脚本在发布流水线的签名步骤之后运行**，结论为拒绝时不得继续上传产物。
- **可达性不能替代签名校验。** 下载源正常、摘要看起来合理，都不构成更新可信的依据。

### 8.4 其它产物护栏

- **发布包名必须与客户端下载模板一致。** `scripts/pack-release.ps1` 在启动时自检这一致性；发布包内必须包含 MIT 分发义务要求的许可声明。
- **第三方组件声明以实际解析依赖为真值。** `scripts/generate-dependency-manifest.ps1 -Mode Check` 核对 `NOTICE` 的直接依赖与随包分发依赖声明，存在漏列或版本不符即非零退出。
- **随包分发的预构建二进制做内容级判定。** `resources/LiteMonitor++.Updater.exe` 由工程以内容项复制进主程序产物，解决方案编译通过不能证明它由当前源码构建；判定依据是产物内嵌的构建标识与源码树比对，不依赖字节级可复现性。
- **构建可复现性是发布校验的前提。** 仓库级 `Directory.Build.props` 显式声明 `Deterministic=true`，发布清单的 SHA-256 比对依赖这一性质。

## 9. 验证分层

### 9.1 三层模型

| 层 | 回答的问题 | 执行位置 | 能否替代下一层 |
|---|---|---|---|
| 确定性测试 | 规则与契约在受控条件下是否成立 | 流水线，任意 Windows 机器 | 不能 |
| 真实组件集成 | 真实组件边界被跨越时是否成立 | 流水线，真实子进程与真实管道 | 不能 |
| 目标环境验收 | 在目标硬件与目标会话上是否成立 | 具备目标环境的机器 | 不可替代 |

三层的关系是收敛关系而非替代关系：任何一层的结论都不能覆盖另一层的适用范围。

### 9.2 确定性测试层

- **三个测试程序集必须全部参与。** `LiteMonitor.Tests`、`LiteMonitor.Updater.Tests`、`LiteMonitor.GpuNonperformance.Tests`；任一程序集整体未被执行即判定失败，防止某个测试工程悄悄没被测到。
- **Debug 与 Release 双配置执行。** Release 一侧同时验证"警告即错误"没有掩盖真实失败。
- **四道互补的防假绿门禁同时生效。** 发现数下限（被跳过的用例仍计入发现数，否则删用例即可绕过）；必须出现的程序集清单；跳过用例数上限；必须真正执行的测试类清单及其最小发现数与"一条都不得被跳过"的要求。后一道是防"静默跳过"的主力——夹具路径失效时，受环境变量门控的用例会被记成跳过而不是失败。
- **计数口径以 TRX 为准。** `total` / `executed` / `passed` / `failed` / `notExecuted` 逐项统计，并逐用例给出 outcome；结论以命令的真实退出码为准，不以控制台摘要为准。
- **门禁只收紧不放宽。** 发现数下限的调整必须写明删除了哪一类用例；流水线与发布流水线的同名字段必须同值，否则会出现"流水线红、发布绿"的口径裂缝。
- **未执行的配置与程序集必须逐条说明原因**，不得把未覆盖写成通过。

### 9.3 真实组件集成层

- **生产主窗体启动检查。** 真实构造生产 `MainForm`，退出码契约见 5.5；该场景不跑消息循环，因此不会启动 Web 监听。
- **依赖声明与实际解析依赖的一致性核对。** 真实读取还原图与包元数据，漏列或版本不符即失败。
- **跨进程协议与监督。** 真实管道、真实子进程、真实的握手与心跳，检查协议违规、快照原子替换与故障监督状态机的迁移。
- **市场契约用仓库内真实夹具。** 夹具目录的内容摘要必须与索引记录一致，因此夹具的换行符口径需要固定。
- **这一层的判据是"真实组件边界被跨越"**，而不是"某个替身被调用了"。

### 9.4 目标环境验收层

- **只有这一层能对目标环境作出结论。** 真实 GPU 与驱动版本、物理显示会话、显示器拓扑与缩放、真实网卡与磁盘、真实 Web 客户端、真实磁盘探测行为都属于本层。
- **虚拟显示器适配器与远程会话不构成有效证据。** 会话类型、显示器拓扑与缩放必须随证据一起记录。
- **缺少目标硬件时该项记为未覆盖。** 不得以模拟结论或仿真结论替代，也不得因为"其它层都通过"而放行。
- **本层没有自动化载体**，结论依赖人工执行与人工记录，因此证据完整性要求最高。

### 9.5 每层证据要求

- **命令与退出码。** 逐条记录实际执行的命令与其真实退出码，原样保留，不得事后整理成结论式描述。
- **源状态。** 仓库根、源提交标识、工作区状态与未跟踪文件清单；有已跟踪文件改动时附差异摘要。
- **构建配置与覆盖。** Debug 或 Release、目标框架、输出路径覆盖、影响运行的环境变量的实际取值。
- **产物摘要。** 被测程序集、主程序、硬件采样子进程、契约程序集的路径与 SHA-256 及修改时间；测试引用的产物必须与记录的产物同源同摘要，否则测试结论无效。
- **依赖锁定情况。** 各工程的还原图、关键直接依赖版本、包缓存位置与包源。
- **机器环境。** 操作系统、CPU 与内存、.NET SDK、PowerShell、目标硬件与驱动是否具备。
- **人工字段。** 跳过原因、偏离说明、失败处置结论与遗留项逐条手写；机器字段可以整段引用脚本输出，但数字不得改写。
- **失败证据必须保留**，不得只保留通过记录。
- **脱敏。** 证据不得包含密钥、令牌、口令与真实主机名，必要时按字段脱敏。

### 9.6 证据生成

`scripts/collect-evidence.ps1` 生成证据骨架中的机器可推导字段：源状态、构建配置、产物摘要、依赖情况、命令行回显、测试计数器、机器环境。脚本只写入显式指定的输出路径，不改动仓库中受版本控制的文件。逐项原因与人工解释必须手写补充。

## 10. 已知限制

- **架构断言未接入流水线。** `scripts/architecture-assert.ps1` 只在本地手动执行；棘轮基线与实测值之间存在漂移，断言覆盖的口径限于命名空间一致性与引用方向两类。
- **编译警告豁免的粒度是警告码而非位置。** 清单无法定位到具体某条豁免，也无法区分同码的不同成因。
- **写入强度不一致。** 配置文件的写入包含落盘确认与回读校验，历史与流量数据的写入只有原子替换。
- **测试工程整体关闭可空检查。** 测试代码中的可空标注不携带类型信息，真实可空缺陷不在测试工程中暴露。
- **未观察任务异常没有进程级兜底。** 该类异常的处置完全依赖每个 fire-and-forget 调用点的自律，缺少集中出口。
- **目标环境验收层没有自动化载体。** 结论质量取决于人工执行与记录，跨机器复现成本高。
- **依赖清单门禁以还原结果为真值源。** 离线或缓存过期环境下该门禁的判定强度受限。
