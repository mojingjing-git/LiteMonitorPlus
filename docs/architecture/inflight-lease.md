# 在途请求租约模型与请求身份

本文描述 LiteMonitor++ 的**在途请求租约模型**与**请求身份**：同一目标上的并发请求如何被合并为一次真实操作、请求身份由哪些要素构成、超时与取消如何分离、租约条目由谁负责释放，以及采集层的在途共享如何复用同一套模型。适用范围是 `src/Plugins`（`PluginExecutor`、`PluginManager`、`Native/CryptoNative`）、`src/System/HardwareServices/HardwareSamplingCoordinator.cs` 与 `src/System/Pipe/PipeHardwareClient.cs`；插件沙箱的执行语义与网络闸门见 `plugin-sandbox.md`，Web 会话模型见 `web-session.md`，硬件采样子进程隔离见 `process-isolation.md`。

---

## 1. 目标与不变量

### 1.1 目标

- **相同目标的并发请求必须合并，而不是重复发起。** 一组并发调用若指向同一请求身份，实际发出的网络请求数必须恰好为 1。
- **合并不得跨越安全边界。** 两个请求只有在"服务端必然返回相同响应"时才允许共享同一条在途请求；任何影响响应的要素缺席都会变成凭据串用或 proxy 串用。
- **合并窗口不得被单个等待者的退出截断。** 一个等待者超时或取消，不得让仍在进行的请求从共享表中消失，否则后来的调用方会再发一条重复请求。
- **调用方的等待期限与底层操作的生命周期必须解耦。** 调用方超时只终止"本调用方的等待"，不构成对底层操作的取消。
- **每个等待者各自履责自己的策略判定。** 命中已在途的租约不构成绕过目标授权与凭据策略的理由。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| 请求身份 | 一组描述"这个请求是什么"的字段；同一身份 ⇒ 同一请求 ⇒ 同一响应 |
| 摘要 | 请求身份的无歧义编码结果；它的字符串形式就是租约表的键 |
| 租约条目 | 在途表中的一项：一个尚未终结的共享操作 + 其身份键 |
| 持有者 | 租约的持有者，即共享操作本体；它是该身份下唯一发起请求的一方 |
| 等待者 | 加入租约并等待结果的调用方；数量可以任意多 |

### 1.3 组件与职责

| 组件 | 位置 | 职责 | 明确不负责 |
|---|---|---|---|
| `PluginExecutor` | `src/Plugins/PluginExecutor.cs` | HTTP 步骤的请求身份构造、摘要计算、在途表管理、等待者的等待与放弃 | 不做插件调度节奏决策；不实现目标授权策略本身，只调用闸门 |
| `PluginManager` | `src/Plugins/PluginManager.cs` | 插件实例调度、连续失败计数与退避、触发客户端重置与缓存清理 | 不直接访问在途表 |
| `CryptoNative` | `src/Plugins/Native/CryptoNative.cs` | 原生步骤的在途去重、等待者计数、共享操作中止 | 不做 HTTP 步骤的身份计算 |
| `HardwareSamplingCoordinator` | `src/System/HardwareServices/HardwareSamplingCoordinator.cs` | 采集节拍、在途采集的合并与共享、采集落定 | 不负责插件的网络请求 |
| `PipeHardwareClient` | `src/System/Pipe/PipeHardwareClient.cs` | 跨进程采样配置的合并应用、调用方超时的降级口径 | 不负责采集节拍 |

在途表是 `PluginExecutor` 的私有状态。其它组件不得直接访问它。

## 2. 请求身份

### 2.1 身份的构成

请求身份由两组维度构成。

**路由维度**（决定"是哪一个逻辑调用"）：`InstanceId`、`TargetIndex`、`StepId`。

**响应维度**（决定"服务端返回什么"）：`Method`、`CanonicalUrl`、`Body`、`Headers`、`Proxy`、`ResponseEncoding`。

路由维度不参与摘要计算；响应维度全部参与摘要计算。

### 2.2 参与规则

| 字段 | 参与摘要 | 规则 |
|---|---|---|
| `InstanceId` | 否 | 插件实例 ID |
| `TargetIndex` | 否 | 步骤展开出的目标索引 |
| `StepId` | 否 | 步骤 ID |
| `Method` | 是 | 大写规范化；未指定按 `GET` |
| `CanonicalUrl` | 是 | 规范化后的 URL |
| `Body` | 是 | 模板解析后的请求体原文 |
| `Headers` | 是 | 步骤级 Header 全部，占位符解析后 |
| `Proxy` | 是 | proxy 配置，占位符解析后；无则为空串 |
| `ResponseEncoding` | 是 | 响应编码；无则为空串 |

不变量：

- **影响响应的字段一个都不许缺席。** `Method`、`Headers`、`Proxy`、`ResponseEncoding` 任一缺席，URL 与请求体相同的两个步骤就会共用一条在途请求与同一条缓存条目，凭据串用与 proxy 串用随之成立。
- **Header 全部参与，不做白名单过滤。** 漏掉一个携带凭据的 Header 造成的串用，比合并机会减少严重得多。
- **路由维度不进入摘要。** 它们已经是缓存键的前缀，重复编码只会让键结构自相矛盾。

### 2.3 规范化

- **方法**：`Trim()` 后转大写；空白视作未指定，按 `GET` 处理。
- **URL**：`scheme` 与 `host` 转小写；移除 `fragment`；`path` 与 `query` 原样保留（不重排 query —— 参数顺序可能影响语义）；非默认端口保留；`userinfo` 保留（可能携带 Basic 凭据，丢弃即改变请求身份）。
- **Header**：名统一小写（HTTP 头名大小写无关）；按 (名, 值) 排序后再参与摘要，保证拼接顺序确定。

### 2.4 摘要算法

- 摘要 = SHA-256 对固定顺序的拼接串取哈希，输出十六进制后**取前 32 个字符**（128 位）。
- 拼接串以版本前缀 `lm-plugin-req-v1` 开头，字段顺序固定：`版本 | 方法 | 规范化URL | 请求体 | 响应编码 | proxy | Header 数量 | (Header 名, Header 值)*`。
- 字段之间采用"长度前缀 + 冒号"的无歧义编码（`长度:内容`），保证任意字段内容都不会造成字段边界歧义。
- 摘要必须是**纯函数**：同一组输入在任何进程、任何次运行都得到同一个值。`GetHashCode()` 是进程内加盐的 32 位弱摘要，不得用于任何"两个请求是否等价"的判断。

### 2.5 键的构成

| 键 | 构成 | 用途 |
|---|---|---|
| 在途键 | 摘要（逐字相等） | 在途表的查找与合并 |
| 缓存键 | `实例ID \| 目标索引 \| 步骤ID \| 摘要` | 步骤结果缓存；实例前缀使按实例清理成为可能 |

不变量：

- **在途键逐字等于摘要。** 允许目标集合、凭据策略等判定结果不得进入在途键或摘要：它们是"能不能发"的策略，不是"发的是什么"的身份。
- **缓存命中判定与在途合并判定必须使用同一套完整字段集。** 二者共用同一个请求身份对象，不得出现"在途隔离了但缓存没隔离"的组合。
- **在途合并允许跨实例。** 摘要相同即同一请求同一响应，跨实例合并是安全的。缓存保持"每个实例各存各的"，因此 `PluginExecutor.ClearCache(instanceId)` 仍按实例前缀清理，且不波及其它实例。

## 3. 租约模型

### 3.1 生命周期

租约条目的状态是：**未获取 → 在途 → 已终结**（终结即从在途表移除）。共享操作失败时，在途直接转入已终结。

| 环节 | 规则 |
|---|---|
| 获取 | 原子获取：加入动作本身不得直接启动请求 |
| 共享 | 多个等待者等待同一个共享操作；等待者数量不影响条目存活 |
| 终结 | 共享操作成功或异常终结时移除条目，一次 |
| 失效 | 共享操作失败时所有等待者收到该失败；条目移除后新到达者可重新发起 |

### 3.2 原子获取

- 在途表是 `ConcurrentDictionary<string, Lazy<Task<string>>>`。`GetOrAdd` 的 valueFactory **只创建一个未求值的 `Lazy`**，不得在工厂里启动请求。
- `Lazy` 使用 `LazyThreadSafetyMode.ExecutionAndPublication` ⇒ 同一把 `Lazy` 只被求值一次。
- `GetOrAdd` 返回的是字典中实际存着的那一把 ⇒ 落败的工厂产物永不被求值 ⇒ 同一身份下不会发出第二条请求。

这条形态的意义在于：valueFactory 并发执行本身不破坏合并；破坏合并的是"在工厂里直接发请求"。

### 3.3 持有者与等待者

| 维度 | 持有者（共享操作） | 等待者（调用方） |
|---|---|---|
| 数量 | 同一身份下恒为 1 | 任意多个 |
| 取消 | 不受任何等待者的取消令牌影响 | 只影响自己 |
| 失败 | 失败即终结 | 收到同一个失败 |
| 退出 | 由共享操作终结驱动移除 | 只释放自己的等待 |
| 对条目的所有权 | 唯一的移除执行者 | 无 |

不变量：**等待者全部退出不改变持有者的存活**（HTTP 路径）。原生步骤按 §3.6 的规则在最后一个等待者离开时中止共享操作。

### 3.4 移除

- 移除**只在共享操作终结时发生**，由共享操作自身的 continuation 驱动，一次。
- 移除必须使用**比较后原子移除**（`TryRemove(KeyValuePair<TKey, TValue>)` 语义）：仅当该键当前映射的值仍是本条目时才删除。
- **等待者的 `finally` 一律不参与移除。** 等待者的收尾只释放自己的等待。

不变量：

- **旧操作的收尾不得删除同键的新条目。** 无条件 `TryRemove(key, out _)` 会与新到达者插入的条目竞争并误删。
- **合并窗口不得被单个等待者的退出截断。** 第一个等待者拿到结果就删条目 ⇒ 后来者无法加入仍在进行的请求。

### 3.5 失败

- 共享操作失败时，所有等待者收到**同一个**失败。
- 失败后条目按 §3.4 移除，下一批到达者可重新发起。
- 共享操作的异常必须被观察（continuation 内读取任务异常）⇒ 所有等待者都取消时，失败不得变成"未观察到的任务异常"。

### 3.6 原生步骤的变体

原生步骤（`CryptoNative`）的在途表是 `ConcurrentDictionary<string, InflightRequest>`，条目结构是"共享操作 + 等待者计数 + 条目自有的中止令牌"。

| 维度 | HTTP 步骤 | 原生步骤 |
|---|---|---|
| 条目 | `Lazy<Task<string>>` | `InflightRequest` |
| 共享操作的令牌 | 无（`CancellationToken.None`），自带期限 | 条目自有的中止令牌 |
| 最后一个等待者离开 | 共享操作继续跑到自身期限 | 共享操作被中止（释放进程级并发槽位） |
| 作用域键 | 无（按摘要全局合并） | 执行作用域标识 `PluginSandboxScope.ScopeId` |

原生步骤额外保证：

- **共享操作不绑定任何等待者的取消令牌**，只绑定条目自有的中止令牌。
- **最后一个等待者离开时中止共享操作**，避免没人等待时白占进程级并发槽位。
- **加入时若条目刚被中止，必须摘掉它并另起一条**，绝不与一条已被取消的请求合并。
- **不同执行作用域不共享在途请求。** 同一插件实例的两次执行各有各的作用域标识 ⇒ 一个代次到期不会连带打断另一个代次正在复用的同一请求。

### 3.7 条目不绑定客户端

在途条目不绑定任何 `HttpClient` 实例。`PluginExecutor.ResetNetworkClients()` 替换并释放客户端时，在途表不被清空，在途请求不被主动取消；被释放客户端上的在途请求允许自然失败。

## 4. 并发与合并语义

### 4.1 合并保证

同一身份的并发调用，实际发出的请求数必须恰好为 1；所有等待者拿到同一个结果（成功值或同一个失败）。

### 4.2 结果分发

- 成功：所有等待者拿到同一份响应正文，各自进入各自的解析与变换环节。
- 失败：所有等待者拿到同一个失败，不得把失败降级成空结果。

### 4.3 策略判定由每个等待者各自履责

命中已在途的租约时，加入方的请求工厂不会被求值 ⇒ 只在请求出口处做的判定对加入方不生效。目标授权与凭据策略的判定因此必须**前移到加入侧**：每个等待者在加入租约前，用自己的声明主机集合各自校验"是否允许发请求"与"是否允许带凭据"。

不变量：**在途命中不得构成绕过策略的理由。** 白名单更严的调用方不得复用白名单更宽的调用方已经建立的租约。

### 4.4 失败后的可重入

共享操作失败 ⇒ 条目移除 ⇒ 后续到达者重新发起。重入必须使用**完整身份**；以残缺身份重入会建立一条与失败原因无关的新租约，掩盖失败诊断。

## 5. 超时与取消

### 5.1 四类终止条件

| 条件 | 作用域 | 等待者观察到的结果 |
|---|---|---|
| 调用方取消 | 本调用方 | 取消异常；共享操作继续 |
| 作用域总时长到期 | 本调用方 | `PluginSandboxException`，原因码 `LM009_DEADLINE_EXCEEDED`；共享操作继续 |
| 共享操作自身期限 | 共享操作本体 | 所有等待者都失败 |
| 全部等待者离开（原生路径） | 共享操作本体 | 中止；结果无人消费 |

作用域总时长上限是 `PluginSandboxLimits.MaxExecutionDurationMs`（30000 毫秒，含该次执行的所有步骤与所有网络等待）。HTTP 共享操作自身的期限来自 `HttpClient.Timeout`（10 秒）与覆盖整条重定向链的链接令牌。

### 5.2 调用方超时不等于底层操作已取消

**调用方的等待期限与底层操作的生命周期是两件事。** 调用方超时只终止"本调用方的等待"；底层操作可能仍在执行 —— 请求仍可能在途，配置应用仍可能在硬件子进程侧执行。

由此得到三条不变量：

- **不得以相同身份立即另发一条独立请求。** 那会对同一目标产生重复请求，并让两次调用观察到同一副作用。以相同身份再次调用会命中同一条在途租约并等待其结果，这是期望行为。
- **不得因为一个等待者放弃就把租约条目移除。** 移除只由共享操作终结驱动（§3.4）。
- **不得把"调用方已超时"当成"底层已取消"来推断结果。** 调用方拿不到结果，不等于底层没有产生结果。

### 5.3 跨进程的等价口径

`PipeHardwareClient.ApplyConfigAsync` 采用同一条口径：合并键是 revision 与配置内容；调用方超时返回 `SamplingApplyResult`（`Applied = false`，`FailureReason = "timeout:{毫秒}ms"`），底层应用继续在硬件子进程侧执行并保留记录。不同内容的并发调用由 revision 更新的那次**明确取代** revision 更旧的那次，被取代方收到 `FailureReason = "superseded-by-revision:N"`，不静默丢弃配置。

## 6. 所有权与释放

### 6.1 移除责任

| 责任 | 归属 |
|---|---|
| 从在途表移除条目 | 共享操作的 continuation（唯一执行者） |
| 移除的原子性 | 比较后原子移除 |
| 共享操作异常的观察 | 共享操作的 continuation |
| 等待者退出时的清理 | 等待者自身（只释放自己的等待） |

### 6.2 异常路径

- **共享操作抛异常** ⇒ 全部等待者收到该失败；条目被移除；异常已被观察。
- **等待者因取消或期限到期退出** ⇒ 只影响该等待者；条目与其他等待者不受影响。
- **响应体超过字节上限** ⇒ 明确失败，原因码 `LM009_RESPONSE_TOO_LARGE`；响应仍被释放，连接随之归还；绝不截断、静默丢数据。
- **客户端被替换导致在途中止** ⇒ 走普通异常路径返回给等待者，不得触发递归重置、不得放大成重置风暴。

### 6.3 资源释放

- `HttpResponseMessage` 由请求出口所在的代码块释放，正文读取受字节上限约束。
- 插件响应体的字节上限是 `PluginSandboxLimits.MaxResponseBytes`（2 MiB）。
- `PluginExecutor.ResetNetworkClients()` 替换客户端后对旧实例做延迟释放，让在途请求跑完或到期；重置**不**清空在途表、**不**主动取消在途请求。

### 6.4 全局重置的上限

客户端重置是**全局**动作，插件的连续失败计数是**按实例**的。因此重置必须限流：`PluginExecutor` 的重置冷却窗口是 60 秒，同一窗口内至多执行一次真正的重置；窗口内的重复调用是幂等空操作（不替换客户端、不释放资源、不递归重置）。⇒ 单个实例的连续失败最多在窗口内引发一次全局重置，不会形成重置风暴。`ResetNetworkClients()` 的公开签名不因限流而改变。

## 7. 与采集侧采样协调的关系

采集层的在途共享是同一模型的另一处应用。

### 7.1 采集侧的合并

`HardwareSamplingCoordinator` 保证：

- **同一时刻最多一个真实采集任务**，并发消费者共享进行中的任务，不排队。
- **未到期时快速返回**：不创建任务、不调用 `hw.Update()`、不清值缓存、不推进采集时间。
- **在途状态覆盖收尾环节**：采集落定回调跑完才解除在途；完成信号在收尾之后发布 ⇒ 调用方拿到完成信号后立刻取值写入缓存，不会被随后的收尾清掉。
- **共享到的请求单独计数**：`HardwareSamplingStatistics.SharedRequests`。

采集侧的"身份"不需要请求身份对象：采集目标与参数由协调器的节拍决定，而不是由每个调用方各自拼装。合并键就是"当前是否存在一条在途采集"。

### 7.2 采集侧不响应取消

**采集方不响应取消令牌。** 调用方取消只终止它自己的等待，采集继续跑完。这与插件侧"取消一个等待者不得取消共享操作"是同一条不变量。

`WebSessionManager` 的共享采样等待包了一层 2 秒上限（`WebSessionManager.SamplingWaitTimeout`）：超时后降级 —— 照常序列化当前缓存值，不挂死请求线程。

### 7.3 两侧不合并

插件执行发生在主进程，采集发生在硬件采样子进程 ⇒ 两个在途域互不合并，也不共享身份摘要。

## 8. 失败语义一览

| 情形 | 结果形态 |
|---|---|
| 作用域总时长到期 | `PluginSandboxException`，`LM009_DEADLINE_EXCEEDED` |
| 响应体超过字节上限 | `PluginResponseTooLargeException`（继承 `PluginSandboxException`），`LM009_RESPONSE_TOO_LARGE` |
| 目标不在声明/授权集合内 | `LM009_REQUEST_TARGET_NOT_ALLOWED` |
| 带凭据的目标不在声明集合内 | `LM009_CREDENTIAL_TARGET_NOT_ALLOWED` |
| 跨进程采样配置调用方超时 | `SamplingApplyResult.FailureReason = "timeout:{毫秒}ms"` |
| 跨进程采样配置被新版本取代 | `SamplingApplyResult.FailureReason = "superseded-by-revision:N"` |

统计口径：采集侧的共享次数由 `HardwareSamplingStatistics.SharedRequests` 记录。

## 9. 已知限制

- **在途租约只在进程内成立。** 进程重启后租约全部消失；摘要仍可复现，但租约不跨进程共享。
- **摘要是 128 位截断值**（SHA-256 的前 32 个十六进制字符），不是完整 SHA-256。碰撞概率极低，但一旦碰撞，两条不同身份会共用同一条在途请求。
- **Header 全部进入摘要**，因此步骤级 Header 的任何变化都会产生新的在途条目，合并机会随 Header 集合的敏感度下降。
- **HTTP 共享操作不绑定调用方取消。** 最后一个等待者离开后，请求仍会跑到自身期限（默认 10 秒），这段时间内它仍占用一个沙箱并发槽位。
- **原生步骤的共享操作在最后一个等待者离开时被中止**，此时取数结果无人消费。
- **在途表没有容量上限**，条目数只受在途操作的生命周期约束；身份维度组合数很大时，表的大小没有硬边界。
- **缓存与在途是两套独立的合并域。** 两者使用同一套身份字段，但生命周期不同：命中步骤缓存的调用不进入在途表。
